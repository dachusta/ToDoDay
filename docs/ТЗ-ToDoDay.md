## 0. Принятые решения и разрешённые противоречия
Перед чтением зафиксируем ключевые решения по ответам:

## 1. Общее описание

### 1.1 Цель
Веб-приложение ToDoDay для микроменеджмента личных дел. Пользователь формирует библиотеку дел и «шаблоны дней» (таблицы, разбитые на 15-минутные слоты), расставляет дела по слотам и проживает дни один за другим. Каждое дело — переиспользуемая сущность, по которой накапливается статистика выполнения/пропуска.

### 1.2 Область применения (MVP)

- Однопользовательское приложение.

- PWA, offline-first, работа без интернета.

- Хранение — локально (IndexedDB).

- Мобильный приоритет, адаптив до десктопа.

### 1.3 Глоссарий

| Термин | Определение |
| --- | --- |
| Дело (Task) | Переиспользуемая сущность: название, приоритет, цвет, длительность. Живёт в общем списке. |
| Шаблон дня (DayTemplate) | Конфигурация дня: имя, порядок в цикле, диапазон времени, правило повторения. |
| Правило повторения (RepeatRule) | Привязка шаблона к датам календаря: дни недели / числа месяца / без привязки. |
| Экземпляр дня (DayInstance) | Шаблон, «материализованный» на конкретную дату. Содержит размещения дел и статус. |
| Размещение (Placement) | Ссылка на Дело, поставленная в конкретный слот конкретного экземпляра дня. Имеет собственный статус. |
| Слот | Ячейка сетки дня размером 15 минут. |
| Цикл | Последовательность шаблонов дней без календарной привязки, идущая по полю order и зацикливающаяся. |

## 2. Функциональные требования

### 2.1 Управление делами (Tasks)
FR-T-1. Создание дела. Форма содержит поля:

- Название (обязательно, 1–100 символов)

- Приоритет: low | medium | high | critical (обязательно, дефолт medium)

- Цвет: 10 предустановленных HEX + произвольный `#RRGGBB` (обязательно, дефолт — случайный из палитры). Палитра, она же `TASK_PALETTE` в `src/models/task.ts`: `#F44336`, `#E91E63`, `#9C27B0`, `#673AB7`, `#3F51B5`, `#2196F3`, `#009688`, `#4CAF50`, `#FF9800`, `#795548`.

- Длительность: кратно 15 мин, 15–1425 мин (обязательно, дефолт 30 мин). 1425 — это `00:00–23:45`, верхняя граница суток шаблона (FR-D-1).
FR-T-2. Редактирование дела. Допустимо всегда. Заморожены для уже созданных размещений не только длительность, но и подпись дела: у каждого Placement хранится снимок durationMin и taskSnapshot `{ title, color, priority }` на момент размещения, и правка дела их не меняет. Поэтому:
- Правка названия/приоритета/цвета и durationMin задачи разрешена в любой момент, в том числе когда дело стоит в активном (незавершённом) дне.
- Новые размещения берут новое значение durationMin; снимки существующих размещений не пересчитываются (ТЗ §6 правило 9).
- Переименование, смена цвета и приоритета тоже не обновляют уже созданные Placement: доска показывает подпись из снимка, live-обновления карточек по правке дела нет. Новые размещения берут новое значение, существующие — прежнее (ТЗ §6 правило 9). Это не расхождение с библиотекой: в списке дел и в форме дело уже новое, а доска — это снимок момента размещения.
- Снимок конкретного размещения меняется только осознанным действием «Заменить на другое дело» (FR-B-7): тогда и taskSnapshot, и durationMin берутся с нового дела.
- Длительность конкретного размещения меняется отдельно, действием «Изменить длительность» (FR-B-7) — оно правит Placement.durationMin, а не дело.
FR-T-3. Архивация дела. Soft-delete: дело помечается archived: true, пропадает из списка, но остаётся в истории для статистики. В активном экземпляре дня в skipped переводятся только размещения со статусом pending. Уже отмеченные done не меняются. Архивация и перевод размещений не одна транзакция: если emitter не дошёл, `initialize` при следующем открытии ещё раз переводит pending-размещения архивных дел активного дня в skipped. Вернуть дело из архива можно (unarchiveTask). На доску архивное дело поставить нельзя (`placeTask` / `replacePlacement` → CONSTRAINT_VIOLATION).
FR-T-4. Список дел. Отображается на отдельной странице. Поддерживается:

- Сортировка: по названию (localeCompare), приоритету, дате создания, длительности. Приоритет — ранг `low < medium < high < critical`, не алфавит подписи.

- Фильтр: по приоритету, по цвету, «Показать архивные» (`showArchived`). Выключен (дефолт) — в списке только неархивные. Включён — неархивные и архивные в одном списке, архив не подменяет живые дела. «Удалить» (FR-T-6) видно только у строк с `archived: true`. Уникальность названия в MVP не требуется (`isTitleTaken` в контракте не блокирует сохранение).

- Поиск по названию: подстрока после trim, без учёта регистра.

- Мини-сводка на карточке и в таблице: страница читает `statsStore` за период «всё время». `useTasksStore` статистику не импортирует (контракты §7). Нет строки в `perTask` — подпись «не размещалось», не «—» и не 0%. Строка есть — «выполнено / пропущено» и рейт; «—» только если рейт null при placed > 0 (FR-S-2).

- Быстрый drag-and-drop дела прямо на доску дня (если доска открыта в соседней панели на широком экране, с 1024 px).
FR-T-5. Дублирование дела — кнопка «Дублировать» создаёт копию с названием «<Название>» + суффикс из i18n `tasks.copySuffix` (ru: ` (копия)`, en: ` (copy)`). Суффикс не зашит в код по-русски: обрезка считается от уже переведённой строки, чтобы итог не превышал 100 символов из FR-T-1: `suffix = t('tasks.copySuffix')`, `base = title.slice(0, 100 - suffix.length).trimEnd()`. Дубликат неархивный, в том же приоритете, цвете и длительности. Создание дела снэкбаром не отменяется: hard delete неархивного запрещён (FR-T-6), отдельного undo-create нет (вайрфреймы §9.3).
FR-T-6. Удаление дела (hard delete). Безвозвратное удаление разрешено только для архивного дела (FR-T-3) и только с подтверждением в UI. Для неархивного дела действие в меню скрыто, а action возвращает CONSTRAINT_VIOLATION. История не теряется: статистика и история размещений берут подпись из Placement.taskSnapshot, поэтому удаление дела не ломает экран статистики (контракты §1.5, §4.4). Отмены у этого действия нет: снэкбар «Восстановить» относится к архивации, а не к удалению (вайрфреймы §9.3).

### 2.2 Управление днями (DayTemplates)
FR-D-1. Создание шаблона дня. Форма содержит:

- Название (обязательно, 1–50 символов)

- Время начала и конца (дефолт 08:00 – 22:00). Формат строго `HH:mm`: часы 00–23, минуты 00, 15, 30 или 45, обе границы внутри `00:00–23:45`. Конец позже начала, длина ≥ 1 ч. Строка не из этого формата (`abc`, `99:99`, `24:00`, `08:07`) — `INVALID_TIME`, а не тихое приведение. Акцентный цвет — `#RRGGBB`, иначе `INVALID_COLOR`.

- Шаг сетки: 15 мин (жёстко в MVP)

- Правило повторения:

- Без привязки (циклический день)

- По дням недели — мультивыбор Пн–Вс

- По числам месяца — мультивыбор 1–31

Правило нормализуется при сохранении (repeat.normalizeRule): поля, не относящиеся к выбранному type, отбрасываются, значения дедуплицируются и сортируются. То есть `{ type: 'weekdays', weekdays: [0], monthdays: [1] }` сохраняется как `{ type: 'weekdays', weekdays: [0] }`, а не «полурабочее» правило. Значения вне диапазона (weekdays — 0..6, monthdays — 1..31) — ошибка VALIDATION_ERROR/INVALID_RULE, а не тихое отбрасывание; пустой после нормализации набор — EMPTY_RULE (контракты §2.5).

- Цвет-акцент дня (для быстрого различения на списке)
FR-D-2. Порядок в цикле. Каждый шаблон имеет order. Порядок задаётся drag-and-drop на странице «Дни». Перестановка мгновенно влияет на циклическую последовательность.
FR-D-3. Редактирование шаблона. Изменения правила повторения не пересчитывают уже материализованные экземпляры (историю не переписываем). В экземпляр копируются только `timeStart` и `timeEnd` на момент создания. Имя и акцентный цвет читаются из живого шаблона, пока он есть; после удаления — заглушка FR-D-4. Правка времени шаблона уже открытый экземпляр не удлиняет и не укорачивает.
FR-D-4. Удаление шаблона. Если на шаблон ссылается хотя бы один незавершённый (active) экземпляр — запретить удаление, предложить сначала завершить день. Отдельного пользовательского «сброса» дня в MVP нет (`resetCurrentDay` не входит в требования). Завершённые экземпляры удалению не мешают, но остаются в истории со своим templateId: снимка шаблона в DayInstance нет, поэтому после удаления шаблона экран дня/истории показывает для такого экземпляра название-заглушку «Шаблон удалён» (i18n `day.templateDeleted`), а не имя удалённого шаблона. Статистика от этого не страдает — она строится на Placement.taskSnapshot (FR-S-1). Снимок шаблона в модель не добавляем: в MVP имя шаблона в истории не требуется (ТЗ §6 правило 7, контракты §2.7).
FR-D-5. Запрет дублей дат (ответ на Q7). При сохранении правила проверяется, что ни один другой шаблон не покрывает те же даты:

- Для weekdays — пересечение множеств дней недели запрещено.

- Для monthdays — пересечение множеств чисел месяца запрещено.

- Для weekdays и monthdays между собой — пересечения допустимы, приоритет отдаётся monthdays.

- При попытке создать конфликт — показать диалог с перечнем конфликтующих шаблонов.
FR-D-6. Пустой день (ответ на Q7). Если на текущую дату ни один шаблон не подходит — рендерится день без шаблона: сетка по дефолту 08:00–22:00. Пока день виртуальный (размещений нет и в Dexie его нет), по центру CTA «Настроить день» и «Взять дело из списка». «Настроить день» открывает форму нового шаблона (DaysPage / DayTemplateForm). После сохранения DaysPage вызывает `resolveCurrentDay({ force: true })`, и только если день всё ещё виртуальный. Пустой день не «создаётся» отдельной кнопкой: он уже есть в памяти. Два признака не смешивать:

- `isTemplateless` — `templateId === null`. Истина и у виртуального дня, и после того как в него положили дела. В шапке вместо имени шаблона — «Без шаблона» (i18n `day.noTemplate`), не «Шаблон удалён». «Шаблон удалён» только когда `templateId !== null`, а шаблона в сторе нет (FR-D-4).
- Пустое состояние доски (CTA вместо дел) — только `isVirtualInstance`: дня нет в Dexie, `placements` пуст. После первого `placeTask` CTA гаснет, остаётся сетка с делами и подписью «Без шаблона».

Пустой день не имеет привязки к шаблону (`templateId === null`) и существует виртуально, пока не материализован размещением или завершением либо не заменён днём по шаблону. Третьего исхода (день исчез сам по себе) нет: «пустой день» — это одно состояние currentInstance, а не отдельная запись. Отсюда однозначные правила реализации:

- Признак «пустой день ещё не в БД» — id экземпляра не записан в cycleState.activeInstanceId. Пока день виртуален, activeInstanceId === null.
- Материализация: первое размещение (placeTask) или завершение дня (completeDay) сохраняет экземпляр в Dexie под уже выданным id и записывает активный id в cycleState.
- Перезагрузка ничего не теряет: размещений в виртуальном дне нет, а сам день детерминированно пересоздаётся resolveCurrentDay на ту же дату (шаблона на дату по-прежнему нет).
- Если для даты виртуального дня позже появляется подходящий шаблон (создан или изменён на DaysPage), DaysPage вызывает `resolveCurrentDay({ force: true })`, и пустой день заменяется днём по шаблону. force пересчитывает только виртуальный день: сохранённый экземпляр с размещениями так не пересоздаётся.
- Если из уже записанного дня убрали все размещения, экземпляр остаётся в Dexie и CTA не возвращается. «Настроить день» есть только у виртуального дня.
- Пустой день не попадает в историю и не требует завершения при смене даты: диалог завершения для него не показывается (отмечать нечего), а новый день просто разрешается на новую дату (ТЗ §2.9).

Виртуальный день — не «второй способ хранить день», а состояние того же currentInstance: переход виртуального дня в сохранённый описан в ТЗ §2.9, в контрактах §3.4 (resolveCurrentDay, placeTask, completeDay) и в скаффолде (§6.3).

### 2.3 Правила повторения и цикл
FR-C-1. Разрешение текущего дня. При открытии приложения:

- Определяется сегодняшняя дата.

- Ищется шаблон с monthdays, покрывающий это число → он становится активным.

- Иначе — шаблон с weekdays, покрывающий текущий день недели.

- Иначе — берётся следующий циклический шаблон (см. FR-C-2).

- Если ничего не найдено → пустой день.

Числа 29–31, которых нет в текущем месяце, не совпадают ни с одним monthday. День проваливается в weekday, затем в цикл. Отдельного «пустого» исхода только из-за короткого месяца нет.
FR-C-2. Циклическая последовательность. Шаблоны с правилом «без привязки» упорядочены по order. После завершения текущего циклического экземпляра указатель lastCyclicTemplateId становится id этого шаблона. Следующий циклический — первый с order больше указателя; если такого нет — шаблон с минимальным order (зацикливание). Указатель двигается только когда завершённый шаблон циклический. Календарное завершение его не меняет. Если удаляется шаблон, чей id равен указателю, в той же транзакции указатель становится id циклического шаблона с наибольшим order строго меньше удалённого (order до уплотнения). Такого шаблона нет — указатель `null`, и следующее разрешение берёт первый оставшийся циклический. Удаление другого шаблона указатель не двигает. Память cycleStore обновляется без импорта стора дней в обратную сторону: daysStore пишет `cycleState` и шлёт emitter, cycleStore подписан (как `onTaskArchived`). Если все семь дней недели заняты правилами weekdays, циклические шаблоны не выбираются никогда: сохранение не блокируется, форма показывает неблокирующее предупреждение (i18n `days.cyclicUnreachable`) и при сохранении weekdays, закрывших все 7 дней, и при сохранении циклического шаблона, когда неделя уже закрыта. `order` шаблонов всегда уплотнён до `0..n-1`: удаление перенумеровывает оставшиеся в той же транзакции, новый шаблон получает `order = число шаблонов до вставки`. `order` общий для календарных и циклических шаблонов; цикл обходит только `type === none`.
FR-C-3. Ручной сдвиг дня (ответ на Q4). Кнопка «Следующий день →» доступна, только пока текущий экземпляр в статусе active и CycleStateDto.manualShiftDate не равен сегодняшней локальной дате. Повторный ручной сдвиг в те же сутки запрещён (правило 12) и возвращает SHIFT_ALREADY_DONE_TODAY; попытка сдвинуть завершённый день — DAY_NOT_ACTIVE (контракты §0.2, §3.4). Сценарий один и тот же в ТЗ, контрактах и скаффолде:

- Нажатие ставит сессионные флаги shiftPending = true и shiftMode = 'early' | 'overdue' (таблица режимов — ТЗ §2.8) и открывает диалог завершения (FR-E-1). До подтверждения БД не меняется. Закрытие диалога без подтверждения сбрасывает shiftPending и shiftMode.

- Подтверждение идёт через completeDay. Обычная кнопка «Завершить день» флаг не ставит. Если завершаемый день уже на сегодняшнюю дату, следующий экземпляр не создаётся. Если день просрочен (`date` < сегодня), после фиксации всё равно открывается день на сегодня — это ветка FR-E-2, не сдвиг. Оговорка относится только к обычному завершению (`shiftPending = false`); к ручному сдвигу она не применяется — там работает ветка сдвига ниже, и для просроченного дня shiftMode = 'overdue' даёт ровно тот же результат (новый экземпляр на сегодня), но другим путём: с записью `manualShiftDate` и запоминанием `nextInstanceId`. FR-E-2 в этом случае не вызывается, чтобы не создать второй экземпляр на сегодня.

- Если shiftPending: отметки фиксируются по правилам FR-E-2 (отмеченные → done, остальные → skipped), затем manualShiftDate записывается как сегодня (YYYY-MM-DD, локальная дата). Пишет это поле только ручной сдвиг: обычное завершение и авто-сдвиг его не трогают. Ветка «просроченный день открывает сегодня» из FR-E-2 здесь не выполняется: новый экземпляр на сегодня создаёт сам сдвиг (shiftMode = 'overdue'), и второго экземпляра на ту же дату не появляется.

- Новый экземпляр материализуется сразу. Его date и шаблон считает `repeat.resolveShiftTargets` (ТЗ §2.8), а не «сегодня + 1» от `new Date()`:
  - shiftMode = 'early' (сдвиг в те же сутки, экземпляр был на сегодня) — и date, и шаблон на завтра: monthdays завтрашнего числа, иначе weekdays завтрашнего дня недели, иначе следующий циклический по FR-C-2, иначе пустой день. Шапка доски показывает дату экземпляра (завтра), а не настенные сутки. На следующие календарные сутки этот экземпляр уже не просрочен (`date` равна новому «сегодня»), второй копии шаблона нет (сценарий 8);
  - shiftMode = 'overdue' (экземпляр был просрочен, его date < сегодня) — date и шаблон на сегодня: та же цепочка приоритетов для сегодняшней даты. Пропущенные дни не догоняются: «Следующий день» из просроченного дня открывает сегодняшний, а не завтрашний.
  timeStart/timeEnd — снимок шаблона или 08:00–22:00. Новый экземпляр становится активным (activeInstanceId); если он пустой — он виртуален и activeInstanceId = null (FR-D-6). Завершённый остаётся в истории со своей датой.

- Отмена завершения (FR-E-3) удаляет только что созданный этим завершением экземпляр (nextInstanceId, если он был сохранён), возвращает manualShiftDate к значению до сдвига и снова делает активным завершённый экземпляр.

Скаффолд этот переход реализует (скаффолд §6.3).
FR-C-4. Автопереход при смене локальной даты. Триггеры одни и те же: старт (initialize), возврат во вкладку (visibilitychange), таймер на ближайшую локальную полночь. Сравнение дат берёт сегодня из new Date() в момент проверки, а не из минутного кэша useNow. Смена currentDate дополнительно вызывает ту же проверку, когда кэш часов догоняет полночь. Что именно происходит — зависит от состояния текущего дня (ТЗ §2.9):

- Виртуальный пустой день (в Dexie его нет): диалога нет, отметок нет — день просто разрешается заново на новую дату (resolveCurrentDay). В историю ничего не пишется.
- Сохранённый день в статусе completed и его date < сегодня: диалога нет, отметки не переносятся — на новую дату разрешается новый день. Так закрывается случай «день завершили вечером, а приложение осталось открытым до полуночи».
- Сохранённый день в статусе active и его date < сегодня:
  - autoShiftAtMidnight включён — диалог не показывается: выполняется подтверждённый сдвиг из FR-C-3 с shiftMode = 'midnight'. Уже `done` остаётся `done`, `pending` становится `skipped`, уже `skipped` не меняется. В `marks` нельзя класть `'skipped'` для размещения со статусом `done`. Шаблон нового дня — на сегодня, пишется lastAutoShiftDate = сегодня, manualShiftDate не пишется. Перед сдвигом cycleState перечитывается из БД: если lastAutoShiftDate уже равен сегодня, второй авто-сдвиг в те же сутки не выполняется (защита в том числе от второй вкладки). Настройка «спрашивать» в этом режиме диалог не возвращает.
  - autoShiftAtMidnight выключен, askToCompleteOnNewDay включён — показывается диалог завершения (FR-E-1), completionSource = 'auto'.
  - Обе настройки выключены — диалога нет, старый день остаётся активным, пока пользователь не завершит его сам («Завершить день» или «Следующий день →»).

Авто-сдвиг пишет lastAutoShiftDate, а не manualShiftDate. Поэтому он не блокирует один ручной сдвиг в те же сутки: после полуночного сдвига «Следующий день →» создаёт экземпляр с date = завтра и шаблоном на завтра (shiftMode 'early', правило 12, ТЗ §2.8). В следующую полночь `checkDayChange` видит `date >= сегодня` и второй экземпляр не создаёт (сценарий 8). Повторный авто-сдвиг в те же сутки не выполняется.

Таймер полуночи ставится на ближайшие локальные 00:00:05. Если в часовом поясе этой ночи нет местной полуночи (перевод часов вперёд), следующий запуск — `visibilitychange` или старт приложения: оба сравнивают календарную дату через `todayISO()`, а не «прошло ли 24 часа».

Отмена авто-диалога («Вернуться к дню» и «Пропустить диалог в этот раз») ставит сессионный skippedAutoPromptDate = сегодня. Пока флаг равен текущей дате, visibility и таймер диалог не открывают снова. Флаг не пишется в БД и не меняет askToCompleteOnNewDay (ТЗ §2.7). После перезагрузки страницы флаг пуст, диалог показывается снова. Ручное открытие и сдвиг этот флаг не ставят.
FR-C-5. Состояние цикла. Хранится в CycleStateDto — синглтоне cycleState (см. §3.1, файл src/models/dayInstance.ts):

```
interface CycleStateDto {
  id: 'current';                        // ключ синглтона
  activeInstanceId: string | null;      // текущий экземпляр дня; null — дня в БД нет (в т.ч. виртуальный пустой день)
  lastCyclicTemplateId: string | null;  // последний завершённый циклический
  manualShiftDate: string | null;       // дата ручного сдвига (ISO). Пишет только ручной сдвиг; блокирует повторный ручной сдвиг
  lastAutoShiftDate: string | null;     // дата авто-сдвига (ISO). Пишет только autoShiftAtMidnight; защищает от второго авто-сдвига в те же сутки
}
```

### 2.4 Доска дня (DayBoard)
FR-B-1. Сетка. Вертикальный таймлайн с шагом 15 минут. Крупные линии — каждые 30 мин, часовые — жирнее и с подписью HH:00. Слот — это старт интервала: при дне `08:00–22:00` последний слот начинается в 21:45, линия `22:00` — граница `timeEnd`, не слот, в неё дело не ставится. Скролл до текущего времени при открытии. `Slot.label` хранит сырое `HH:mm`; на экран строка выходит через `timeFormat` (FR-SET-3).
FR-B-2. Размещение дел.

- Drag-and-drop из панели «Дела» в слот.

- Перетаскивание уже размещённого дела между слотами.

- Snap к 15-минутной сетке.

- Дело занимает durationMin / 15 слотов подряд. Одно и то же дело можно поставить в день несколько раз: каждое размещение — отдельный Placement со своим статусом.

- Клавиатурная альтернатива drag-and-drop (НФТ §7): у PlacementCard есть меню действий, пункт «Переместить в слот…» открывает список слотов текущего дня; выбор слота делает то же, что drop. Стрелки двигают фокус только внутри этого списка, саму карточку по сетке не переносят. Карточка — focusable (tabindex), Enter/Space открывает меню. aria: карточка — `role="button"`, `aria-pressed` на время перетаскивания, `aria-label` с названием и временем; список слотов — `role="list"`, слот — `role="listitem"` с `aria-label` «08:15».
FR-B-3. Пересечения. Разрешены (по дефолту), но подсвечиваются:

- Конфликтующие дела отображаются полосами с частичным наложением (50% opacity) и иконкой warning.

- В шапке дня счётчик конфликтов — это `conflicts.length`, число пар, а не число карточек. Одна пара наложений даёт баннер «1 конфликт». Баннер информационный, кнопки «Детали» нет: подсветка карточек и есть деталь.

- Интервал размещения полуоткрытый: `[startMin, startMin + durationMin)`. Касание границей (одно кончается там, где другое начинается) конфликтом не является.

- В конфликты попадают только размещения со статусом pending и done, у которых startMin !== null. Пропущенные (skipped) размещения конфликтов не создают и в счётчик не входят: они уже не часть плана дня (detectConflicts, контракты §4.4).

- Настройка showConflicts (ТЗ §2.7) только прячет подсветку и счётчик. Выключение не запрещает наложение и не удаляет пересечения.
FR-B-4. Выход за пределы. Дело, которое не помещается в интервал экземпляра (timeStart–timeEnd снимка, не текущего шаблона), не отклоняется: оно попадает в нераспределённую зону. Признак — Placement.startMin === null. Отрицательный startMin не используется. Проверка «помещается / не помещается» — ветка укладки, а не ошибка валидации: валидный, но не помещающийся слот превращается в null. Невалидный startMin (не целое число, не кратно 15, отрицательный) — это именно VALIDATION_ERROR, данные не меняются (контракты §3.4). Границы считает scheduler.fitInDay(startMin, durationMin, instance) (ТЗ §4.4).
FR-B-5. Нераспределённая зона. Список размещений текущего дня с startMin === null. Пользователь может позже перетащить их в сетку — тогда startMin становится смещением от timeStart, кратным 15 и не меньшим 0.
FR-B-6. Карточка размещения. Показывает:

- Название дела

- Цветную полосу слева (цвет дела)

- Значок приоритета

- Время начала и конца (подпись через `timeFormat`, FR-SET-3)

- Состояние статуса иконкой, не чекбоксом: pending — без отметки, done — ✓, skipped — ✗. Три статуса чекбоксом не различаются (снятая галочка не отделяет pending от skipped). Меняет статус только меню FR-B-7. Пока текущее локальное время попало внутрь интервала размещения, карточка дополнительно показывает ▶. Это только рисунок: `Placement.status` от него не меняется.
FR-B-7. Быстрые действия по размещению (контекстное меню / свайп):

- Отметить выполненным / снять отметку. Если слот ещё не начался, отметка `done` показывает неблокирующее предупреждение и всё равно сохраняется (контракты §3.4 `setPlacementStatus`).

- Отметить пропущенным / снять отметку

- Изменить длительность (только для этого размещения: правит Placement.durationMin, снимок дела не трогает; доступно, пока экземпляр active). Если новый размер с текущим `startMin` не проходит `fitInDay`, размещение уходит в нераспределённые (`startMin = null`), а не отвергается.

- Убрать из дня (удалить это размещение; дело в библиотеке и так остаётся)

- Заменить на другое дело. Снимок и длительность берутся с нового дела. Если новая длительность не влезает в текущий слот, `startMin` становится `null`.

- Переместить в слот… (клавиатурная альтернатива drag-and-drop, FR-B-2)

Полный набор действий совпадает с контекстным меню из вайрфреймов §1.4. Действия, которых нет в скаффолде, перечислены в таблице гэпов (скаффолд §6).

### 2.5 Завершение дня
FR-E-1. Диалог завершения. Триггерится:

- Вручную (кнопка «Завершить день»)

- При сдвиге на следующий день (FR-C-3)

- Автоматически при наступлении новых суток (FR-C-4)
Содержимое диалога:

- Список всех размещений текущего дня с чекбоксами, включая нераспределённые (`startMin === null` — без времени, подпись «без времени»).

- По умолчанию: `done` — отмечены; `pending` и `skipped` — сняты.

- Пользователь может снять галочку с ранее отмеченного `done`.

- Быстрые кнопки «Отметить всё» и «Снять всё».

- Кнопка «Подтвердить». Чекбокс здесь бинарный: отмечено → `done`, снято → `skipped`. На карточке доски чекбокса нет (FR-B-6).

- Опция «Пропустить диалог в этот раз» только у авто-триггера (FR-C-4). Это разовый сессионный пропуск: skippedAutoPromptDate, без записи в настройки. Постоянный отказ — тумблер «Спрашивать о завершении при новом дне» на SettingsPage (вайрфреймы §8, ТЗ §2.7, поле askToCompleteOnNewDay). «Вернуться к дню» у авто-диалога делает тот же разовый пропуск. У ручного завершения и у сдвига «Вернуться к дню» только закрывает диалог.
FR-E-2. Логика фиксации после подтверждения:

- Отмеченные → status = 'done'.

- Не отмеченные (включая ранее помеченные done, с которых сняли галочку) → status = 'skipped'.

- Экземпляр получает status = 'completed', completedAt = Date.now() и остаётся в БД для статистики.

- activeInstanceId не обнуляется. Если завершаемый день имеет сегодняшнюю дату, завершённый экземпляр остаётся текущим до смены календарной даты или до ручного сдвига. Повторное открытие приложения в ту же дату не вызывает resolveCurrentDay и не создаёт второй экземпляр. Ранний сдвиг создаёт экземпляр на завтра, а не второй экземпляр на сегодня (ТЗ §2.8).

- Если завершаемый день просрочен (`date` < сегодня) и это не сдвиг (`shiftPending` ложен): после фиксации сразу разрешается день на сегодня (`resolveCurrentDay`), без диалога и без переноса отметок. Пользователь не остаётся на экране вчерашнего дня. Сдвиг идёт своей веткой (FR-C-3) и этот вызов не дублирует. Созданный экземпляр запоминается в nextInstanceId — его удаляет отмена (FR-E-3). Если фиксация уже записана, а `resolveCurrentDay` вернул ошибку, `completeDay` не делает вид, что всё хорошо: диалог закрывается (повторное «Подтвердить» упрётся в `DAY_NOT_ACTIVE`), статистика всё равно пересчитывается, наружу уходит `DB_ERROR` с `details.reason = 'RESOLVE_AFTER_COMPLETE'`. UI предлагает «Открыть сегодняшний день» — повторный `resolveCurrentDay()`.

- Если завершённый шаблон циклический, lastCyclicTemplateId продвигается и в IndexedDB, и в памяти cycleState. Календарный шаблон указатель не двигает. manualShiftDate и lastAutoShiftDate при обычном завершении не изменяются.

- После успешной фиксации вызывается statsStore.recompute() — экран статистики, если он открыт, показывает новые числа без ручного обновления (контракты §3.4/§3.5, FR-S-1).
FR-E-3. Отмена завершения. Пока в памяти сессии задан lastCompletedInstanceId, в шапке доски видна кнопка «Отменить завершение». Тост «День завершён» (5 с) даёт ту же кнопку как ярлык и не является единственным входом: после его исчезновения кнопка в шапке остаётся до перезагрузки или до успешной отмены. После перезагрузки снапшота нет, экземпляр считается закрытым.

Отмена возвращает день в active, восстанавливает снимок размещений, lastCyclicTemplateId и manualShiftDate и снова делает этот день текущим. Созданный этим завершением экземпляр удаляется всегда: его id пишется в nextInstanceId и для пустого (виртуального) дня, которого ещё нет в Dexie. Если пользователь успел положить в него дела, placeTask материализует тот же id, и отмена удаляет экземпляр вместе с этими делами. Специально не восстанавливается lastAutoShiftDate: авто-сдвиг в эти сутки уже произошёл, повторять его после отмены нельзя — день останется активным до ручного действия или следующей смены даты. После успешной отмены вызывается statsStore.recompute(); ошибка пересчёта логируется и отмену не откатывает (контракты §3.4 cancelCompletion).
FR-E-4. Отсутствие переноса. В MVP невыполненные дела не переносятся на следующий день. Пользователь переносит их вручную из списка дел.

### 2.6 Статистика
FR-S-1. Накопительные счётчики по каждому делу:

- totalPlaced — сколько раз размещалось

- totalDone — выполнено

- totalSkipped — пропущено

- completionRate = totalDone / (totalDone + totalSkipped)

Имена FR и поля TaskStats (контракты §4.1, скаффолд services/stats.ts):

- totalPlaced — placed, подпись «размещено»

- totalDone — done, подпись «выполнено»

- totalSkipped — skipped, подпись «пропущено»

- completionRate — rate, подпись «рейт»
FR-S-2. Экран статистики. Таблица дел, у которых есть хотя бы одно размещение в завершённых экземплярах выбранного периода. Дело без такой истории в таблицу не попадает: строки «0 размещено / 0 выполнено / 0 пропущено» не существует ни для никогда не размещённого дела, ни для дела, размещавшегося только вне периода (нулевой рейт «—» поэтому тоже относится только к делам с размещениями). Строка с рейтом 0% — это дело, у которого в периоде placed > 0 и done = 0 (все размещения пропущены). Несколько завершённых экземпляров на одну календарную дату (импорт без проверки семантики; индекса уникальности `date` нет) считаются все: за этот день в счётчиках может быть больше одного размещения одного дела. Ранний сдвиг второй экземпляр на сегодня не создаёт (ТЗ §2.8). Подпись title/color/priority берётся из снимка с наибольшей датой экземпляра, а при равной дате — с большим `placedAt`. Итоговая сводка считается по всем делам периода. Список показывает все строки периода, с сортировкой и прокруткой, без усечения «первые N» (вайрфреймы §7.1/§7.2). Топ-5 и антитоп-5 в MVP нет. Колонки:

- Название, цвет, приоритет

- Счётчики (placed / done / skipped)

- Прогресс-бар completionRate: `rate = done / (done + skipped)`, при 0/0 — прочерк «—»

- Сортировка по любой колонке
FR-S-3. Периоды. Фильтр: 7 дней / 30 дней / всё время. В MVP обязателен вариант «всё время», он же дефолт экрана. Окно 7 дней — сегодня и 6 предыдущих локальных дат, 30 дней — сегодня и 29 предыдущих.
FR-S-4. Отдельная страница дела. История размещений: дата, время, статус.

### 2.7 Настройки
FR-SET-1. Тема: Light / Dark / Auto (по системной).
FR-SET-2. Язык: ru (дефолт) / en (заготовка).
FR-SET-3. Формат времени: 24ч / 12ч. Применяется ко всем часовым подписям: слоты сетки, интервал на карточке, список диалога завершения, шапка дня. Сетка в данных по-прежнему хранит минуты; `HH:mm` в сторе — внутренний вид, на экран строка выходит через форматтер настройки. `12h` не меняет шаг 15 минут и не меняет хранение.
FR-SET-4. Экспорт данных: JSON-дамп всех сущностей. Точный формат, состав блоков и версия файла — контракты §5.4 (version «1.0»). После успешного экспорта обновляется lastBackupAt.
FR-SET-5. Импорт данных: из JSON, с подтверждением перезаписи. Перед записью файл валидируется структурно: JSON разбирается, version поддерживается, все блоки data присутствуют и совпадают с моделями по форме (контракты §5.4). Семантика не проверяется: пересечение правил, длина дня и кратность длительности импорт не отклоняет. Если в файле два шаблона делят один день недели, день разрешает `repeat.resolveDayForDate` (первый по `order`). `weekdayMap` / `monthdayMap` — кэш того же правила (первый по `order` побеждает, не последний в массиве). Невалидный файл → VALIDATION_ERROR, данные в БД и localStorage не меняются. Импорт таблиц Dexie выполняется одной транзакцией; блок settings пишется в localStorage после неё и в транзакцию не входит. Если Dexie уже записана, а localStorage не принял settings, `importAll` возвращает `STORAGE_ERROR` с `details.reason = 'SETTINGS_AFTER_IMPORT'`: таблицы остаются импортированными, настройки — прежними, повторный полный импорт не запускается сам. Код именно `STORAGE_ERROR`, а не `DB_ERROR`: сбой произошёл на записи настроек, а не в IndexedDB, и UI по коду отличает «повторить запись настроек» от «повторить импорт» (контракты §0.2, §5.4). UI предлагает «Повторить запись настроек» — ту же запись блока settings без второй очистки Dexie. После успешного импорта сторы переинициализируются (reload или полный rehydrate).
FR-SET-6. Спрашивать о завершении при новом дне (askToCompleteOnNewDay, по умолчанию включено). Постоянный выключатель авто-диалога FR-C-4. Разовый пропуск в диалоге эту настройку не меняет.
FR-SET-7. Авто-сдвиг в 00:00 (autoShiftAtMidnight, по умолчанию выключено). Если включено, смена даты выполняет подтверждённый сдвиг из FR-C-3 в режиме 'midnight' (шаблон нового дня — на сегодня) без диалога и пишет lastAutoShiftDate, а не manualShiftDate. Уже выполненные размещения остаются `done` (FR-C-4). Пока выключено, сдвиг только кнопкой «Следующий день».
FR-SET-8. Показывать конфликты (showConflicts, по умолчанию включено). См. FR-B-3: прячет подсветку и счётчик, пересечения по-прежнему разрешены.
FR-SET-9. Первый день недели для отображения (firstDayOfWeek): 0 — понедельник (дефолт), 1 — воскресенье. Влияет только на порядок чипов Пн–Вс в форме шаблона: при 1 ряд начинается с вс. На `RepeatRule.weekdays` не влияет: там 0 всегда понедельник. На заголовок «понедельник, 23 сентября» не влияет.
FR-SET-10. Очистить все данные (clearAll). Кнопка в разделе «Данные» на SettingsPage, помечена как опасная, выполняется только после подтверждения («Удалить все дела, шаблоны и историю? Действие необратимо»). Очищает:
- таблицы Dexie: tasks, dayTemplates, dayInstances;
- singleton cycleState — пересоздаётся через ensureCycleState со значениями по умолчанию (активный день, указатель цикла и обе даты сдвига обнуляются);
- настройки в localStorage по всем ключам `tododay:*`;
- сессионное состояние сторов (currentInstance, кэш статистики, снапшоты отмены завершения).

Экспорт перед очисткой автоматически не делается, но диалог предлагает выгрузить данные, если экспорта ещё не было (lastBackupAt === null). После очистки выполняется та же переинициализация, что и после импорта (reload или rehydrate), и приложение показывает пустые состояния. В коде — settingsStore.clearAll() (контракты §5.3/§5.4).

### 2.8 Правила дат (локальная дата) — единый свод
Все даты в приложении — локальные календарные даты строкой 'YYYY-MM-DD'. Этот раздел — единственное место, где описаны правила; FR-C-3, FR-C-4, FR-S-3 и контракты §3.4 ссылаются сюда.

Определения:

| Понятие | Правило |
| --- | --- |
| Сегодня | `todayISO()` = `format(new Date(), 'yyyy-MM-dd')` (date-fns, локальная зона). Никогда не `toISOString()` и не `new Date('YYYY-MM-DD')` |
| День недели (0 = пн) | `weekday0 = (local.getDay() + 6) % 7`, где `local = parseISODate(iso)`. `Date.getDay()` даёт 0 = воскресенье, поэтому без `+ 6` понедельник становится 1 и правило weekdays съезжает на сутки. `firstDayOfWeek` эту формулу не сдвигает |
| Границы периода статистики | Сравнение строк 'YYYY-MM-DD'; `periodStartISO`: '7d' — сегодня и 6 предыдущих дат, '30d' — сегодня и 29 предыдущих, 'all' — без границы |
| Дата экземпляра | DayInstance.date — локальная дата, на которую день проживается |
| Дата сдвига (targetDate) | Дата нового экземпляра. Для `early` — завтра (`addDaysISO(дата завершаемого, 1)`). Для `midnight` и `overdue` — сегодня |
| Дата шаблона (templateDate) | Дата календаря, по которой выбирается шаблон. Для `early` совпадает с targetDate (завтра). Для `midnight` и `overdue` — сегодня |
| manualShiftDate | Дата последнего ручного сдвига. Пишется только ручным сдвигом (shiftMode 'early'/'overdue'); блокирует повторный ручной сдвиг, пока равна сегодня |
| lastAutoShiftDate | Дата последнего авто-сдвига. Пишется только autoShiftAtMidnight (shiftMode 'midnight'); блокирует повторный авто-сдвиг в те же сутки |

Запрещено во всём проекте:

- `new Date('YYYY-MM-DD')` — парсится как UTC-полночь и на границе суток/периода даёт сдвиг на день. Для разбора ISO-даты использовать локальный конструктор `new Date(y, m - 1, d)` (helper `dates.parseISODate`); правило проверяется линтером (скаффолд §3.5, no-restricted-syntax).
- `toISOString()` для получения календарной даты — только для timestamps (`createdAt`, `completedAt`, `exportedAt`).
- Арифметика дат «вручную» через `Date.now() + 86400000` — только через `dates.addDaysISO(iso, n)`.

Режимы сдвига (передаются в completeDay через состояние shiftMode, контракты §3.1/§3.4):

| Режим | Когда | Дата завершаемого экземпляра | targetDate | templateDate | Что пишется | Диалог |
| --- | --- | --- | --- | --- | --- | --- |
| early | Ручной сдвиг «Следующий день →» в те же сутки | = сегодня | завтра | завтра | manualShiftDate = сегодня | Да (FR-E-1, shift) |
| overdue | Ручной сдвиг, когда активный день просрочен | < сегодня | сегодня | сегодня | manualShiftDate = сегодня | Да (FR-E-1, shift) |
| midnight | autoShiftAtMidnight в момент смены даты | < сегодня | сегодня | сегодня | lastAutoShiftDate = сегодня; manualShiftDate не пишется | Нет (FR-C-4) |

Формула: для `'early'` при `instanceDate === сегодня` обе даты равны `addDaysISO(instanceDate, 1)`; для `'midnight'` и `'overdue'` обе даты равны сегодня. Шаблон берётся от даты завершаемого экземпляра, а не от `new Date() + 1` в момент сдвига: просроченный день поэтому не перескакивает сегодня. Реализация — чистая функция `repeat.resolveShiftTargets(instanceDate, today, mode)` (ТЗ §4.4, скаффолд §7.1). Инвариант: режим 'early' допустим только при `instanceDate === today`; если состояние противоречиво, функция возвращает режим 'overdue' (обе даты — сегодня) и пишет console.warn.

Смена даты без сдвига:

- Завершённый вчера день при смене даты не переиспользуется: на сегодня разрешается новый день (FR-C-4, FR-E-2).
- Просроченные дни не «догоняются»: сколько бы дней ни было пропущено, следующий проживаемый день — сегодняшний.

### 2.9 Жизненный цикл текущего дня
Состояния currentInstance и переходы. Отдельного поля «состояние» в модели нет: состояние выводится из presence в Dexie, InstanceStatus и активного id.

| Состояние | В Dexie | InstanceStatus | Признак | Как попадаем |
| --- | --- | --- | --- | --- |
| virtual-empty (пустой день) | Нет | — (в памяти 'active') | `activeInstanceId !== currentInstance.id` (обычно null) | resolveCurrentDay, когда ни один шаблон не подошёл (FR-D-6) |
| active | Да | 'active' | `activeInstanceId === currentInstance.id` | resolveCurrentDay по шаблону; либо placeTask/completeDay материализовали пустой день; либо resolveCurrentDay({ force: true }) заменил виртуальный день днём по шаблону |
| completed | Да | 'completed' | `activeInstanceId === currentInstance.id` | completeDay без сдвига, когда дата дня = сегодня |
| next (создан завершением) | Да или нет | 'active' | новый id в activeInstanceId (или null, если новый день пустой) | completeDay со shiftPending (FR-C-3); либо автопереход с просроченного дня (FR-E-2) |

Переходы:

```
virtual-empty --placeTask--------> active        (экземпляр пишется в Dexie, activeInstanceId = id)
virtual-empty --completeDay------> completed     (пустой день сохраняется в историю: FR-D-6)
virtual-empty --шаблон появился--> active        (resolveCurrentDay({ force: true }) заменяет виртуальный день днём по шаблону; FR-D-6)
virtual-empty --смена даты-------> virtual-empty/active на новую дату (в историю не пишется, диалога нет)
active        --completeDay------> completed     (дата дня = сегодня: экземпляр остаётся текущим)
active        --completeDay+shift> next          (early: date = завтра; overdue/midnight: date = сегодня; старый — completed)
active(просрочен)--completeDay---> completed + next на сегодня (без диалога и без отметок, FR-E-2)
completed     --cancelCompletion-> active        (в течение сессии, FR-E-3; next-экземпляр удаляется)
completed     --смена даты-------> active/virtual-empty на сегодня (без диалога, отметки не переносятся)
active(просроч)--смена даты------> диалог завершения или авто-сдвиг (FR-C-4) или тишина (обе настройки выключены)
```

Инварианты:

- Ранний сдвиг не кладёт второй экземпляр на сегодня: завершённый день остаётся со своей датой, новый получает завтра. Индекса уникальности `dayInstances.date` всё равно нет: импорт семантику не проверяет и может принести две записи на одну дату (FR-SET-5). `resolveCurrentDay` второй экземпляр на уже текущую дату не создаёт. Экземпляр, датированный будущим (следствие раннего сдвига), остаётся текущим и после перезапуска приложения до полуночи: `initialize` не создаёт новый экземпляр на сегодня и не теряет день, выбранный пользователем (сценарий 9 в §2.10).
- Виртуальный день всегда пуст: placements = [], поэтому его потеря при перезагрузке безопасна.
- Виртуальный день перестаёт быть текущим только тремя путями: его материализуют placeTask/completeDay, его заменяет resolveCurrentDay({ force: true }) при появлении шаблона на эту дату, либо смена даты разрешает день заново. Молчаливого исчезновения без нового currentInstance не бывает (FR-D-6).
- Завершать можно и пустой день — это единственный случай, когда в истории появляется экземпляр без размещений.

### 2.10 Нормативные сценарии
Сценарии ниже — часть требований: тесты в контрактах §9 проверяют именно их.

1. Вчерашний день не завершён, приложение открыто сегодня, autoShiftAtMidnight выключен, askToCompleteOnNewDay включён. Показывается диалог завершения с вчерашним днём (FR-C-4). «Пропустить диалог в этот раз» ставит skippedAutoPromptDate: до перезагрузки диалог не возвращается, вчерашний день остаётся активным. Подтверждение переводит вчерашний день в completed и разрешает день на сегодня (FR-E-2). «Отменить завершение» в сессии возвращает вчерашний день и удаляет созданный сегодняшний.
2. То же, но autoShiftAtMidnight включён, и во вчерашнем дне часть размещений уже `done`. Диалога нет: `done` остаётся `done`, pending становится skipped, manualShiftDate не пишется, lastAutoShiftDate = сегодня, новый экземпляр — дата сегодня, шаблон на сегодняшний календарь. Повторный вызов checkDayChange в те же сутки сдвиг не повторяет. Кнопка «Следующий день →» в эти сутки доступна: она создаст экземпляр с датой завтра и шаблоном на завтра (shiftMode 'early').
3. Ручной сдвиг в тот же день, когда экземпляр уже на сегодня. Первый сдвиг: manualShiftDate = сегодня, новый экземпляр — дата завтра, шаблон на завтра. Шапка показывает завтрашнюю дату. Второй сдвиг в те же календарные сутки: кнопка недоступна (canShiftNext = false), action возвращает SHIFT_ALREADY_DONE_TODAY, БД не меняется.
4. Сдвиг просроченного дня вручную (вчерашний день, пользователь нажал «Следующий день →»). shiftMode = 'overdue': новый экземпляр — дата сегодня, шаблон на сегодня (не на завтра), manualShiftDate = сегодня.
5. Пустой день: шаблонов нет. День показывается как пустой, в Dexie ничего нет, activeInstanceId = null. Добавление первого дела сохраняет экземпляр и activeInstanceId. Перезагрузка до добавления дела даёт тот же пустой день; перезагрузка после — день с делом. Если на DaysPage создан шаблон на сегодня, DaysPage вызывает `resolveCurrentDay({ force: true })`, и виртуальный день сменяется днём по шаблону (в Dexie появляется уже день по шаблону, а не пустой). Завершение пустого дня сохраняет экземпляр с placements = [] в историю.
6. Пустой день и смена даты. В полночь виртуальный пустой день не показывается в диалоге и не попадает в историю: он просто разрешается на новую дату. Если после полуночи для новой даты есть шаблон, день сразу материализуется по шаблону.
7. Дело удалено из архива, а его размещения остались в завершённых днях. Статистика показывает его по taskSnapshot размещений (FR-T-6, контракты §4.4), экран истории размещений — по тем же снимкам.
8. Ранний сдвиг и следующие сутки. В понедельник вечером «Следующий день →» создаёт экземпляр с датой вторника и вторничным шаблоном; понедельничный экземпляр остаётся завершённым со своей датой. Во вторник 00:00 `checkDayChange` видит `date >= сегодня` и выходит: диалога нет, второй экземпляр с тем же шаблоном не создаётся. То же после цепочки «полуночный авто-сдвиг, затем ранний сдвиг» из сценария 2.
9. Ранний сдвиг и перезапуск до полуночи. Понедельник вечером выполнен ранний сдвиг (сценарий 8), экземпляр датирован вторником. Если приложение перезапустить в те же сутки до 00:00, текущим остаётся вторничный экземпляр: `initialize` видит `date >= сегодня`, `resolveCurrentDay` не вызывается, второй экземпляр на понедельник не создаётся, `activeInstanceId` не меняется. В полночь `checkDayChange` выходит по тому же условию: диалога нет, отметки не переносятся.

### 3.3 Политика миграций Dexie
Схема версионирована (`db.version(n).stores({...})`). Правила для MVP и дальше:

- Текущая схема — version(1). Правки документа, не меняющие набор таблиц/индексов (например, добавление поля `lastAutoShiftDate` в cycleState в ревизии 1.2), новую версию не требуют: отсутствующие поля достраивает `ensureCycleState()` дефолтами, а не Dexie-миграция.
- Как только меняется набор таблиц или индексов — добавляется `db.version(n + 1).stores({...}).upgrade(tx => ...)`. Индексы в новой версии перечисляются полностью (Dexie не наследует их автоматически), удаление индекса оформляется строкой без него.
- Данные пользователя миграция не удаляет: upgrade-функция только дополняет/перекладывает поля. Деструктивная миграция (очистка таблицы) недопустима без подтверждения пользователя.
- Изменение схемы обязательно отмечается в этом ТЗ и в журнале правок; тест `db.schema` проверяет, что объявленная версия совпадает с ожидаемой.
- Импорт JSON из файла другой версии формата не мигрирует БД: версия формата проверяется до записи (контракты §5.4), при несовпадении импорт отклоняется.

### 3.4 Локальные даты в модели
Поля-даты моделей (`DayInstance.date`, `CycleStateDto.manualShiftDate`, `lastAutoShiftDate`) хранят локальную календарную дату 'YYYY-MM-DD'. Полный свод правил — ТЗ §2.8.

### 4.4 Сервисы (чистые функции)

Даты (ТЗ §2.8, файл services/dates.ts):

- dates.todayISO(): string — сегодняшняя локальная дата 'YYYY-MM-DD'.

- dates.toLocalISO(date: Date): string — локальная дата из Date (без UTC-сдвига).

- dates.addDaysISO(iso: string, n: number): string — арифметика по календарю.

- dates.parseISODate(iso: string): Date — локальная полночь (`new Date(y, m-1, d)`).

- dates.minutesOfDay('HH:mm'): number — минуты от начала суток. Для уже проверенной строки.

- dates.parseClock('HH:mm'): number | null — FR-D-1. null, если это не `HH:mm` с минутами 00/15/30/45 в диапазоне `00:00–23:45`.

Цикл и правила дней (services/repeat.ts):

- repeat.resolveDayForDate(date, templates, lastCyclicTemplateId): DayTemplate | null — FR-C-1.

- repeat.resolveShiftTargets(instanceDate, today, mode): { mode: ShiftMode; targetDate: string; templateDate: string } — ТЗ §2.8. Единственное место, где вычисляются даты сдвига: для `'early'` при `instanceDate === today` обе даты равны `addDaysISO(instanceDate, 1)`; для `'midnight'` и `'overdue'` обе равны `today`. Инвариант 'early' требует `instanceDate === today`, иначе возвращается 'overdue' + console.warn.

- repeat.normalizeRule(rule): RepeatRule — FR-D-1: отбрасывает поля, не относящиеся к type, дедуплицирует и сортирует значения.

- repeat.validateRule(rule): ValidationIssue[] — EMPTY_RULE (пустой набор) и INVALID_RULE (значения вне диапазона 0..6 / 1..31 или не целые).

- repeat.validateNoOverlap(rule, templates, excludeId?): ValidationIssue[] — FR-D-5. Правило и правила других шаблонов нормализуются; результат — ValidationIssue с conflictingTemplateIds и values (единый тип, см. §3.1).

Раскладка доски (services/scheduler.ts):

- scheduler.isValidStartMin(v: unknown): v is number — true только для целого, кратного 15, ≥ 0. Невалидный startMin — ошибка VALIDATION_ERROR, а не snap и не null (контракты §3.4).

- scheduler.fitInDay(startMin: number, durationMin: number, instance: DayInstance): boolean — FR-B-4. Вызывается только с не-null и уже проверенным startMin; границы берутся из снимка экземпляра (timeStart/timeEnd), не из шаблона. Дело помещается, если `startMin + durationMin <= minutesOfDay(timeEnd) - minutesOfDay(timeStart)`.

- scheduler.detectConflicts(placements): Conflict[] — FR-B-3. Учитывает только размещения со startMin !== null и статусом pending или done; skipped конфликтов не создаёт. Интервал полуоткрытый: касание `startMin + durationMin` следующего размещения — не конфликт.

Статистика (services/stats.ts):

- stats.aggregateStats(instances, period, today): { perTask: Map<string, TaskStats>; overall: OverallStats } — FR-S-1. `today` — локальная дата `'YYYY-MM-DD'`, аргумент, не `new Date()` внутри функции.

### 5.3 Ключевые компоненты

- DayGrid — колонка времени может виртуализироваться; слой карточек размещений лежит поверх всей высоты дня и не привязан к размонтированию слота (НФТ §7). Перенос по сетке — pointer events, не vuedraggable (ТЗ §4.1).

- PlacementCard — карточка на абсолютном позиционировании с высотой, пропорциональной длительности. Ключ списка — placement.id, чтобы виртуальный скролл не пересоздавал карточки; состав карточки считается из снимка размещения, без создания новых объектов в разметке (НФТ §7).

- CompleteDayDialog — модалка со списком размещений, чекбоксами, кнопками. Для пустого/незаполненного дня показывает состояние «нечего отмечать» и не открывается автоматически (FR-C-4, ТЗ §2.9).

- DayTemplateForm — форма с динамическим блоком RepeatRule (поля, не относящиеся к выбранному type, скрыты и нормализуются при сохранении).

- PlacementActions (контекстное меню/свайп) — единый список действий FR-B-7, он же клавиатурная альтернатива drag-and-drop.

Quasar Dark plugin + авто-переключение по системной.

## 7. Нефункциональные требования

- Производительность: FCP < 1.5 c на 3G; доска дня рендерит 100+ размещений без просадок. Виртуализируется колонка подписей времени. Слой размещений позиционируется на всю высоту дня и не размонтируется вместе с якорным слотом: карточка на несколько слотов не должна пропадать, когда её первый слот вышел из окна. Ключ карточки — placement.id. Тяжёлые вычисления (слоты, конфликты, границы) — в computed/getters, а не в разметке.

- Офлайн: 100% функционала доступно без сети (PWA + service worker).

- Хранение: IndexedDB, экспорт/импорт JSON (политика миграций — ТЗ §3.3).

- Доступность: контраст WCAG AA; focus-trap в модалках; клавиатурная альтернатива drag-and-drop — меню «Переместить в слот…», стрелки только внутри списка слотов (FR-B-2, FR-B-7). PlacementCard — `role="button"`, `aria-pressed` на время перетаскивания, `aria-label` с названием и временем. Список слотов — `role="list"`, слот — `role="listitem"` с именем «08:15». Перенос объявляется через `aria-live`.

- i18n: ru (дефолт), en (заготовка), все строки через vue-i18n, включая раздел настроек и служебные тексты (скаффолд §9.3/§9.4). Переключение языка немедленно меняет локаль i18n (контракты §5.3).

- Адаптив: breakpoints Quasar; mobile-first.

- Тесты: Vitest для services/* и сторов (покрытие ≥ 70% на критичных модулях). Обязательный минимум — сценарии ТЗ §2.10 и правила дат ТЗ §2.8 (список в контрактах §9).

- Логирование: `console.warn` — только для ожидаемых доменных аномалий и нефатальных ошибок побочных эффектов, по закрытому списку из четырёх пунктов, которые покрывают пять мест вызова: (1) противоречивый режим сдвига — `early` при `instanceDate !== сегодня` (`repeat.resolveShiftTargets` вырождает его в `overdue`, ТЗ §2.8); (2) `shiftPending` без `shiftMode` в `completeDay` — режим выводится из даты завершаемого экземпляра (скаффолд §6.3); (3) ошибка `statsStore.recompute()` после `completeDay` / `cancelCompletion` — пункт покрывает оба вызова, фиксация дня и отмена считаются успешными, статистику можно пересчитать позже (FR-E-2, FR-E-3); (4) ошибка обработчика `onTaskArchived` при переводе pending-размещений в skipped — архивация уже записана в БД, добьёт её следующий `initialize` (FR-T-3). Ни один warn из списка не подменяет `Result` основной операции: наружу отдаётся успех, если сама операция записана. Любой `console.warn` вне списка — нарушение НФТ; если список начнёт расти, warn'ы уходят в один `logger`-сервис. `console.log` / `console.error` в коде приложения не используются. Пересечение правил шаблона — это `CONFLICT`, не warn. Недостижимый цикл — строка формы `days.cyclicUnreachable`, не запись в консоль. Ошибки БД основной операции — `Result.err` с кодом `DB_ERROR`, а не warn.

### 8.3 Порядок и зависимости

1. Этап 0 — обязательная база: без него проект не запускается и не проверяется.
2. Этап 1 закрывает весь слой данных до UI: страницы и компоненты опираются на готовый API контрактов.
3. Этап 2 даёт каркас навигации; после него модули идут в порядке «Дела» (3) → «Дни» (4) → «Доска» (5) → «Завершение» (6) → «Статистика» (7) → «Настройки» (8): доска и завершение используют дела и шаблоны, статистика — завершённые экземпляры.
4. Тесты (этап 9) пишутся инкрементально: юнит-тесты сервисов — сразу после этапа 0, интеграционные тесты сторов — после этапа 1, сценарии доски и завершения — после этапов 5–6. В таблице этап 9 идёт после UI только для сквозной оценки, а не как «тесты в самом конце».
5. Этап 10 — финальная полировка и полная приёмка по чек-листу ТЗ §9.

### 8.4 Оценка и допущения

- Итог — ориентир ~20 рабочих дней одного разработчика на оставшийся после скаффолда объём. Цифра — оценка сложности, а не срок: реальный срок зависит от числа разработчиков и знакомства со стеком.
- Допущения: работа ведётся по контрактам как источнику истины (при расхождении правится скаффолд); версии пакетов из `package.json` скаффолда проверены (ТЗ §4.1.1); прогон `pnpm typecheck`/`lint`/`test` в текущем окружении не выполнялся и входит в этапы 0 и 9 (скаффолд §11, приложение И журнала).
- Оценки не включают: повторную реализацию уже закрытого скаффолдом (8.1), открытые вопросы ТЗ §10, расширение словарей i18n сверх фактического объёма (130 ключей скаффолда; ревизия 1.11.0 добавила три ключа навигации, ревизия 1.12.0 — 52 ключа раздела `tasks.*`, ревизия 1.13.0 — 48 ключей раздела `days.*` и `common.close`, ревизия 1.14.0 — 20 ключей разделов `day.*` и `placement.*`, ревизия 1.15.0 — 8 ключей разделов `day.*` и `completion.*`, ревизия 1.16.0 — 21 ключ раздела `stats.*`, ревизия 1.17.0 — 6 ключей раздела `settings.*`, итого 288 — приложения П, Р, С, Т, У, Ф и Х журнала) и сокращение словарей/типов (вынесено за рамки, приложения И/К журнала).

## 9. Критерии приёмки
По делам:

- □  Можно создать дело с названием, приоритетом, цветом, длительностью кратной 15 мин.

- □  Дело можно редактировать, архивировать, дублировать.

- □  Валидация не пропускает пустое имя и длительность вне диапазона.

- □  Дубликат с длинным названием получает суффикс текущей локали (`tasks.copySuffix`) длиной не более 100 символов вместе с базой (FR-T-5).

- □  Длительность 1425 принимается, 1440 и некратная 15 — нет (FR-T-1).

- □  Правка durationMin задачи не меняет durationMin уже созданных размещений (FR-T-2, правило 9).

- □  Переименование, смена цвета и приоритета не меняют taskSnapshot уже созданных размещений: доска показывает прежнюю подпись, новое размещение — новую (FR-T-2, правило 9).

- □  Безвозвратное удаление доступно только архивному делу и требует подтверждения; у неархивного — CONSTRAINT_VIOLATION (FR-T-6).
По дням:

- □  Можно создать шаблон с диапазоном, правилом и порядком в цикле.

- □  Попытка создать пересекающееся правило даёт ошибку с перечнем конфликтов.

- □  Правило с лишними для своего type полями сохраняется нормализованным, значения вне диапазона отклоняются (FR-D-1).

- □  Для даты без подходящего шаблона показывается пустой день.

- □  Пустой день отсутствует в Dexie, пока не материализован делом/завершением или не заменён днём по шаблону (FR-D-6).

- □  Создание шаблона на дату виртуального дня заменяет пустой день днём по шаблону (resolveCurrentDay({ force: true })); материализованный день force не пересоздаёт (FR-D-6).

- □  Первое дело в пустом дне сохраняет экземпляр и activeInstanceId; перезагрузка восстанавливает день (FR-D-6).

- □  Удаление шаблона с активным экземпляром запрещено; завершённые экземпляры удалённого шаблона показывают «Шаблон удалён» (FR-D-4).
По циклу:

- □  Календарные шаблоны подставляются по дате.

- □  Циклические шаблоны идут по order и зацикливаются.

- □  Кнопка «Следующий день» доступна только для незавершённого дня.

- □  Ручной сдвиг в те же сутки создаёт экземпляр с датой «завтра» и шаблоном на завтра (shiftMode 'early'). На следующие сутки второй экземпляр с тем же шаблоном не создаётся (сценарий 8), FR-C-3.

- □  Сдвиг просроченного дня и авто-сдвиг в полночь создают экземпляр с датой «сегодня» и шаблоном на сегодня ('overdue'/'midnight'), FR-C-3/FR-C-4.

- □  Авто-сдвиг пишет lastAutoShiftDate и не блокирует ручной сдвиг в те же сутки; второй авто-сдвиг в те же сутки не выполняется, FR-C-4.

- □  Авто-сдвиг не переводит уже `done` в `skipped` (сценарий 2).

- □  Смена даты при незакрытом дне: диалог, если авто-сдвиг выключен и «спрашивать» включено; тишина, если выключены обе настройки (FR-C-4).

- □  Завершённый вчера день при смене даты заменяется днём на сегодня без диалога и без переноса отметок (правило 13).

- □  Виртуальный пустой день при смене даты не попадает в историю и не открывает диалог (правило 14).

- □  Повторное открытие в ту же дату не создаёт второй экземпляр уже завершённого дня.

- □  Второй ручной сдвиг за сутки недоступен и отклоняется кодом SHIFT_ALREADY_DONE_TODAY; сдвиг завершённого дня — DAY_NOT_ACTIVE.

- □  Все календарные даты берутся через services/dates.ts; в коде нет new Date('YYYY-MM-DD') и toISOString() для дат (ТЗ §2.8).
По доске:

- □  Drag-and-drop из списка в слот и между слотами работает.

- □  Перемещение доступно с клавиатуры через меню размещения (НФТ §7).

- □  Сетка 15 мин, крупные линии каждые 30 мин.

- □  Пересечения подсвечиваются; skipped в конфликты не попадает (FR-B-3).

- □  Дело, не влезающее в день, уходит в «нераспределённые» (startMin = null).

- □  Невалидный startMin возвращает VALIDATION_ERROR и не меняет размещение (FR-B-4).

- □  Контекстное меню размещения содержит «Изменить длительность» (FR-B-7).
По завершению:

- □  Диалог показывает все размещения с чекбоксами.

- □  Отмена галочки помечает дело skipped.

- □  После подтверждения экземпляр получает completed.

- □  После завершения дня статистика пересчитывается без ручного обновления (FR-S-1, контракты §3.4).

- □  Отмена завершения доступна всю сессию кнопкой в шапке доски (тост 5 с её не заменяет) и удаляет экземпляр, созданный этим завершением, в том числе пустой и уже с делами; статистика пересчитывается (FR-E-3).
По статистике:

- □  Счётчики done/skipped/rate корректны.

- □  Дело без размещений в завершённых экземплярах периода в таблицу не попадает; строка «0 размещено / 0 выполнено» не существует (FR-S-2).

- □  Рейт 0% показывается только для placed > 0 и done = 0.

- □  На странице дела видна история размещений.
Настройки и данные:

- □  Время шаблона вне `HH:mm` с минутами 00/15/30/45 и цвет акцента не в `#RRGGBB` отклоняются (FR-D-1).

- □  С 1024 px нижней таб-панели нет, до 1024 px она есть (ТЗ §5.1, вайрфреймы §11).

- □  Переключение языка немедленно меняет локаль интерфейса (FR-SET-2, контракты §5.3).

- □  Экспорт создаёт JSON с version «1.0»; импорт невалидного файла отклоняется без изменения данных (FR-SET-4/5).

- □  Сбой записи настроек после импорта даёт код STORAGE_ERROR (не DB_ERROR), Dexie остаётся импортированной, повторяется только запись settings (FR-SET-5, контракты §0.2).

- □  «Очистить все данные» требует подтверждения и очищает Dexie, cycleState и localStorage (FR-SET-10).
НФТ:

- □  Приложение работает офлайн.

- □  Устанавливается как PWA.

- □  Есть ru/en, light/dark.

- □  Все строки интерфейса, включая раздел настроек, приходят из i18n (скаффолд §9.3/§9.4).
