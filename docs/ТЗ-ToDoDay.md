## 1. Общее описание

### 1.1 Цель
Веб-приложение ToDoDay для микроменеджмента личных дел. Пользователь формирует библиотеку дел и планы дней — конкретные, повторяющиеся или заготовки без даты — расставляет дела по 15-минутной сетке и проживает дни один за другим. «Сегодня» исполняет план дня; любые отклонения сохраняются фактом дня и не переписывают план. Каждое дело — переиспользуемая сущность, по которой накапливается статистика выполнения/пропуска.

### 1.2 Область применения (MVP)

- Однопользовательское приложение.

- PWA, offline-first, работа без интернета.

- Хранение — локально (IndexedDB).

- Мобильный приоритет, адаптив до десктопа.

### 1.3 Глоссарий

| Термин | Определение |
| --- | --- |
| Дело (Task) | Переиспользуемая сущность: название, приоритет, цвет, длительность. Живёт в общем списке. |
| План дня (DayPlan) | Единая сущность раздела «Дни»: имя, акцент, диапазон времени, правило повторения, `date` (только у конкретного дня) и список `plannedPlacements`. Существует в одном из трёх режимов — `oneoff`, `recurring`, `template`. |
| Режим плана (DayPlanMode) | `oneoff` — конкретная дата и правило `none`; `recurring` — правило `weekdays`/`monthdays`, `date: null`; `template` — заготовка «без даты», `date: null`, правило `none`. Вычисляется `planMode`, а не хранится отдельным полем. |
| Элемент плана (PlannedPlacement) | Ссылка на дело внутри плана: `id`, `taskId`, `startMin` (смещение от `timeStart`, `null` — без времени), `durationMin`. Это замысел, а не факт исполнения. |
| Правило повторения (RepeatRule) | Привязка плана к датам календаря: дни недели, числа месяца или без привязки. |
| Экземпляр дня (DayInstance) | Факт конкретной даты: `planId`, размещения, статус, снимок диапазона времени. Экземпляр живёт в Dexie, кроме виртуального пустого дня. |
| Размещение (Placement) | Ссылка на дело в конкретном слоте конкретного экземпляра дня. Имеет собственный статус, снимок дела и признаки `plannedId`, `unplanned`, `shifted`, `durationChanged`, `plannedDurationMin`, `removed`. |
| `plannedId` | id элемента плана, из которого создано размещение. `null` — дело добавлено в «Сегодня» вне плана. У легаси-записей поле отсутствует и нормализуется при чтении. |
| `unplanned` | Признак «нет плановой основы»: добавлено, заменено, убрано в «Сегодня» или элемент плана исчез. Перенос по времени и изменение длительности сюда не входят. |
| `shifted` | Признак «плановое дело перенесли по времени в „Сегодня“»: дело и длительность те же, время другое. У размещения без слота (`startMin: null`) не ставится. |
| `durationChanged` | Признак «длительность отличается от плановой» (у добавленного/заменённого — от исходной длительности на момент появления). |
| `plannedDurationMin` | Базовая длительность: у планового размещения — длительность элемента плана, у добавленного/заменённого — длительность на момент появления. Нужна для подписи «было → стало» и сравнения. |
| `removed` | Признак «плановое дело убрано в „Сегодня“». Размещение остаётся в массиве, скрывается с сетки и из «Нераспределённых», при завершении получает `skipped`; `shifted`/`durationChanged` снимаются. |
| «Убрано из плана» | Блок доски с размещениями `removed: true`; у каждого есть действие «Вернуть в день». |
| Пустой день | День без плана: `planId === null`, размещений нет, в Dexie не записан. Показывается с дефолтной сеткой 08:00–22:00 и CTA «Создать день» / «Взять дело». |
| Слот | Ячейка сетки дня размером 15 минут. `Slot.startMin` — смещение от начала дня, `Slot.label` — сырое `HH:mm`. |
| Легаси: шаблон дня (DayTemplate) | Термин модели 1.x. В 2.0.0 шаблоны стали планами; физическое имя таблицы `dayTemplates` сохранено только как хранилище планов, а поля `plannedTaskIds` и `order` мигрируют при обновлении БД (ТЗ §3.3). В активных требованиях слово «шаблон» не используется. |
| Легаси: цикл, `order`, `lastCyclicTemplateId` | Механика 1.x. В 2.0.0 удалена: план выбирается на дату. `lastCyclicTemplateId` — необязательное легаси-поле импорта, которое не читается и не пишется приложением. |

## 2. Функциональные требования

### 2.1 Управление делами (Tasks)
FR-T-1. Создание дела. Форма содержит поля:

- Название (обязательно, 1–100 символов).

- Приоритет: `low`, `medium`, `high`, `critical` (обязательно, дефолт `medium`).

- Цвет: 10 предустановленных HEX + произвольный `#RRGGBB` (обязательно, дефолт — случайный из палитры). Палитра, она же `TASK_PALETTE` в `src/models/task.ts`: `#F44336`, `#E91E63`, `#9C27B0`, `#673AB7`, `#3F51B5`, `#2196F3`, `#009688`, `#4CAF50`, `#FF9800`, `#795548`.

- Длительность: кратна 15 мин, 15–1425 мин (обязательно, дефолт 30 мин). 1425 — это `00:00–23:45`, верхняя граница суток плана (FR-D-1).
FR-T-2. Редактирование дела. Допустимо всегда. Заморожены для уже созданных размещений не только длительность, но и подпись дела: у каждого `Placement` хранится снимок `durationMin` и `taskSnapshot { title, color, priority }` на момент размещения, и правка дела их не меняет. Поэтому:
- Правка названия/приоритета/цвета и `durationMin` задачи разрешена в любой момент, в том числе когда дело стоит в активном (незавершённом) дне.
- Новые размещения берут новое значение `durationMin`; снимки существующих размещений не пересчитываются (ТЗ §6 правило 9).
- Переименование, смена цвета и приоритета тоже не обновляют уже созданные `Placement`: доска показывает подпись из снимка, live-обновления карточек по правке дела нет. Это не расхождение с библиотекой: в списке дел и в форме дело уже новое, а доска — снимок момента размещения.
- Снимок конкретного размещения меняется только осознанным действием «Заменить дело» (FR-B-7): тогда и `taskSnapshot`, и `durationMin` берутся с нового дела.
- Длительность конкретного размещения меняется отдельно, действием «Изменить длительность» (FR-B-7) — оно правит `Placement.durationMin`, а не дело.
FR-T-3. Архивация дела. Soft-delete: дело помечается `archived: true`, пропадает из списка, но остаётся в истории для статистики. В активном экземпляре дня в `skipped` переводятся только размещения со статусом `pending`. Уже отмеченные `done` не меняются. Архивация и перевод размещений не одна транзакция: если emitter не дошёл, `initialize` при следующем открытии ещё раз переводит pending-размещения архивных дел активного дня в `skipped`. Вернуть дело из архива можно (`unarchiveTask`). На доску и в план архивное дело поставить нельзя (`placeTask` / `placeTaskInPlan` / `replacePlacement` → `CONSTRAINT_VIOLATION`); в уже сохранённом плане такая ссылка остаётся с плашкой «в архиве» и пропускается при материализации (FR-D-7).
FR-T-4. Список дел. Отображается на отдельной странице. Поддерживается:

- Сортировка: по названию (`localeCompare`), приоритету, дате создания, длительности. Приоритет — ранг `low < medium < high < critical`, не алфавит подписи.

- Фильтр: по приоритету, по цвету, «Показать архивные» (`showArchived`). Выключен (дефолт) — в списке только неархивные. Включён — неархивные и архивные в одном списке, архив не подменяет живые дела. «Удалить» (FR-T-6) видно только у строк с `archived: true`. Уникальность названия в MVP не требуется.

- Поиск по названию: подстрока после `trim`, без учёта регистра.

- Мини-сводка на карточке и в таблице: страница читает `statsStore` за период «всё время». `useTasksStore` статистику не импортирует. Нет строки в `perTask` — подпись «не размещалось», не «—» и не 0 %. Строка есть — «выполнено / пропущено» и рейт; «—» только если рейт `null` при `placed > 0` (FR-S-2).

- Быстрый drag-and-drop дела прямо на доску дня: на широком экране (с 1024 px) доска и панель дел `TaskDragPanel` видны одновременно; на узком экране перенос дела на доску недоступен, а перемещение размещения идёт через меню «Переместить в слот…».
FR-T-5. Дублирование дела — кнопка «Дублировать» создаёт копию с названием «<Название>» + суффикс из i18n `tasks.copySuffix` (ru: ` (копия)`, en: ` (copy)`). Суффикс не зашит в код по-русски: обрезка считается от уже переведённой строки, чтобы итог не превышал 100 символов из FR-T-1: `suffix = t('tasks.copySuffix')`, `base = title.slice(0, 100 - suffix.length).trimEnd()`. Дубликат неархивный, в том же приоритете, цвете и длительности. Создание дела снэкбаром не отменяется: hard delete неархивного запрещён (FR-T-6), отдельного undo-create нет.
FR-T-6. Удаление дела (hard delete). Безвозвратное удаление разрешено только для архивного дела (FR-T-3) и только с подтверждением в UI. Для неархивного дела действие в меню скрыто, а action возвращает `CONSTRAINT_VIOLATION`. История не теряется: статистика и история размещений берут подпись из `Placement.taskSnapshot`, поэтому удаление дела не ломает экран статистики. В той же транзакции, что и удаление строки `tasks`, ссылка вычищается из `plannedPlacements` всех планов. Отмены у этого действия нет: снэкбар «Восстановить» относится к архивации, а не к удалению.

### 2.2 Управление планами дней
Раздел «Дни» хранит `DayPlan` — единую сущность для конкретного дня, повторяющегося дня и заготовки «без даты». Режим вычисляется функцией `planMode` (FR-D-2); отдельной таблицы пресетов или второй сущности дня нет.

FR-D-1. Создание плана дня. Форма `DayPlanForm` содержит:

- Название (обязательно, 1–50 символов).

- Режим: «Один день», «По дням недели», «По числам месяца», «Без даты (заготовка)». Первые три задают `oneoff`/`recurring`, четвёртый — `template` (FR-D-2).

- Для режима «Один день» — дата `YYYY-MM-DD` (по умолчанию сегодня). Дата должна существовать: `2025-02-30` даёт `INVALID_DATE`, а не тихое приведение к 2 марта.

- Время начала и конца (дефолт 08:00–22:00). Формат строго `HH:mm`: часы 00–23, минуты 00, 15, 30 или 45, обе границы внутри `00:00–23:45`. Конец позже начала, длина от 1 ч до 23 ч 45 мин (60–1425 мин). Строка не из этого формата (`abc`, `99:99`, `24:00`, `08:07`) — `INVALID_TIME`. Акцентный цвет — `#RRGGBB`, иначе `INVALID_COLOR`.

- Шаг сетки: 15 мин (жёстко в MVP).

- Правило повторения для режима `recurring`: дни недели (0 = Пн … 6 = Вс, мультивыбор) или числа месяца (1–31, мультивыбор). Правило нормализуется при сохранении (`repeat.normalizeRule`): поля, не относящиеся к выбранному `type`, отбрасываются, значения дедуплицируются и сортируются. То есть `{ type: 'weekdays', weekdays: [0], monthdays: [1] }` сохраняется как `{ type: 'weekdays', weekdays: [0] }`. Значения вне диапазона — `INVALID_RULE`, пустой после нормализации набор — `EMPTY_RULE`.

Создание может взять за основу другой план (`basedOnPlanId`): имя, акцент, время и элементы плана копируются в новый конкретный день, у элементов появляются новые `id`. Так «пресет» выражается без отдельной сущности (FR-D-10). Список дел ведётся не в форме, а на странице плана `/days/:id` (FR-D-7).

FR-D-2. Режим плана. Режим не хранится отдельным полем и вычисляется функцией `planMode(plan)` из `src/models/day.ts`:

- `recurring`, если `repeatRule.type !== 'none'`;
- `template`, если правило `none` и `date === null`;
- `oneoff`, если правило `none` и дата задана.

Форма предлагает четыре варианта, потому что `recurring` делится на два типа правила. Переключение режима очищает неприменимые поля: у `recurring` и `template` `date` всегда `null`, у `oneoff` правило всегда `none`. Один и тот же план не может быть одновременно конкретным днём и повторяющимся.

FR-D-3. Редактирование плана. Правка доступна на странице `/days/:id` (кнопка «Настройки дня» открывает `DayPlanForm`) и меняет сам план, а не историю:

- Изменение имени и акцентного цвета видно сразу, в том числе в шапке открытого дня: живой план читается из стора, снимка имени в экземпляре нет.
- Изменение правила повторения не пересчитывает завершённые экземпляры. Открытый факт, если он открыт по этому плану, синхронизируется с новой плановой основой (FR-D-11).
- Изменение времени начала сдвигает `startMin` плановых элементов так, чтобы абсолютное время сохранялось. Элемент, который после сдвига не помещается в новый диапазон, получает `startMin: null` («Нераспределённые»). Уже открытый факт обрабатывается тем же правилом.
- Правка сетки плана (добавление, перенос, длительность, замена, удаление элемента) действует на будущие дни и на текущий факт, если он открыт по плану. Правка плана никогда не выполняется со стороны «Сегодня»: там меняется только факт (FR-B-8).
- Завершённый экземпляр не переписывается; после удаления плана он показывает «План дня удалён» (FR-D-4).

FR-D-4. Удаление плана. Если на план ссылается хотя бы один незавершённый (`active`) экземпляр — запретить удаление и предложить сначала завершить день (`CONSTRAINT_VIOLATION`, сообщение `days.deletePlanBlocked`). Отдельного пользовательского «сброса» дня в MVP нет. Завершённые экземпляры удалению не мешают, но остаются в истории со своим `planId`: снимка плана в `DayInstance` нет, поэтому после удаления плана экран дня и истории показывает заглушку «План дня удалён» (i18n `day.planDeleted`), а не имя удалённого плана. Статистика не страдает — она строится на `Placement.taskSnapshot` (FR-S-1). Снимок плана в модель не добавляем: в MVP имя плана в истории не требуется (ТЗ §6 правило 7). Удаление заготовки «без даты» и плана без активных экземпляров ограничений не имеет.

FR-D-5. Запрет дублей дат и пересечений правил. При сохранении проверяется:

- Конкретная дата уникальна: второй план `oneoff` на ту же дату отклоняется с `DATE_TAKEN` (и `VALIDATION_ERROR`), а уникальный индекс `&date` в Dexie закрывает гонку. План на дату, где уже есть завершённый экземпляр, тоже не создаётся (FR-D-8).
- Для `weekdays` пересечение множеств дней недели с другим повторяющимся планом запрещено (`OVERLAP_WEEKDAYS`, `CONFLICT`).
- Для `monthdays` пересечение множеств чисел месяца запрещено (`OVERLAP_MONTHDAYS`, `CONFLICT`).
- Пересечения `weekdays` и `monthdays` между собой допустимы: при выборе дня числа месяца имеют приоритет (FR-C-1).
- Конкретный день на дату перекрывает повторяющийся план — это не конфликт, а штатное перекрытие (FR-D-9).

Ошибка пересечения возвращает `CONFLICT` с `details.conflictingPlanIds`; `DaysPage` показывает баннер и диалог с перечнем конфликтующих планов. Импорт семантику не проверяет (FR-SET-5): если в файле правила всё же пересеклись, `resolvePlanForDate` выбирает первый по `createdAt`, затем по `id`.

FR-D-6. Пустой день. Если на дату ни один план не подходит — рендерится день без плана: сетка по дефолту 08:00–22:00, `planId === null`. Пока день виртуальный (размещений нет и в Dexie его нет), по центру CTA «Создать день» и «Взять дело из списка». «Создать день» ведёт на `/days?create=YYYY-MM-DD` и открывает форму нового плана на эту дату; «Взять дело» — на `/tasks`. После создания плана на дату виртуальный день заменяется днём по плану (штатная синхронизация `useCycleStore`), второй экземпляр не создаётся. Два признака не смешивать:

- `isPlanless` — плана у дня нет вовсе (`currentPlan === null`, `planId === null`). В шапке вместо имени плана — «Без плана» (i18n `day.noPlan`). Это и виртуальный пустой день, и день, в который добавили дела без плана.
- `isPlanMissing` — у экземпляра был `planId`, но план удалён или не найден. Тогда в шапке «План дня удалён» (i18n `day.planDeleted`), а не «Без плана».

Пустое состояние доски (CTA вместо дел) — только `isVirtualInstance`: дня нет в Dexie, `placements` пуст. После первого `placeTask` CTA гаснет, остаётся сетка с делами и подписью «Без плана». Материализация и замена виртуального дня:

- Признак «пустой день ещё не в БД» — id экземпляра не записан в `cycleState.activeInstanceId`. Пока день виртуален, `activeInstanceId === null`.
- Первое размещение (`placeTask`) или завершение дня (`completeDay`) сохраняет экземпляр в Dexie под уже выданным `id` и записывает активный id в `cycleState`.
- Перезагрузка ничего не теряет: размещений в виртуальном дне нет, а сам день детерминированно пересоздаётся `resolveCurrentDay` на ту же дату.
- Если для даты виртуального дня позже появляется подходящий план, `useCycleStore` вызывает `resolveCurrentDay({ force: true })`, и пустой день заменяется днём по плану. `force` пересчитывает только виртуальный день: сохранённый экземпляр с размещениями так не пересоздаётся.
- Если из уже записанного дня убрали все размещения, экземпляр остаётся в Dexie и CTA не возвращается. «Создать день» есть только у виртуального дня.
- Пустой день не попадает в историю, пока его не завершили; при смене даты диалог завершения для него не показывается (отмечать нечего), а новый день просто разрешается на новую дату (ТЗ §2.9). Завершение пустого дня — единственный случай, когда в истории появляется экземпляр без размещений.

FR-D-7. Дела плана (`plannedPlacements`). План хранит упорядоченный массив элементов `{ id, taskId, startMin, durationMin }`. Правила:

- **Редактор.** Список живёт на странице `/days/:id`: дела перетаскиваются из панели `TaskDragPanel` на 15-минутную сетку или добавляются через `PlanTaskPicker` (поиск и чекбоксы). Добавление из picker ставит элемент без времени (`startMin: null`, «Нераспределённые»); drop на слот задаёт `startMin` как смещение от `timeStart`. Одно и то же дело можно поставить в план несколько раз: у каждого элемента свой `id`. Повторяющийся `id` при нормализации заменяется новым.
- **Правка элемента.** «Изменить длительность» правит `durationMin` элемента (15–1425, кратно 15). Если новая длительность не помещается в диапазон плана, `startMin` становится `null`. «Заменить дело» меняет `taskId` и `durationMin`; «Убрать из дня» удаляет элемент из плана. «Переместить в слот…» и перенос pointer events меняют `startMin`.
- **Сохранение.** Каждый `taskId` должен существовать: отсутствующая ссылка — `TASK_NOT_FOUND` / `VALIDATION_ERROR`, и план не записывается. Архивное дело — не ошибка: ссылка остаётся в плане с плашкой «в архиве», но при материализации пропускается.
- **Нормализация.** `normalizePlannedPlacements` отбрасывает пустые `taskId`, чинит невалидную длительность до 30 мин, невалидный или не помещающийся `startMin` уводит в `null`, устраняет совпадения `id`.
- **Материализация.** При создании экземпляра дня (`resolveCurrentDay`, сдвиг и авто-сдвиг в `completeDay`) каждый доступный элемент превращается в обычный `Placement` с `plannedId`, `unplanned: false`, `shifted: false`, `durationChanged: false`, `plannedDurationMin` из элемента, `removed: false`, `status: 'pending'`, `durationMin` из элемента и `taskSnapshot` из дела на момент открытия. `startMin` сохраняется, если помещается в диапазон; иначе `null`. Архивные и отсутствующие дела пропускаются.
- **Один раз.** Заготовки создаются только при создании экземпляра. Перезагрузка, повторный `initialize`, `resolveCurrentDay` на существующем дне и правка плана уже открытый день не дублируют (FR-D-3, FR-D-11). Замена виртуального дня через `resolveCurrentDay({ force: true })` — создание экземпляра, поэтому заготовки появляются и там.
- **Жизненный цикл дел.** Архивация дела план не чистит: после возврата из архива ссылка снова участвует в следующих днях (FR-T-3). Безвозвратное удаление архивного дела вычищает ссылку из всех планов в той же транзакции, что и удаление дела (FR-T-6).
- **Статистика.** Размещения плана — обычные размещения: в завершённом дне неотмеченные становятся `skipped` (FR-E-2) и учитываются в `placed`/`skipped`/рейтинге (FR-S-1); отклонения от плана дополнительно считаются внеплановыми (FR-S-5).
- **Импорт/экспорт.** В экспорте версии `2.0` план содержит `plannedPlacements`. Файл версии `1.0` без этого поля импортируется: `plannedTaskIds` превращаются в элементы без времени, `durationMin` берётся из дела (FR-SET-5).

FR-D-8. План на конкретную дату. Конкретный день создаётся с `date: 'YYYY-MM-DD'` и правилом `none`; дата обязательна и должна существовать. Дата уникальна: на одну дату — не больше одного плана. На дату, где уже есть завершённый экземпляр, новый план не создаётся (`DATE_TAKEN`): история дня не переписывается. Конкретный день не открывается в другие даты.

FR-D-9. Повторяющийся день. Один общий план на правило: `repeatRule` типа `weekdays` или `monthdays`, `date: null`. Правка такого плана влияет на все будущие даты и на текущий «Сегодня», если он открыт по этому плану. Правила одного типа не пересекаются (FR-D-5); конкретный день на дату перекрывает повторяющийся план. Второй повторяющийся план с тем же набором дат не создаётся; частичное пересечение тоже запрещено. Повторяющийся план не является копией по датам и не создаёт per-date сущностей.

FR-D-10. Заготовка «Без даты». План с `date: null` и правилом `none`. В «Сегодня» не открывается и в выборе на дату не участвует (FR-C-1). Используется как основа: карточка в секции «Без даты» предлагает «Создать день на дату», и `basedOnPlanId` копирует имя, акцент, время и элементы плана в новый конкретный день. Заготовка может получить дату или правило при правке и тогда перестаёт быть заготовкой (FR-D-2). Отдельных пресетов в модели нет.

FR-D-11. Сетка и синхронизация плана. Дела плана расставляются по 15-минутной сетке; не помещающиеся уходят в «Нераспределённые» (`startMin: null`). Правка плана влияет на все будущие даты и на текущий факт, если он открыт по этому плану. Синхронизацию выполняет `reconcileInstanceWithPlan` по правилам:

- неизменённые плановые размещения получают новое дело, время, длительность и снимок из плана;
- отклонения (`unplanned`, `shifted`, `durationChanged`) и `removed`-позиции сохраняются как факт; у планового дела с совпадающим `taskId` базовая длительность `plannedDurationMin` синхронизируется с планом, а признаки пересчитываются — если план догнал факт, отметка снимается;
- новые элементы плана добавляются в факт;
- элемент, удалённый из плана, исчезает из факта, только если он оставался обычным `pending`; уже отмеченный (`done`/`skipped`) или изменённый в «Сегодня» остаётся фактом с `plannedId: null` и `unplanned: true` (перенос сбрасывается, изменение длительности сохраняется по `plannedDurationMin`);
- при смене начала дня фактические `startMin` пересчитываются так, чтобы абсолютное время сохранялось; не помещающееся уходит в `null`;
- статусы размещений (`pending`/`done`/`skipped`) не сбрасываются.

Правка плана не меняет уже завершённые экземпляры. Внеплановые правки в «Сегодня» не меняют план (FR-B-8).

FR-D-12. Ограничения правки плана. Смена даты, смена режима (`oneoff` ↔ `recurring` ↔ `template`) и удаление плана запрещены, пока существует активный экземпляр, открытый по этому плану (`CONSTRAINT_VIOLATION`, `days.dateLocked` / `days.deletePlanBlocked`). Сначала день нужно завершить. Правка имени, акцента, времени и правила без смены режима разрешена; открытый факт синхронизируется по FR-D-11. Завершённые экземпляры истории не переписываются: удаление плана оставляет их с заглушкой «План дня удалён», а статистика опирается на `taskSnapshot`.

### 2.3 Выбор плана на дату и сдвиги
Циклический порядок 1.x (`order`, `lastCyclicTemplateId`) в 2.0.0 не используется: план на дату выбирается календарным правилом. Поля цикла остаются только в чтении старых файлов (ТЗ §3.3) и не двигаются ни завершением дня, ни сдвигом.

FR-C-1. Разрешение дня на дату. `repeat.resolvePlanForDate(date, plans)` возвращает план или `null`:

- Ищется план `oneoff` с `date`, равной запрошенной. Точная дата имеет высший приоритет.
- Иначе — повторяющийся план `monthdays`, чьё число месяца покрывает дату.
- Иначе — повторяющийся план `weekdays`, чей день недели покрывает дату (`weekday0 = (getDay() + 6) % 7`, 0 = Пн).
- Иначе — `null` (пустой день, FR-D-6).

Заготовки `template` (`date === null`, правило `none`) в выборе не участвуют. Числа 29–31, которых нет в текущем месяце, не совпадают ни с одним `monthday`; день проваливается в `weekdays`, затем в пустой день. Отдельного «пустого» исхода только из-за короткого месяца нет. Если после импорта правила всё же пересеклись, побеждает первый план по `createdAt`, затем по `id`; это детерминированный запасной порядок, а не поощряемая конфигурация (FR-D-5).

FR-C-3. Ручной сдвиг дня. Кнопка «Следующий день» с иконкой стрелки доступна, только пока текущий экземпляр в статусе `active` и `CycleStateDto.manualShiftDate` не равен сегодняшней локальной дате (`canShiftNext`). Повторный ручной сдвиг в те же сутки запрещён (правило 12) и возвращает `SHIFT_ALREADY_DONE_TODAY`; попытка сдвинуть завершённый день — `DAY_NOT_ACTIVE`. Сценарий один и тот же в ТЗ, контрактах и коде:

- Нажатие ставит сессионные флаги `shiftPending = true` и `shiftMode = 'early' | 'overdue'` (таблица режимов — ТЗ §2.8) и открывает диалог завершения (FR-E-1). До подтверждения БД не меняется. Закрытие диалога без подтверждения сбрасывает `shiftPending` и `shiftMode`.
- Подтверждение идёт через `completeDay`. Обычная кнопка «Завершить день» флаг не ставит. Если завершаемый день уже на сегодняшнюю дату, следующий экземпляр не создаётся. Если день просрочен (`date` < сегодня), после фиксации всё равно открывается день на сегодня — это ветка FR-E-2, не сдвиг. Оговорка относится только к обычному завершению (`shiftPending = false`); к ручному сдвигу она не применяется — там работает ветка сдвига ниже, и для просроченного дня `shiftMode = 'overdue'` даёт ровно тот же результат (новый экземпляр на сегодня), но другим путём: с записью `manualShiftDate` и запоминанием `nextInstanceId`. FR-E-2 в этом случае не вызывается, чтобы не создать второй экземпляр на сегодня.
- Если `shiftPending`: отметки фиксируются по правилам FR-E-2 (отмеченные → `done`, остальные → `skipped`, `removed` → `skipped`), затем `manualShiftDate` записывается как сегодня (`YYYY-MM-DD`, локальная дата). Пишет это поле только ручной сдвиг: обычное завершение и авто-сдвиг его не трогают. Ветка «просроченный день открывает сегодня» из FR-E-2 здесь не выполняется: новый экземпляр на сегодня создаёт сам сдвиг (`shiftMode = 'overdue'`), и второго экземпляра на ту же дату не появляется.
- Новый экземпляр материализуется сразу. Его дату считает `repeat.resolveShiftTargets` (ТЗ §2.8), а план выбирается на эту дату через `resolvePlanForDate`, а не «следующий по порядку»:
  - `shiftMode = 'early'` (сдвиг в те же сутки, экземпляр был на сегодня) — дата завтра и план на завтра: конкретный день завтрашней даты, иначе числа месяца, иначе дни недели, иначе пустой день. Шапка доски показывает дату экземпляра (завтра), а не настенные сутки. На следующие календарные сутки этот экземпляр уже не просрочен (`date` равна новому «сегодня»), второго экземпляра с тем же планом нет (сценарий 8).
  - `shiftMode = 'overdue'` (экземпляр был просрочен, его `date` < сегодня) — дата и план на сегодня по той же цепочке приоритетов. Пропущенные дни не догоняются: «Следующий день» из просроченного дня открывает сегодняшний, а не завтрашний.
  - `timeStart`/`timeEnd` — снимок плана или 08:00–22:00. Новый экземпляр становится активным (`activeInstanceId`); если плана нет, день пустой и виртуальный (`activeInstanceId = null`, FR-D-6). Завершённый остаётся в истории со своей датой.
- Отмена завершения (FR-E-3) удаляет только что созданный этим завершением экземпляр (`nextInstanceId`, если он был сохранён), возвращает `manualShiftDate` к значению до сдвига и снова делает активным завершённый экземпляр.

FR-C-4. Автопереход при смене локальной даты. Триггеры: старт (`initialize`), возврат во вкладку (`visibilitychange`), таймер на ближайшую локальную полночь. Сравнение дат берёт сегодня из `new Date()` в момент проверки, а не из минутного кэша `useNow`. Смена `currentDate` дополнительно вызывает ту же проверку, когда кэш часов догоняет полночь. Что именно происходит — зависит от состояния текущего дня (ТЗ §2.9):

- Виртуальный пустой день (в Dexie его нет): диалога нет, отметок нет — день просто разрешается заново на новую дату (`resolveCurrentDay`). В историю ничего не пишется.
- Сохранённый день в статусе `completed` и его `date` < сегодня: диалога нет, отметки не переносятся — на новую дату разрешается новый день. Так закрывается случай «день завершили вечером, а приложение осталось открытым до полуночи».
- Сохранённый день в статусе `active` и его `date` < сегодня:
  - `autoShiftAtMidnight` включён — диалог не показывается: выполняется подтверждённый сдвиг из FR-C-3 с `shiftMode = 'midnight'`. Уже `done` остаётся `done`, `pending` становится `skipped`, `skipped` не меняется, `removed` остаётся `skipped`. План нового дня выбирается на сегодня; пишется `lastAutoShiftDate = сегодня`, `manualShiftDate` не пишется. Перед сдвигом `cycleState` перечитывается из БД: если `lastAutoShiftDate` уже равен сегодня, второй авто-сдвиг в те же сутки не выполняется (защита в том числе от второй вкладки). Настройка «спрашивать» в этом режиме диалог не возвращает.
  - `autoShiftAtMidnight` выключен, `askToCompleteOnNewDay` включён — показывается диалог завершения (FR-E-1), `completionSource = 'auto'`.
  - Обе настройки выключены — диалога нет, старый день остаётся активным, пока пользователь не завершит его сам («Завершить день» или «Следующий день»).

Авто-сдвиг пишет `lastAutoShiftDate`, а не `manualShiftDate`. Поэтому он не блокирует один ручной сдвиг в те же сутки: после полуночного сдвига «Следующий день» создаёт экземпляр с датой завтра и планом на завтра (`shiftMode = 'early'`, правило 12, ТЗ §2.8). В следующую полночь `checkDayChange` видит `date >= сегодня` и второй экземпляр не создаёт (сценарий 8). Повторный авто-сдвиг в те же сутки не выполняется.

Таймер полуночи ставится на ближайшие локальные 00:00:05. Если в часовом поясе этой ночи нет местной полуночи (перевод часов вперёд), следующий запуск — `visibilitychange` или старт приложения: оба сравнивают календарную дату через `todayISO()`, а не «прошло ли 24 часа».

Отмена авто-диалога («Вернуться к дню» и «Пропустить диалог в этот раз») ставит сессионный `skippedAutoPromptDate = сегодня`. Пока флаг равен текущей дате, `visibilitychange` и таймер диалог не открывают снова. Флаг не пишется в БД и не меняет `askToCompleteOnNewDay` (ТЗ §2.7). После перезагрузки страницы флаг пуст, диалог показывается снова. Ручное открытие и сдвиг этот флаг не ставят.

FR-C-5. Состояние текущего дня. Хранится в `CycleStateDto` — синглтоне `cycleState` (см. §3.1, файл `src/models/dayInstance.ts`):

```
interface CycleStateDto {
  id: 'current';                        // ключ синглтона
  activeInstanceId: string | null;      // текущий экземпляр дня; null — дня в БД нет (в т.ч. виртуальный пустой день)
  manualShiftDate: string | null;       // дата ручного сдвига (ISO). Пишет только ручной сдвиг; блокирует повторный ручной сдвиг
  lastAutoShiftDate: string | null;     // дата авто-сдвига (ISO). Пишет только autoShiftAtMidnight; защищает от второго авто-сдвига в те же сутки
  lastCyclicTemplateId?: string | null; // ЛЕГАСИ импорта 1.0: не читается и не пишется приложением
}
```

Обязательного поля, связанного с циклическим порядком, в `CycleStateDto` нет. Необязательный `lastCyclicTemplateId` принимается только при импорте старого файла и не участвует в выборе плана, сдвиге или отмене завершения.

### 2.4 Доска дня (DayBoard)
FR-B-1. Сетка. Вертикальный таймлайн с шагом 15 минут. Крупные линии — каждые 30 мин, часовые — жирнее и с подписью `HH:00`. Слот — это старт интервала: при дне `08:00–22:00` последний слот начинается в 21:45, линия `22:00` — граница `timeEnd`, не слот, в неё дело не ставится. Скролл до текущего времени при открытии. `Slot.label` хранит сырое `HH:mm`; на экран строка выходит через `timeFormat` (FR-SET-3). Один и тот же `buildSlots` строит сетку доски «Сегодня» и редактора плана.

FR-B-2. Размещение дел.

- Drag-and-drop из панели «Дела» в слот (на широком экране) и из нераспределённой зоны на сетку.

- Перетаскивание уже размещённого дела между слотами (pointer events, `usePlacementDrag`).

- Snap к 15-минутной сетке.

- Дело занимает `durationMin / 15` слотов подряд. Одно и то же дело можно поставить в день несколько раз: каждое размещение — отдельный `Placement` со своим статусом.

- Плановое размещение приходит из плана и имеет `plannedId`; добавленное в «Сегодня» — `plannedId: null` и `unplanned: true` (FR-B-8). Перенос планового дела по времени даёт `shifted`, изменение длительности — `durationChanged`; эти признаки не делают размещение внеплановым.

- Клавиатурная альтернатива drag-and-drop (НФТ §7): у `PlacementCard` есть меню действий, пункт «Переместить в слот…» открывает список слотов текущего дня; выбор слота делает то же, что drop. Стрелки двигают фокус только внутри этого списка, саму карточку по сетке не переносят. Карточка — focusable (`tabindex`), Enter/Space открывает меню. ARIA: карточка — `role="button"`, `aria-pressed` на время перетаскивания, `aria-label` с названием и временем; список слотов — `role="list"`, слот — `role="listitem"` с `aria-label` «08:15».

FR-B-3. Пересечения. Разрешены (по дефолту), но подсвечиваются:

- Конфликтующие дела отображаются полосами с частичным наложением и иконкой предупреждения.
- В шапке дня счётчик конфликтов — это `conflicts.length`, число пар, а не число карточек. Одна пара наложений даёт баннер «1 конфликт». Баннер информационный, кнопки «Детали» нет: подсветка карточек и есть деталь.
- Интервал размещения полуоткрытый: `[startMin, startMin + durationMin)`. Касание границей (одно кончается там, где другое начинается) конфликтом не является.
- В конфликты попадают только размещения со статусом `pending` и `done`, у которых `startMin !== null` и `removed !== true`. Пропущенные (`skipped`) и убранные из плана конфликтов не создают и в счётчик не входят (`detectConflicts`).
- Настройка `showConflicts` (ТЗ §2.7) только прячет подсветку и счётчик. Выключение не запрещает наложение и не удаляет пересечения.

FR-B-4. Выход за пределы. Дело, которое не помещается в интервал экземпляра (`timeStart`–`timeEnd` снимка, не текущего плана), не отклоняется: оно попадает в нераспределённую зону. Признак — `Placement.startMin === null`. Отрицательный `startMin` не используется. Проверка «помещается / не помещается» — ветка укладки, а не ошибка валидации: валидный, но не помещающийся слот превращается в `null`. Невалидный `startMin` (не целое число, не кратно 15, отрицательный) — это именно `VALIDATION_ERROR`, данные не меняются. Границы считает `scheduler.fitInDay(startMin, durationMin, instance)` (ТЗ §4.4).

FR-B-5. Нераспределённая зона. Список размещений текущего дня с `startMin === null` и `removed !== true`. Пользователь может позже перетащить их в сетку — тогда `startMin` становится смещением от `timeStart`, кратным 15 и не меньшим 0. Не помещающееся значение снова уходит в `null`, а не отклоняется. В редакторе плана эта зона показывает элементы плана без времени.

FR-B-6. Карточка размещения. Показывает:

- Название дела из `taskSnapshot`.
- Цветную полосу слева (цвет из снимка).
- Значок приоритета.
- Время начала и конца (подпись через `timeFormat`, FR-SET-3); для размещения без слота — «без времени».
- Состояние статуса иконкой, не чекбоксом: `pending` — без отметки, `done` — ✓, `skipped` — ✗. Три статуса чекбоксом не различаются. Меняет статус только меню FR-B-7. Пока текущее локальное время попало внутрь интервала размещения, карточка дополнительно показывает ▶. Это только рисунок: `Placement.status` от него не меняется.
- Бейдж «внепланово», если у размещения нет плановой основы (`unplanned`).
- Бейдж «перенесено», если плановое дело сдвинуто по времени (`shifted`); время карточки — фактическое, подпись «план: HH:mm» показывает прежнее плановое.
- Бейдж «длительность», если длительность отличается от плановой или исходной (`durationChanged`); рядом прежняя длительность зачёркнута, затем «→» и новая. Полный текст «изменена длительность: было X, стало Y» уходит в `aria-label` карточки и в статистику. Бейдж короткий, потому что карточка узкая (НФТ ТЗ §7).
- Плашку «в архиве» в редакторе плана, если дело уже archived.

Перенос и изменение длительности независимы: у одного размещения могут быть оба бейджа. У добавленного или заменённого дела плановой основы нет, поэтому перенос не отмечается, а изменение длительности — отмечается.

FR-B-7. Быстрые действия по размещению (контекстное меню / свайп / клавиатура). Полный набор совпадает в «Сегодня» и в редакторе плана, кроме статусов: в плане статусов выполнения нет.

- Отметить выполненным / снять отметку. Если слот ещё не начался, отметка `done` показывает неблокирующее предупреждение и всё равно сохраняется.
- Отметить пропущенным / снять отметку.
- Изменить длительность (только для этого размещения: правит `Placement.durationMin` / `PlannedPlacement.durationMin`, снимок дела не трогает; доступно, пока экземпляр active). Если новый размер с текущим `startMin` не проходит `fitInDay` (в плане — `fitInDayRange`), размещение уходит в нераспределённые (`startMin = null`), а не отвергается.
- Убрать из дня. Для внепланового размещения — удалить его из факта; для планового — перевести в `removed` и показать в «Убрано из плана» (FR-B-8). Дело в библиотеке остаётся.
- Заменить дело. Снимок и длительность берутся с нового дела. Если новая длительность не влезает в текущий слот, `startMin` становится `null`.
- Переместить в слот… (клавиатурная альтернатива drag-and-drop, FR-B-2).

Действия, которых нет в коде, в требования не входят: список строится из `visiblePlacementActions`. Завершённый день доступен только для чтения — изменяющих действий нет.

FR-B-8. Отклонения в «Сегодня» и связь с планом. «Сегодня» — исполнение плана, а не его редактор. Любое отклонение сохраняется в экземпляре дня и не меняет `DayPlan`. Отклонения классифицируются тремя независимыми признаками (`services/dayPlans.ts`, `placementDeviation`):

- `unplanned` — нет плановой основы: добавлено, заменено, убрано или элемент плана исчез;
- `shifted` — то же дело и та же длительность, но другое время; если фактический `startMin === null` (дело ушло в «Нераспределённые»), переносом это не считается;
- `durationChanged` — длительность отличается от плановой (у добавленного/заменённого — от исходной).

Правила:

- Добавление дела из панели/списка создаёт размещение с `plannedId: null`, `unplanned: true`, `shifted: false`, `durationChanged: false`, `removed: false`. Базовая длительность `plannedDurationMin` равна длительности дела на момент добавления.
- Перенос планового дела меняет только `shifted` (и записывает фактическое время). Возврат на плановое время снимает `shifted`. План не меняется.
- Изменение длительности планового дела меняет только `durationChanged`; прежняя плановая длительность остаётся в `plannedDurationMin` для подписи «было → стало». Возврат длительности к плановой снимает отметку. Изменение длительности, после которого дело не влезает и уходит в `startMin: null`, остаётся только `durationChanged`, без `shifted`.
- Перенос и изменение длительности вместе дают оба признака. Правка плана обновляет плановую основу, но сохраняет фактические время/длительность отклонения и пересчитывает признаки по новому плану: если план догнал факт, отметка снимается.
- Замена дела — `unplanned`; `plannedDurationMin` становится длительностью нового дела, поэтому сама замена не считается изменением длительности. Последующее изменение длительности заменённого дела считается по этой базе.
- Удаление планового размещения не удаляет его из массива: `removed = true`, `unplanned = true`, `shifted = false`, `durationChanged = false`, `status = 'skipped'`. Размещение скрывается с сетки и из «Нераспределённых», попадает в блок «Убрано из плана» (`RemovedPlannedZone`) и не участвует в конфликтах. Кнопка «Вернуть в день» (`restorePlacement`) снимает `removed`, возвращает `pending` и плановые значения; если элемента плана уже нет, размещение остаётся внеплановым.
- Удаление внепланового размещения удаляет его из факта полностью.
- Правка плана синхронизирует только неизменённую плановую основу; отклонения (`unplanned`, `shifted`, `durationChanged`), `removed` и статусы сохраняются (FR-D-11). Если элемент плана удалён, размещение остаётся фактом: `plannedId: null`, `unplanned: true`; перенос сбрасывается (сравнивать не с чем), изменение длительности сохраняется по `plannedDurationMin`.
- В шапке доски есть кнопка «Открыть план» (`day.openPlan`), если план существует; она ведёт на `/days/:id`. Для удалённого плана кнопки нет, шапка показывает «План дня удалён».
- Счётчик `unplannedCount` в сторе считает `unplanned === true` и `removed !== true`; убранные учитываются отдельно (`removedCount`), их число сообщается в диалоге завершения, а при завершении они становятся `skipped`. Статистика считает три признака отдельно (FR-S-5).
- Легаси-размещения без новых полей нормализуются с `shifted: false`, `durationChanged: false`, `plannedDurationMin = durationMin`; прошлая история не переклассифицируется.

### 2.5 Завершение дня
FR-E-1. Диалог завершения. Триггерится:

- Вручную (кнопка «Завершить день»).
- При сдвиге на следующий день (FR-C-3).
- Автоматически при наступлении новых суток (FR-C-4).

Содержимое диалога:

- Список размещений текущего дня с чекбоксами, включая нераспределённые (`startMin === null` — без времени, подпись «без времени»). Убранные из плана (`removed`) в список не попадают: для них показывается подсказка «Убрано из плана: N — будет помечено пропущенным».
- По умолчанию: `done` — отмечены; `pending` и `skipped` — сняты.
- Пользователь может снять галочку с ранее отмеченного `done`.
- Быстрые кнопки «Отметить всё» и «Снять всё».
- Кнопка «Подтвердить». Чекбокс здесь бинарный: отмечено → `done`, снято → `skipped`. На карточке доски чекбокса нет (FR-B-6).
- Опция «Пропустить диалог в этот раз» только у авто-триггера (FR-C-4). Это разовый сессионный пропуск: `skippedAutoPromptDate`, без записи в настройки. Постоянный отказ — тумблер «Спрашивать о завершении при новом дне» на `SettingsPage` (ТЗ §2.7, поле `askToCompleteOnNewDay`). «Вернуться к дню» у авто-диалога делает тот же разовый пропуск. У ручного завершения и у сдвига «Вернуться к дню» только закрывает диалог.

FR-E-2. Логика фиксации после подтверждения:

- Отмеченные → `status = 'done'`.
- Не отмеченные (включая ранее помеченные `done`, с которых сняли галочку) → `status = 'skipped'`.
- Размещения с `removed: true` → `skipped` независимо от отметки: они уже убраны из плана в «Сегодня».
- Экземпляр получает `status = 'completed'`, `completedAt = Date.now()` и остаётся в БД для статистики.
- `activeInstanceId` не обнуляется. Если завершаемый день имеет сегодняшнюю дату, завершённый экземпляр остаётся текущим до смены календарной даты или до ручного сдвига. Повторное открытие приложения в ту же дату не вызывает `resolveCurrentDay` и не создаёт второй экземпляр. Ранний сдвиг создаёт экземпляр на завтра, а не второй экземпляр на сегодня (ТЗ §2.8).
- Если завершаемый день просрочен (`date` < сегодня) и это не сдвиг (`shiftPending` ложен): после фиксации сразу разрешается день на сегодня (`resolveCurrentDay`), без диалога и без переноса отметок. Пользователь не остаётся на экране вчерашнего дня. Сдвиг идёт своей веткой (FR-C-3) и этот вызов не дублирует. Созданный экземпляр запоминается в `nextInstanceId` — его удаляет отмена (FR-E-3). Если фиксация уже записана, а `resolveCurrentDay` вернул ошибку, `completeDay` не делает вид, что всё хорошо: диалог закрывается (повторное «Подтвердить» упрётся в `DAY_NOT_ACTIVE`), статистика всё равно пересчитывается, наружу уходит `DB_ERROR` с `details.reason = 'RESOLVE_AFTER_COMPLETE'`. UI предлагает «Открыть сегодняшний день» — повторный `resolveCurrentDay()`.
- Указателя последовательности больше нет: завершение дня не двигает `lastCyclicTemplateId`. `manualShiftDate` и `lastAutoShiftDate` при обычном завершении не изменяются.
- После успешной фиксации вызывается `statsStore.recompute()` — экран статистики, если он открыт, показывает новые числа без ручного обновления (FR-S-1, FR-S-5).

FR-E-3. Отмена завершения. Пока в памяти сессии задан `lastCompletedInstanceId`, в шапке доски видна кнопка «Отменить завершение». Тост «День завершён» (5 с) даёт ту же кнопку как ярлык и не является единственным входом: после его исчезновения кнопка в шапке остаётся до перезагрузки или до успешной отмены. После перезагрузки снапшота нет, экземпляр считается закрытым.

Отмена возвращает день в `active`, восстанавливает снимок размещений (включая `unplanned`, `shifted`, `durationChanged`, `plannedDurationMin` и `removed`), `manualShiftDate` и снова делает этот день текущим. Созданный этим завершением экземпляр удаляется всегда: его id пишется в `nextInstanceId` и для пустого (виртуального) дня, которого ещё нет в Dexie. Если пользователь успел положить в него дела, `placeTask` материализует тот же id, и отмена удаляет экземпляр вместе с этими делами. Специально не восстанавливается `lastAutoShiftDate`: авто-сдвиг в эти сутки уже произошёл, повторять его после отмены нельзя — день останется активным до ручного действия или следующей смены даты. После успешной отмены вызывается `statsStore.recompute()`; ошибка пересчёта логируется и отмену не откатывает.

FR-E-4. Отсутствие переноса. В MVP невыполненные дела не переносятся на следующий день. Пользователь переносит их вручную из списка дел или добавляет в план будущего дня.

### 2.6 Статистика
FR-S-1. Накопительные счётчики по каждому делу:

- `placed` — сколько раз размещалось (включая убранные из плана, внеплановые, перенесённые и с изменённой длительностью);
- `done` — выполнено;
- `skipped` — пропущено;
- `unplanned` — сколько размещений было внеплановыми: добавлено, заменено, убрано в «Сегодня» или элемент плана исчез;
- `shifted` — сколько плановых размещений перенесли по времени в «Сегодня» (дело и длительность те же);
- `durationChanged` — сколько размещений получили длительность, отличную от плановой (у добавленного/заменённого — от исходной);
- `rate = done / (done + skipped)`; `null`, если знаменатель 0;
- `pending` остаётся в типе `TaskStats`, но при выборке только завершённых экземпляров всегда 0.

`unplanned`, `shifted` и `durationChanged` — независимые подмножества `placed`, а не отдельные строки. Перенос и изменение длительности в `unplanned` не входят; они могут встретиться у одного размещения вместе. У добавленного или заменённого дела изменение длительности дополнительно считается `durationChanged`.

Подписи: `placed` — «размещено», `done` — «выполнено», `skipped` — «пропущено», `unplanned` — «внеплановых», `shifted` — «перенесено», `durationChanged` — «изменена длительность», `rate` — «рейт».

FR-S-2. Экран статистики. Таблица дел, у которых есть хотя бы одно размещение в завершённых экземплярах выбранного периода. Дело без такой истории в таблицу не попадает: строки «0 размещено / 0 выполнено / 0 пропущено» не существует ни для никогда не размещённого дела, ни для дела, размещавшегося только вне периода (нулевой рейт «—» поэтому тоже относится только к делам с размещениями). Строка с рейтом 0 % — это дело, у которого в периоде `placed > 0` и `done = 0` (все размещения пропущены). Несколько завершённых экземпляров на одну календарную дату (импорт без проверки семантики; индекса уникальности `date` у `dayInstances` нет) считаются все: за этот день в счётчиках может быть больше одного размещения одного дела. Ранний сдвиг второй экземпляр на сегодня не создаёт (ТЗ §2.8). Подпись `title`/`color`/`priority` берётся из снимка с наибольшей датой экземпляра, а при равной дате — с большим `placedAt`. Итоговая сводка считается по всем делам периода. Список показывает все строки периода, с сортировкой и прокруткой, без усечения «первые N». Топ-5 и антитоп-5 в MVP нет. Колонки:

- Название, цвет, приоритет.
- Счётчики `placed` / `done` / `skipped` / `unplanned` / `shifted` / `durationChanged`.
- Прогресс-бар `rate`: `rate = done / (done + skipped)`, при 0/0 — прочерк «—».
- Сортировка по любой колонке, включая `unplanned`, `shifted` и `durationChanged`.

Сводка экрана показывает семь чисел: `placed`, `done`, `skipped`, `unplanned`, `shifted`, `durationChanged`, `rate`.

FR-S-3. Периоды. Фильтр: 7 дней / 30 дней / всё время. В MVP обязателен вариант «всё время», он же дефолт экрана. Окно 7 дней — сегодня и 6 предыдущих локальных дат, 30 дней — сегодня и 29 предыдущих.

FR-S-4. Отдельная страница дела. История размещений: день, время (или «без времени»), длительность, статус. Строки группируются по дню экземпляра: заголовок группы — подпись дня («Понедельник · 23 сентября»), поэтому день указывается один раз, а не повторяется в каждой строке. Внутри дня строки идут по времени. Время — время суток с учётом начала дня экземпляра, а не смещение от начала дня. Перенесённые строки помечены «перенесено», изменённые по длительности — «изменена длительность» (с прежней длительностью для подписи «было → стало»), внеплановые — «внепланово», убранные из плана — «убрано из плана»; отметки могут сочетаться. История читается `statsStore.loadTaskHistory`, кэшируется и сбрасывается при изменении агрегатов. Незавершённые дни в историю не входят.

FR-S-5. Статистика отклонений. `TaskStats`/`OverallStats` считают три независимых подмножества: `unplanned`, `shifted`, `durationChanged`. В таблице статистики есть колонки на каждое, в сводке — плитки, в истории дела — отметки. Любое из отклонений одновременно входит в `placed` и в свой статус (`done`/`skipped`), поэтому рейт считается по общему знаменателю; это подмножества, а не отдельные строки. Перенос и изменение длительности не считаются внеплановыми. Убранное из плана при завершении становится `skipped` и учитывается и в `skipped`, и в `unplanned`.

FR-S-6. Статистика конкретного дня. В разделе «Статистика» под разбивкой по делам есть блок «По дням»: список завершённых дней выбранного периода, новые сверху. Строка дня показывает дату, число выполненных/пропущенных и счётчики отклонений (`unplanned`, `shifted`, `durationChanged`, только при значении > 0). Клик открывает отдельную страницу дня `/stats/day/:date` (подэкран с кнопкой «назад»). Страница показывает дату дня, сводку из тех же семи чисел и список дел дня: время (или «без времени»), длительность (для `durationChanged` — прежняя зачёркнута и новая), статус и отметки отклонений; убранные из плана входят как `skipped` + `unplanned` + «убрано из плана». День — это `DayInstance.date`, а не календарная дата фактического завершения: просроченный вчерашний день остаётся вчерашним. В статистику входят только завершённые экземпляры; несколько завершённых экземпляров на одну дату суммируются, пустые дни в список не попадают. Период 7/30/всё время применяется к списку дней так же, как к «По делам»; по умолчанию — «всё время». Данные дня читает `statsStore.loadDayStats`; `instances` в результате отличает «нет завершённого дня» от «день без дел».

### 2.7 Настройки
FR-SET-1. Тема: Light / Dark / Auto (по системной).
FR-SET-2. Язык: ru (дефолт) / en (заготовка).
FR-SET-3. Формат времени: 24ч / 12ч. Применяется ко всем часовым подписям: слоты сетки, интервал на карточке, список диалога завершения, шапка дня, редактор плана. Сетка в данных по-прежнему хранит минуты; `HH:mm` в сторе — внутренний вид, на экран строка выходит через форматтер настройки. `12h` не меняет шаг 15 минут и не меняет хранение.
FR-SET-4. Экспорт данных: JSON-дамп всех сущностей. Формат — `version: '2.0'`, блоки `tasks`, `dayPlans`, `dayInstances`, `cycleState`, `settings` (контракты §5.4). В `dayPlans` выгружаются нормализованные планы с `plannedPlacements`; физическое имя таблицы `dayTemplates` в файл не проникает. После успешного экспорта обновляется `lastBackupAt`.
FR-SET-5. Импорт данных: из JSON, с подтверждением перезаписи. Поддерживаются версии `2.0` и `1.0`. Перед записью файл валидируется структурно: JSON разбирается, версия поддерживается, обязательные блоки присутствуют и совпадают с моделями по форме. Версия `1.0` читает `dayTemplates` и превращает `plannedTaskIds` в `plannedPlacements` без времени; версия `2.0` читает `dayPlans` и нормализует их. Семантика правил не проверяется: пересечение правил, длина дня и кратность длительности импорт не отклоняет. Невалидный файл → `VALIDATION_ERROR`, данные в БД и localStorage не меняются. Импорт таблиц Dexie выполняется одной транзакцией; блок `settings` пишется в localStorage после неё и в транзакцию не входит. Если Dexie уже записана, а localStorage не принял settings, `importAll` возвращает `STORAGE_ERROR` с `details.reason = 'SETTINGS_AFTER_IMPORT'`: таблицы остаются импортированными, настройки — прежними, повторный полный импорт не запускается сам. UI предлагает «Повторить запись настроек» — ту же запись блока settings без второй очистки Dexie. После успешного импорта сторы переинициализируются (полный rehydrate). Легаси-поле `lastCyclicTemplateId` при импорте отбрасывается.
FR-SET-6. Спрашивать о завершении при новом дне (`askToCompleteOnNewDay`, по умолчанию включено). Постоянный выключатель авто-диалога FR-C-4. Разовый пропуск в диалоге эту настройку не меняет.
FR-SET-7. Авто-сдвиг в 00:00 (`autoShiftAtMidnight`, по умолчанию выключено). Если включено, смена даты выполняет подтверждённый сдвиг из FR-C-3 в режиме `midnight` (план нового дня — на сегодня) без диалога и пишет `lastAutoShiftDate`, а не `manualShiftDate`. Уже выполненные размещения остаются `done` (FR-C-4). Пока выключено, сдвиг только кнопкой «Следующий день».
FR-SET-8. Показывать конфликты (`showConflicts`, по умолчанию включено). См. FR-B-3: прячет подсветку и счётчик, пересечения по-прежнему разрешены.
FR-SET-9. Первый день недели для отображения (`firstDayOfWeek`): 0 — понедельник (дефолт), 1 — воскресенье. Влияет только на порядок чипов Пн–Вс в форме плана: при 1 ряд начинается с вс. На `RepeatRule.weekdays` не влияет: там 0 всегда понедельник. На заголовок «понедельник, 23 сентября» не влияет.
FR-SET-10. Очистить все данные (`clearAll`). Кнопка в разделе «Данные» на `SettingsPage`, помечена как опасная, выполняется только после подтверждения («Удалить все дела, планы и историю? Действие необратимо»). Очищает:

- таблицы Dexie: `tasks`, `dayTemplates` (они же планы), `dayInstances`;
- синглтон `cycleState` — пересоздаётся через `ensureCycleState` со значениями по умолчанию (`activeInstanceId`, `manualShiftDate` и `lastAutoShiftDate` обнуляются);
- настройки в localStorage по всем ключам `tododay:*`;
- сессионное состояние сторов (`currentInstance`, кэш статистики, снапшоты отмены завершения).

Экспорт перед очисткой автоматически не делается, но диалог предлагает выгрузить данные, если экспорта ещё не было (`lastBackupAt === null`). После очистки выполняется та же переинициализация, что и после импорта (rehydrate), и приложение показывает пустые состояния. В коде — `settingsStore.clearAll()`.

### 2.8 Правила дат (локальная дата) — единый свод
Все даты в приложении — локальные календарные даты строкой `'YYYY-MM-DD'`. Этот раздел — единственное место, где описаны правила; FR-C-3, FR-C-4, FR-S-3 и контракты §3.4 ссылаются сюда.

Определения:

| Понятие | Правило |
| --- | --- |
| Сегодня | `todayISO()` = `format(new Date(), 'yyyy-MM-dd')` (date-fns, локальная зона). Никогда не `toISOString()` и не `new Date('YYYY-MM-DD')` |
| День недели (0 = пн) | `weekday0 = (local.getDay() + 6) % 7`, где `local = parseISODate(iso)`. `Date.getDay()` даёт 0 = воскресенье, поэтому без `+ 6` понедельник становится 1 и правило `weekdays` съезжает на сутки. `firstDayOfWeek` эту формулу не сдвигает |
| Границы периода статистики | Сравнение строк `'YYYY-MM-DD'`; `periodStartISO`: `'7d'` — сегодня и 6 предыдущих дат, `'30d'` — сегодня и 29 предыдущих, `'all'` — без границы |
| Дата экземпляра | `DayInstance.date` — локальная дата, на которую день проживается |
| Дата сдвига (`targetDate`) | Дата нового экземпляра. Для `early` — завтра (`addDaysISO(дата завершаемого, 1)`). Для `midnight` и `overdue` — сегодня |
| План на дату | `repeat.resolvePlanForDate(targetDate, plans)`: точная дата → число месяца → день недели → пустой день |
| `manualShiftDate` | Дата последнего ручного сдвига. Пишется только ручным сдвигом (`early`/`overdue`); блокирует повторный ручной сдвиг, пока равна сегодня |
| `lastAutoShiftDate` | Дата последнего авто-сдвига. Пишется только `autoShiftAtMidnight` (`midnight`); блокирует повторный авто-сдвиг в те же сутки |

Запрещено во всём проекте:

- `new Date('YYYY-MM-DD')` — парсится как UTC-полночь и на границе суток/периода даёт сдвиг на день. Для разбора ISO-даты использовать локальный конструктор `new Date(y, m - 1, d)` (helper `dates.parseISODate`); правило проверяется линтером (`no-restricted-syntax`).
- `toISOString()` для получения календарной даты — только для timestamps (`createdAt`, `completedAt`, `exportedAt`).
- Арифметика дат «вручную» через `Date.now() + 86400000` — только через `dates.addDaysISO(iso, n)`.

Режимы сдвига (передаются в `completeDay` через состояние `shiftMode`, контракты §3.1/§3.4):

| Режим | Когда | Дата завершаемого экземпляра | `targetDate` | План | Что пишется | Диалог |
| --- | --- | --- | --- | --- | --- | --- |
| `early` | Ручной сдвиг «Следующий день» в те же сутки | = сегодня | завтра | на завтра | `manualShiftDate = сегодня` | Да (FR-E-1, shift) |
| `overdue` | Ручной сдвиг, когда активный день просрочен | < сегодня | сегодня | на сегодня | `manualShiftDate = сегодня` | Да (FR-E-1, shift) |
| `midnight` | `autoShiftAtMidnight` в момент смены даты | < сегодня | сегодня | на сегодня | `lastAutoShiftDate = сегодня`; `manualShiftDate` не пишется | Нет (FR-C-4) |

Формула: для `'early'` при `instanceDate === сегодня` `targetDate = addDaysISO(instanceDate, 1)`; для `'midnight'` и `'overdue'` `targetDate = сегодня`. План всегда выбирается на `targetDate`, а не «следующий по порядку»: просроченный день поэтому не перескакивает сегодня. Реализация — чистая функция `repeat.resolveShiftTargets(instanceDate, today, mode)` (ТЗ §4.4). Инвариант: режим `'early'` допустим только при `instanceDate === today`; если состояние противоречиво, функция возвращает режим `'overdue'` (дата — сегодня) и пишет `console.warn`.

Смена даты без сдвига:

- Завершённый вчера день при смене даты не переиспользуется: на сегодня разрешается новый день (FR-C-4, FR-E-2).
- Просроченные дни не «догоняются»: сколько бы дней ни было пропущено, следующий проживаемый день — сегодняшний.

### 2.9 Жизненный цикл текущего дня
Состояния `currentInstance` и переходы. Отдельного поля «состояние» в модели нет: состояние выводится из наличия в Dexie, `InstanceStatus` и активного id.

| Состояние | В Dexie | `InstanceStatus` | Признак | Как попадаем |
| --- | --- | --- | --- | --- |
| virtual-empty (пустой день) | Нет | — (в памяти `active`) | `activeInstanceId !== currentInstance.id` (обычно null), `planId === null` | `resolveCurrentDay`, когда `resolvePlanForDate` вернул null (FR-D-6) |
| active | Да | `active` | `activeInstanceId === currentInstance.id` | `resolveCurrentDay` по плану; либо `placeTask`/`completeDay` материализовали пустой день; либо `resolveCurrentDay({ force: true })` заменил виртуальный день днём по плану |
| active после правки плана | Да | `active` | `activeInstanceId === currentInstance.id` | `reconcileInstanceWithPlan` обновил плановую основу, сохранив отклонения (FR-D-11) |
| completed | Да | `completed` | `activeInstanceId === currentInstance.id` | `completeDay` без сдвига, когда дата дня = сегодня |
| next (создан завершением) | Да или нет | `active` | новый id в `activeInstanceId` (или null, если нового плана нет) | `completeDay` со `shiftPending` (FR-C-3); либо автопереход с просроченного дня (FR-E-2) |

Переходы:

```
virtual-empty --placeTask--------> active        (экземпляр пишется в Dexie, planId = null, activeInstanceId = id)
virtual-empty --completeDay------> completed     (пустой день сохраняется в историю: FR-D-6)
virtual-empty --план появился----> active        (resolveCurrentDay({ force: true }) заменяет виртуальный день днём по плану; FR-D-6)
virtual-empty --смена даты-------> virtual-empty/active на новую дату (в историю не пишется, диалога нет)
active        --правка плана-----> active        (reconcileInstanceWithPlan: план обновлён, unplanned/removed сохранены; FR-D-11)
active        --completeDay------> completed     (дата дня = сегодня: экземпляр остаётся текущим)
active        --completeDay+shift> next          (early: date = завтра; overdue/midnight: date = сегодня; старый — completed)
active(просроч)--completeDay-----> completed + next на сегодня (без диалога и без отметок, FR-E-2)
completed     --cancelCompletion-> active        (в течение сессии, FR-E-3; next-экземпляр удаляется)
completed     --смена даты-------> active/virtual-empty на сегодня (без диалога, отметки не переносятся)
active(просроч)--смена даты------> диалог завершения или авто-сдвиг (FR-C-4) или тишина (обе настройки выключены)
```

Инварианты:

- Ранний сдвиг не кладёт второй экземпляр на сегодня: завершённый день остаётся со своей датой, новый получает завтра. Индекса уникальности `dayInstances.date` нет: импорт семантику не проверяет и может принести две записи на одну дату (FR-SET-5). `resolveCurrentDay` второй экземпляр на уже текущую дату не создаёт. Экземпляр, датированный будущим (следствие раннего сдвига), остаётся текущим и после перезапуска приложения до полуночи: `initialize` не создаёт новый экземпляр на сегодня и не теряет день, выбранный пользователем (сценарий 9 в §2.10).
- Виртуальный день всегда пуст: `placements = []`, поэтому его потеря при перезагрузке безопасна.
- Виртуальный день перестаёт быть текущим только тремя путями: его материализуют `placeTask`/`completeDay`, его заменяет `resolveCurrentDay({ force: true })` при появлении плана на эту дату, либо смена даты разрешает день заново. Молчаливого исчезновения без нового `currentInstance` не бывает (FR-D-6).
- Завершать можно и пустой день — это единственный случай, когда в истории появляется экземпляр без размещений.
- Удаление плана не удаляет экземпляр и его размещения: факт остаётся с `planId`, шапка показывает «План дня удалён» (FR-D-4).
- После материализации дня правка плана не подменяет `currentInstance`: синхронизация меняет только плановую основу, а `unplanned`/`removed` и статусы остаются фактом (FR-D-11).

### 2.10 Нормативные сценарии
Сценарии ниже — часть требований: тесты в контрактах §9 проверяют именно их.

1. Вчерашний день не завершён, приложение открыто сегодня, `autoShiftAtMidnight` выключен, `askToCompleteOnNewDay` включён. Показывается диалог завершения с вчерашним днём (FR-C-4). «Пропустить диалог в этот раз» ставит `skippedAutoPromptDate`: до перезагрузки диалог не возвращается, вчерашний день остаётся активным. Подтверждение переводит вчерашний день в `completed` и разрешает день на сегодня (FR-E-2). «Отменить завершение» в сессии возвращает вчерашний день и удаляет созданный сегодняшний.
2. То же, но `autoShiftAtMidnight` включён, и во вчерашнем дне часть размещений уже `done`. Диалога нет: `done` остаётся `done`, `pending` становится `skipped`, `removed` остаётся `skipped`, `manualShiftDate` не пишется, `lastAutoShiftDate = сегодня`, новый экземпляр — дата сегодня, план на сегодня. Повторный вызов `checkDayChange` в те же сутки сдвиг не повторяет. Кнопка «Следующий день» в эти сутки доступна: она создаст экземпляр с датой завтра и планом на завтра (`shiftMode = 'early'`).
3. Ручной сдвиг в тот же день, когда экземпляр уже на сегодня. Первый сдвиг: `manualShiftDate = сегодня`, новый экземпляр — дата завтра, план на завтра. Шапка показывает завтрашнюю дату. Второй сдвиг в те же календарные сутки: кнопка недоступна (`canShiftNext = false`), action возвращает `SHIFT_ALREADY_DONE_TODAY`, БД не меняется.
4. Сдвиг просроченного дня вручную (вчерашний день, пользователь нажал «Следующий день»). `shiftMode = 'overdue'`: новый экземпляр — дата сегодня, план на сегодня (не на завтра), `manualShiftDate = сегодня`.
5. Пустой день: планов нет. День показывается как пустой, в Dexie ничего нет, `activeInstanceId = null`. Добавление первого дела сохраняет экземпляр и `activeInstanceId`, `planId` остаётся `null`, размещение получает `unplanned: true`. Перезагрузка до добавления дела даёт тот же пустой день; перезагрузка после — день с делом. Если на дату создан план, синхронизация `useCycleStore` заменяет виртуальный день днём по плану (в Dexie появляется уже день по плану, а не пустой). Завершение пустого дня сохраняет экземпляр с `placements = []` в историю.
6. Пустой день и смена даты. В полночь виртуальный пустой день не показывается в диалоге и не попадает в историю: он просто разрешается на новую дату. Если после полуночи для новой даты есть план, день сразу материализуется по плану.
7. Дело удалено из архива, а его размещения остались в завершённых днях. Статистика показывает его по `taskSnapshot` размещений (FR-T-6), экран истории размещений — по тем же снимкам.
8. Ранний сдвиг и следующие сутки. В понедельник вечером «Следующий день» создаёт экземпляр с датой вторника и планом вторника; понедельничный экземпляр остаётся завершённым со своей датой. Во вторник 00:00 `checkDayChange` видит `date >= сегодня` и выходит: диалога нет, второй экземпляр с тем же планом не создаётся. То же после цепочки «полуночный авто-сдвиг, затем ранний сдвиг» из сценария 2.
9. Ранний сдвиг и перезапуск до полуночи. Понедельник вечером выполнен ранний сдвиг (сценарий 8), экземпляр датирован вторником. Если приложение перезапустить в те же сутки до 00:00, текущим остаётся вторничный экземпляр: `initialize` видит `date >= сегодня`, `resolveCurrentDay` не вызывается, второй экземпляр на понедельник не создаётся, `activeInstanceId` не меняется. В полночь `checkDayChange` выходит по тому же условию: диалога нет, отметки не переносятся.
10. Правка плана при открытом дне. В плане на сегодня изменено время дела или добавлен новый элемент. Открытый день получает новую плановую основу: неизменённые размещения обновляются, перенесённое сохраняется с `shifted: true` и фактическим временем, изменённое по длительности — с `durationChanged: true`, убранное остаётся в «Убрано из плана», статусы не сбрасываются. Если новая плановая основа совпала с фактом, отметка переноса/длительности снимается. Завершённые дни не меняются.
11. Убрано из плана. Плановое дело убрано в «Сегодня»; оно исчезает с сетки, появляется в «Убрано из плана», в диалоге завершения его нет, но при подтверждении оно получает `skipped`. «Вернуть в день» возвращает его на плановое место; статистика после завершения учитывает его как пропущенное и внеплановое, без отметок переноса и длительности.
12. Удалённый план. План завершённого дня удалён. Экземпляр остаётся в истории, шапка дня и диалог завершения показывают «План дня удалён», статистика и история размещений не страдают. Кнопки «Открыть план» нет.
13. Перенос и длительность. Плановое дело на 09:00 перенесли на 11:00 — карточка показывает «перенесено» и «план: 09:00», счётчик `unplanned` не растёт. Затем длительность 30 → 45 мин — на карточке «длительность» и «30 мин → 45 мин», `durationChanged` = 1, `shifted` остаётся 1. Завершение дня: статистика показывает `placed 1`, `done 0/1` по отметке, `unplanned 0`, `shifted 1`, `durationChanged 1`; история дела группирует запись под днём и несёт обе отметки. План дня не изменился.
14. Статистика дня. В «Статистике» блок «По дням» показывает завершённые дни периода. Клик открывает `/stats/day/:date`: сводка дня, выполненные, пропущенные, перенесённые, с изменённой длительностью и убранные из плана. Просроченный вчерашний день, завершённый сегодня, остаётся под вчерашней датой; незавершённый сегодняшний день в статистику дня не входит.

### 3.2 Схема БД (IndexedDB через Dexie)

| Таблица | Ключ | Индексы |
| --- | --- | --- |
| `tasks` | `id` | `archived`, `priority`, `createdAt` |
| `dayTemplates` — физическое хранилище планов; в коде алиас `db.dayPlans` | `id` | `&date` (уникальная дата конкретного дня) |
| `dayInstances` | `id` | `date`, `planId`, `templateId`, `status` |
| `cycleState` | singleton (`id = 'current'`) | — |

Dexie-схема — версия 2. Физическое имя таблицы планов остаётся `dayTemplates`: в нём уже лежат строки пользователя, и копировать их ради переименования не нужно. Код работает через `db.dayPlans`; `db.dayTemplates` — легаси-алиас того же хранилища. `&date` делает дату уникальной; `null`-даты IndexedDB не индексирует, поэтому повторяющиеся планы и заготовки «без даты» не конфликтуют. Индекса `order` больше нет: порядок 1.x не используется.

Таблицы `settings` в IndexedDB нет: пользовательские настройки живут только в localStorage через `useStorage`. В экспорт/импорт они попадают чтением из localStorage, а не из Dexie.

### 3.3 Политика миграций Dexie
Схема версионирована (`db.version(n).stores({...})`). Текущая версия — 2.

- **v1 → v2.** Набор таблиц сохраняется, чтобы не копировать данные пользователя. В `dayTemplates` upgrade-функция нормализует `repeatRule`, выставляет `date` (только для правила `none`), превращает `plannedTaskIds` в `plannedPlacements` без времени (`durationMin` из дела или 30), достраивает `gridStepMin`, `name`, `accentColor`, `timeStart`, `timeEnd`, `updatedAt` и удаляет `plannedTaskIds` и `order`. В `dayInstances` добавляется индекс `planId`; старые записи без `planId` читаются как день без плана. `cycleState` не мигрирует: `ensureCycleState` достраивает отсутствующие поля.
- **Нормализация на чтении.** `normalizeDayPlan`, `normalizePlacement`, `normalizeDayInstance` и `ensureCycleState` чинят старые и импортированные записи: отсутствующие `plannedId`/`unplanned`/`removed` получают безопасные дефолты, а новые `shifted`/`durationChanged` — `false`, `plannedDurationMin` — фактическую длительность (поэтому легаси-запись не получает ложную отметку). `view` не падает на неполной строке. Поэтому правка полей модели не обязана быть Dexie-миграцией.
- **Как только меняется набор таблиц или индексов**, добавляется `db.version(n + 1).stores({...}).upgrade(tx => ...)`. Индексы в новой версии перечисляются полностью (Dexie не наследует их автоматически), удаление индекса оформляется строкой без него.
- **Данные пользователя миграция не удаляет.** Upgrade-функция только дополняет/перекладывает поля. Деструктивная миграция (очистка таблицы) недопустима без подтверждения пользователя.
- **Изменение схемы** обязательно отмечается в этом ТЗ и в журнале правок; `test/services/db.spec.ts` проверяет `ensureCycleState` и устойчивость чтения старых записей, а `test/stores/settings.spec.ts` — импорт старого формата.
- **Импорт JSON** не мигрирует БД: версия формата проверяется до записи. Файл `1.0` конвертируется в планы через `migrateLegacyPlanRow`, файл `2.0` читается как есть; неподдерживаемая версия отклоняется (FR-SET-5).

### 3.4 Локальные даты в модели
Поля-даты моделей (`DayPlan.date`, `DayInstance.date`, `CycleStateDto.manualShiftDate`, `lastAutoShiftDate`) хранят локальную календарную дату `'YYYY-MM-DD'`. Полный свод правил — ТЗ §2.8. `DayInstance.templateId` — легаси-поле 1.x: используется только для подписи старых записей и не является ссылкой на план.

### 4.4 Сервисы (чистые функции)

Даты (`services/dates.ts`, ТЗ §2.8):

- `dates.todayISO()`: string — сегодняшняя локальная дата.
- `dates.toLocalISO(date)`: string — локальная дата из `Date` (без UTC-сдвига).
- `dates.parseISODate(iso)`: Date — локальная полночь (`new Date(y, m - 1, d)`).
- `dates.isValidISODate(value)`: boolean — форма и существование даты (`2025-02-30` → false).
- `dates.addDaysISO(iso, n)`: string — календарная арифметика.
- `dates.minutesOfDay('HH:mm')`: number — минуты от начала суток.
- `dates.parseClock('HH:mm')`: number | null — только `HH:mm` с минутами 00/15/30/45 в диапазоне `00:00–23:45`.
- `dates.formatMinutesOfDay(minutes, format)`: string — подпись 24ч/12ч (FR-SET-3).
- `dates.formatClock(hhmm, format)`: string — сырое `HH:mm` → подпись.
- `dates.buildSlots(timeStart, timeEnd)`: Slot[] — сетка 15 мин, общая для доски и плана.

Правила и выбор дня (`services/repeat.ts`):

- `repeat.resolvePlanForDate(date, plans)`: `DayPlan | null` — точная дата → число месяца → день недели → `null` (FR-C-1).
- `repeat.resolveShiftTargets(instanceDate, today, mode)`: `{ mode: ShiftMode; targetDate: string }` — ТЗ §2.8. Для `'early'` при `instanceDate === today` дата — завтра; для `'midnight'`/`'overdue'` — сегодня. Противоречивый `'early'` вырождается в `'overdue'` + `console.warn`.
- `repeat.normalizeRule(rule)`: RepeatRule — отбрасывает поля не по `type`, дедуплицирует и сортирует.
- `repeat.validateRule(rule)`: ValidationIssue[] — `EMPTY_RULE` и `INVALID_RULE`.
- `repeat.validateNoOverlap(rule, plans, excludeId?)`: ValidationIssue[] — пересечения только того же типа (FR-D-5).

Раскладка (`services/scheduler.ts`):

- `scheduler.isValidStartMin(v)`: boolean — целое, кратное 15, ≥ 0.
- `scheduler.rangeLengthMin(timeStart, timeEnd)`: number.
- `scheduler.fitInDayRange(startMin, durationMin, timeStart, timeEnd)`: boolean — для плана.
- `scheduler.fitInDay(startMin, durationMin, instance)`: boolean — границы снимка экземпляра (FR-B-4).
- `scheduler.detectConflicts(placements)`: Conflict[] — только `pending`/`done`, `startMin !== null`, `removed !== true`; полуоткрытый интервал (FR-B-3).

План и факт (`services/dayPlans.ts`):

- `normalizePlannedPlacements`, `normalizeDayPlan`, `normalizePlacement`, `normalizeDayInstance` — безопасное чтение старых записей.
- `migrateLegacyPlanRow(raw, tasksById)` — легаси-строка `dayTemplates` → `DayPlan` (только импорт/миграция).
- `materializePlan(plan, tasks, now)` — `PlannedPlacement[]` → `Placement[]` с `plannedId`, пропуском архивных/отсутствующих (FR-D-7).
- `copyPlanPlacements(plan, tasks)` — копия элементов в новый день (FR-D-10).
- `toPlanPlacementViews(plan, tasks)` — адаптер плана для сетки редактора; все размещения `pending`, без статусов выполнения.
- `reconcileInstanceWithPlan(instance, plan, tasks)` — синхронизация факта с планом, сохранение отклонений (`unplanned`/`shifted`/`durationChanged`)/`removed`/статусов (FR-D-11).
- `placementDeviation(placement, plan)` / `refreshPlacementDeviation(placement, plan)` — чистая классификация отклонений и запись признаков (FR-B-8).
- `isPlacementUnplanned(placement, plan)` — тонкая обёртка над `placementDeviation(...).unplanned` (FR-B-8).
- `plannedStartMin(placement, plan)` — плановое время для подписи «план: HH:mm».
- `planMode` — реэкспорт из модели для UI.

Статистика (`services/stats.ts`):

- `stats.aggregateStats(instances, period, today)`: `{ perTask: Map<string, TaskStats>; overall: OverallStats }` — FR-S-1/FR-S-5. `today` — аргумент, не системные часы. `unplanned`/`shifted`/`durationChanged` считаются по флагам размещений; `rate` — `done / (done + skipped)` или `null`.
- `stats.aggregateDayRollups(instances)` — сводка по датам для блока «По дням»; `stats.buildDayStats(instances, date)` — суммы и плоский список размещений дня (FR-S-6).

Прочее:

- `validators/task.ts` — проверка полей дела; `validators/day.ts` — имя, цвет, время, дата, `TASK_NOT_FOUND`, `INVALID_PLACEMENT`; `useDayPlansStore.validate` делегирует сюда.
- `services/taskDrag.ts` — MIME, запись/чтение payload переноса дела.
- `services/dataTransfer.ts` — скачивание Blob и выбор JSON-файла.
- `services/appInfo.ts` — версия и дата сборки для блока «О приложении».

### 5.3 Ключевые компоненты

- `DayGrid` — колонка времени может виртуализироваться; слой карточек размещений лежит поверх всей высоты дня и не привязан к размонтированию слота (НФТ §7). Перенос по сетке — pointer events, не vuedraggable.
- `PlacementCard` — карточка на абсолютном позиционировании с высотой, пропорциональной длительности. Ключ списка — `placement.id`, чтобы виртуальный скролл не пересоздавал карточки; состав карточки считается из снимка размещения, без создания новых объектов в разметке. Показывает статус, бейджи «внепланово», «перенесено», «длительность», подпись «план: HH:mm» и пару «прежняя → новая» для изменённой длительности (прежняя зачёркнута).
- `CompleteDayDialog` — модалка со списком размещений, чекбоксами, кнопками. Убранные из плана в список не входят, но подсказка сообщает их число; для пустого дня — состояние «нечего отмечать». `DayBoard` управляет диалогом через `cycle.completing`/`dismissCompletion`.
- `DayPlanForm` — форма плана: режимы, дата, правило `RepeatRule`, имя, акцент, время; блок `RepeatRule` скрывает поля не по `type`; копирование основы через `basedOnPlanId`.
- `DayPlanPage` — страница `/days/:id`: шапка с датой/правилом/диапазоном, кнопки «Добавить дело», «Настройки дня», «Удалить», сетка `DayGrid` + `UnallocatedZone`, `PlanTaskPicker`, `PlacementEditDialogs`, регион `aria-live`.
- `DayPlanCard` — карточка плана в списке: имя, режим/дата, диапазон, число дел, действия «Открыть», «Создать день на дату», «Удалить».
- `RemovedPlannedZone` — блок «Убрано из плана» с кнопкой «Вернуть в день»; живёт на доске «Сегодня».
- `PlacementActions` и `PlacementEditDialogs` — единый список действий FR-B-7 для кнопки «⋮», правого клика, долгого тапа, свайпа и клавиатуры; диалоги длительности, замены и выбора слота.
- `TaskDragPanel` + `usePlacementDrag` — источник переноса дела на доску/план на широком экране и pointer-перенос карточки по сетке со snap к 15 минутам.
- `StatsSummary` — семь плиток сводки (`placed`, `done`, `skipped`, `unplanned`, `shifted`, `durationChanged`, `rate`); используется на экране статистики, странице дела и странице дня.
- `StatsTable` / `StatsCards` — разбивка по делам с новыми колонками/счётчиками и сортировкой по ним.
- `DayStatsList` — список дел конкретного дня: время, длительность (прежняя → новая), статус и отметки отклонений; `DayStatsPage` — страница `/stats/day/:date`.

## 6. Бизнес-правила и краевые случаи

| # | Кейс | Поведение |
| --- | --- | --- |
| 1 | Пустой день без дел | Виртуальный день: дефолтная сетка + CTA, в Dexie ничего нет, `activeInstanceId = null`, `planId = null` (FR-D-6) |
| 2 | Конфликт правил дней | Запрет сохранения: пересечение правил `weekdays`/`monthdays` и вторая запись на дату (FR-D-5) |
| 3 | Дело длиннее дня | Валидный, но не помещающийся слот → «нераспределённые» (`startMin = null`); невалидный `startMin` → `VALIDATION_ERROR` (FR-B-4) |
| 4 | Пересечения дел | Разрешены, подсветка warning. В конфликты не попадают `skipped` и `removed` (FR-B-3) |
| 5 | День не завершён к смене даты | Диалог только если авто-сдвиг выключен и «спрашивать» включено (FR-C-4). Обе настройки выключены — тишина, вчерашний день остаётся. Отмена авто-диалога гасит его до перезагрузки |
| 6 | Отмена завершения | Кнопка в шапке доски всю сессию (тост 5 с — ярлык). Возвращает день, снимки (включая `unplanned`/`shifted`/`durationChanged`/`plannedDurationMin`/`removed`), `manualShiftDate`, удаляет созданный экземпляр даже с уже положенными делами, пересчитывает статистику (FR-E-3) |
| 7 | Удаление плана с активным экземпляром | Запрет, предложение сначала завершить. Завершённые экземпляры остаются с `planId` без снимка имени: показываем «План дня удалён» (FR-D-4) |
| 7а | План создан/изменён, когда текущий день пустой | Синхронизация `useCycleStore` вызывает `resolveCurrentDay({ force: true })`: виртуальный пустой день заменяется днём по плану; материализованный день так не пересоздаётся (FR-D-6) |

## 7. Нефункциональные требования

- **Производительность.** Цель FCP — менее 1.5 c на Slow 3G. Проверяемый бюджет автотеста — 2.0 c. Фактическая оценка — ≈1.97 c: она посчитана по критической цепочке собранного `dist/pwa` (HTML + CSS в gzip) на профиле Lighthouse Slow 3G (3 × 400 мс RTT, 400 кбит/с), а не измерена браузером. Доска дня рендерит 100+ размещений без просадок: колонка подписей времени виртуализируется, слой размещений позиционируется на всю высоту дня и не размонтируется вместе с якорным слотом, ключ карточки — `placement.id`. Тяжёлые вычисления (слоты, конфликты, границы, прогресс) — в `computed`/геттерах, а не в разметке.

- **Офлайн.** 100 % функционала доступно без сети (PWA + service worker). Стартовый экран в `index.html` — inline-разметка и стиль без внешних ресурсов; `test/pwa/offline.spec.ts` проверяет критическую цепочку, предкеш и `NavigationRoute` на `index.html`.

- **Хранение.** IndexedDB, экспорт/импорт JSON (политика миграций — ТЗ §3.3). Настройки — только в localStorage, в Dexie их нет.

- **Доступность.** Контраст WCAG AA; focus-trap в модалках (`inert` на `#q-app`); клавиатурная альтернатива drag-and-drop — меню «Переместить в слот…», стрелки только внутри списка слотов (FR-B-2, FR-B-7). `PlacementCard` — `role="button"`, `aria-pressed` на время перетаскивания, `aria-label` с названием и временем. Список слотов — `role="list"`, слот — `role="listitem"` с именем «08:15». Перенос и подсветка слота объявляются через `aria-live`.

- **i18n.** ru (дефолт), en (заготовка), все строки через vue-i18n, включая настройки, диалоги, пустые состояния и ошибки по кодам `Result`. Переключение языка немедленно меняет локаль i18n. Строки удалённых режимов и полей в словарях отсутствуют; полноту проверяют `test/i18n/completeness.spec.ts` и `test/i18n/keys.spec.ts`.

- **Адаптив.** Breakpoints Quasar; mobile-first; граница 1024 px (ТЗ §5.1).

- **Тесты.** Vitest для `services/*`, сторов и компонентов; порог покрытия — ≥ 70 % на критичных модулях (`vitest.config.ts`). Обязательный минимум — сценарии ТЗ §2.10, правила дат ТЗ §2.8, отклонения FR-B-8, статистика отклонений FR-S-5 и статистика дня FR-S-6. Список файлов — контракты §9.

- **Логирование.** `console.warn` — только для ожидаемых доменных аномалий и нефатальных ошибок побочных эффектов, по закрытому списку из пяти пунктов (шесть мест вызова): (1) противоречивый режим сдвига — `early` при `instanceDate !== сегодня` (`repeat.resolveShiftTargets` вырождает его в `overdue`, ТЗ §2.8); (2) `shiftPending` без `shiftMode` в `completeDay` — режим выводится из даты завершаемого экземпляра; (3) ошибка `statsStore.recompute()` после `completeDay` / `cancelCompletion` — пункт покрывает оба вызова, фиксация дня и отмена считаются успешными, статистику можно пересчитать позже (FR-E-2, FR-E-3); (4) ошибка обработчика `onTaskArchived` при переводе pending-размещений в `skipped` — архивация уже записана в БД, добьёт её следующий `initialize` (FR-T-3); (5) ошибка синхронизации открытого дня после сохранения плана — план уже записан, день догонит следующая синхронизация/`initialize` (FR-D-11). Ни один warn из списка не подменяет `Result` основной операции: наружу отдаётся успех, если сама операция записана. Любой `console.warn` вне списка — нарушение НФТ; если список начнёт расти, warn'ы уходят в один `logger`-сервис. `console.log` / `console.error` в коде приложения не используются. Пересечение правил плана — это `CONFLICT`, не warn. Ошибки БД основной операции — `Result.err` с кодом `DB_ERROR`, а не warn.

## 11. История ревизии 2.0.0

Ревизия 2.0.0 заменила модель «шаблон + цикл + экземпляр» (1.x) на «план + факт». Подробная хронология и решения — в [журнале, приложение Ы](Журнал-правок-ToDoDay.md).

### 11.1. Модель

- `DayPlan` — единая сущность с режимами `oneoff`/`recurring`/`template`; `date` только у конкретного дня.
- `PlannedPlacement` — элемент плана с `startMin` и `durationMin`; `Placement` получил `plannedId`, `unplanned`, `removed`.
- `DayInstance.planId` связывает факт с планом; `templateId` остался легаси-полем чтения старых записей.
- `CycleStateDto` больше не двигает циклический указатель; `lastCyclicTemplateId` — необязательное легаси-поле импорта.
- Полные интерфейсы — §3.1, модель БД — §3.2.

### 11.2. Требования

- В §2.2 вошли FR-D-1…FR-D-12: режимы, дата, правило, `plannedPlacements`, сетка плана, ограничения и удаление.
- В §2.4 добавлен FR-B-8: `unplanned`, `removed`, «Убрано из плана», возврат и «Открыть план».
- В §2.6 добавлен FR-S-5: счётчики внеплановых в статистике и истории.
- Требование о циклической последовательности удалено; FR-C-1, FR-C-3, FR-C-4 и FR-C-5 переписаны без цикла. Нумерация остальных FR сохранена.

### 11.3. Выбор дня и сдвиги

- `repeat.resolvePlanForDate`: точная дата → числа месяца → дни недели → пустой день; заготовки не участвуют.
- `repeat.resolveShiftTargets`: `early` в те же сутки — завтра, `midnight`/`overdue` — сегодня; план выбирается на целевую дату.
- Пустой день остаётся виртуальным, пока не материализован размещением/завершением или не заменён днём по плану (FR-D-6).
- Подробности — §2.3 и §2.8.

### 11.4. Данные

- Dexie v2: физическая таблица `dayTemplates` хранит планы (алиас `db.dayPlans`, уникальный индекс `&date`); upgrade превращает `plannedTaskIds` в `plannedPlacements`; `dayInstances` индексируется `planId`.
- Экспорт — версия 2.0 (`tasks`, `dayPlans`, `dayInstances`, `cycleState`, `settings`); размещения несут аддитивные `shifted`, `durationChanged`, `plannedDurationMin`, поэтому версия формата не менялась. Импорт 1.0 поддерживается: старые строки `dayTemplates` превращаются в планы без времени.
