## 1. Общее описание

### 1.1 Цель
Веб-приложение ToDoDay для микроменеджмента личных дел. Пользователь формирует библиотеку дел и «шаблоны дней» (таблицы, разбитые на 15-минутные слоты), расставляет дела по слотам и проживает дни один за другим. Каждое дело — переиспользуемая сущность, по которой накапливается статистика выполнения/пропуска.

### 1.2 Область применения (MVP)

- Однопользовательское приложение.

- PWA, offline-first, работа без интернета.

- Хранение — локально (IndexedDB).

- Мобильный приоритет, адаптив до десктопа.

### 1.3 Глоссарий

| Термин | Определение |
| --- | --- |
| Дело (Task) | Переиспользуемая сущность: название, приоритет, цвет, длительность. Живёт в общем списке. |
| Шаблон дня (DayTemplate) | Конфигурация дня: имя, порядок в цикле, диапазон времени, правило повторения. |
| Правило повторения (RepeatRule) | Привязка шаблона к датам календаря: дни недели / числа месяца / без привязки. |
| Экземпляр дня (DayInstance) | Шаблон, «материализованный» на конкретную дату. Содержит размещения дел и статус. |
| Размещение (Placement) | Ссылка на Дело, поставленная в конкретный слот конкретного экземпляра дня. Имеет собственный статус. |
| Слот | Ячейка сетки дня размером 15 минут. |
| Цикл | Последовательность шаблонов дней без календарной привязки, идущая по полю order и зацикливающаяся. |

## 2. Функциональные требования

### 2.1 Управление делами (Tasks)
FR-T-1. Создание дела. Форма содержит поля:

- Название (обязательно, 1–100 символов)

- Приоритет: low | medium | high | critical (обязательно, дефолт medium)

- Цвет: палитра Quasar (10 предустановленных) + произвольный HEX (обязательно, дефолт — случайный из палитры)

- Длительность: кратно 15 мин, 15 – 1440 мин (обязательно, дефолт 30 мин)
FR-T-2. Редактирование дела. Допустимо, если дело не стоит ни в одном активном (незавершённом) экземпляре дня. Иначе — только название/приоритет/цвет; длительность заморожена для активных размещений (сохраняется снимок durationMin в Placement).
FR-T-3. Удаление дела. Soft-delete: дело помечается archived: true, пропадает из списка, но остаётся в истории для статистики. При удалении из активных размещений — они помечаются skipped.
FR-T-4. Список дел. Отображается на отдельной странице. Поддерживается:

- Сортировка: по названию, приоритету, дате создания, длительности.

- Фильтр: по приоритету, по цвету, «только не архивные».

- Поиск по названию.

- Быстрый drag-and-drop дела прямо на доску дня (если доска открыта в соседней панели на широком экране).
FR-T-5. Дублирование дела — кнопка «Дублировать» создаёт копию с названием «<Название> (копия)».

### 2.2 Управление днями (DayTemplates)
FR-D-1. Создание шаблона дня. Форма содержит:

- Название (обязательно, 1–50 символов)

- Время начала и конца (HH:mm, дефолт 08:00 – 22:00). Валидация: конец > начало, длина ≥ 1 ч

- Шаг сетки: 15 мин (жёстко в MVP)

- Правило повторения:

- Без привязки (циклический день)

- По дням недели — мультивыбор Пн–Вс

- По числам месяца — мультивыбор 1–31

- Цвет-акцент дня (для быстрого различения на списке)
FR-D-2. Порядок в цикле. Каждый шаблон имеет order. Порядок задаётся drag-and-drop на странице «Дни». Перестановка мгновенно влияет на циклическую последовательность.
FR-D-3. Редактирование шаблона. Изменения правила повторения не пересчитывают уже материализованные экземпляры (историю не переписываем).
FR-D-4. Удаление шаблона. Если на шаблон ссылается хотя бы один незавершённый экземпляр — запретить удаление, предложить сначала завершить/сбросить день.
FR-D-5. Запрет дублей дат (ответ на Q7). При сохранении правила проверяется, что ни один другой шаблон не покрывает те же даты:

- Для weekdays — пересечение множеств дней недели запрещено.

- Для monthdays — пересечение множеств чисел месяца запрещено.

- Для weekdays и monthdays между собой — пересечения допустимы, приоритет отдаётся monthdays.

- При попытке создать конфликт — показать диалог с перечнем конфликтующих шаблонов.
FR-D-6. Пустой день (ответ на Q7). Если на текущую дату ни один шаблон не подходит — рендерится «пустой день»: сетка по дефолту 08:00–22:00, без дел, с CTA «Настроить день / Взять дело из списка». Пустой день не имеет привязки к шаблону и не сохраняется в историю как экземпляр, пока в него не положат хотя бы одно дело или не завершат его.

### 2.3 Правила повторения и цикл
FR-C-1. Разрешение текущего дня. При открытии приложения:

- Определяется сегодняшняя дата.

- Ищется шаблон с monthdays, покрывающий это число → он становится активным.

- Иначе — шаблон с weekdays, покрывающий текущий день недели.

- Иначе — берётся следующий циклический шаблон (см. FR-C-2).

- Если ничего не найдено → пустой день.
FR-C-2. Циклическая последовательность. Шаблоны с правилом «без привязки» упорядочены по order. После завершения текущего циклического экземпляра следующий вычисляется как:

- Первый шаблон с order больше текущего;

- Если такого нет — шаблон с минимальным order (зацикливание).
FR-C-3. Ручной сдвиг дня (ответ на Q4). Пока текущий день не завершён, доступна кнопка «Следующий день →»:

- Действие триггерит диалог завершения дня (FR-E-1).

- После подтверждения текущий экземпляр закрывается, а следующий берётся по FR-C-1/FR-C-2 от текущей даты.

- Если сдвинутый день относится к календарному правилу другой даты — его date проставляется как дата сдвига (ручное смещение фиксируется в CycleState.manualShiftDate).
FR-C-4. Автопереход в 00:00. При открытии приложения после смены суток, если предыдущий активный экземпляр не завершён, автоматически показывается диалог завершения (FR-E-1). Отмена диалога оставляет старый день активным до следующего открытия.
FR-C-5. Состояние цикла. Хранится в CycleStateDto — синглтоне cycleState (см. §3.1, файл src/models/dayInstance.ts):

```
interface CycleStateDto {
  id: 'current';                        // ключ синглтона
  activeInstanceId: string | null;      // текущий экземпляр дня (если есть)
  lastCyclicTemplateId: string | null;  // последний завершённый циклический
  manualShiftDate: string | null;       // дата ручного сдвига (ISO)
}
```

### 2.4 Доска дня (DayBoard)
FR-B-1. Сетка. Вертикальный таймлайн с шагом 15 минут. Крупные линии — каждые 30 мин, часовые — жирнее и с подписью HH:00. Скролл до текущего времени при открытии.
FR-B-2. Размещение дел.

- Drag-and-drop из панели «Дела» в слот.

- Перетаскивание уже размещённого дела между слотами.

- Snap к 15-минутной сетке.

- Дело занимает durationMin / 15 слотов подряд.
FR-B-3. Пересечения. Разрешены (по дефолту), но подсвечиваются:

- Конфликтующие дела отображаются полосами с частичным наложением (50% opacity) и иконкой warning.

- В шапке дня счётчик конфликтов.
FR-B-4. Выход за пределы. Дело, не помещающееся до timeEnd, автоматически переносится в «нераспределённую зону» под сеткой.
FR-B-5. Нераспределённая зона. Список дел, размещённых на день, но не вставленных в слоты (например, не влезли). Пользователь может позже перетащить их в сетку.
FR-B-6. Карточка размещения. Показывает:

- Название дела

- Цветную полосу слева (цвет дела)

- Значок приоритета

- Время начала и конца

- Чекбокс «выполнено» (см. FR-E)
FR-B-7. Быстрые действия по размещению (контекстное меню / свайп):

- Отметить выполненным / снять отметку

- Отметить пропущенным / снять отметку

- Убрать из дня (вернуть в общий список)

- Заменить на другое дело

### 2.5 Завершение дня
FR-E-1. Диалог завершения. Триггерится:

- Вручную (кнопка «Завершить день»)

- При сдвиге на следующий день (FR-C-3)

- Автоматически при наступлении новых суток (FR-C-4)
Содержимое диалога:

- Список всех размещений текущего дня с чекбоксами.

- По умолчанию: уже отмеченные done — отмечены; pending — сняты.

- Пользователь может отменить ранее отмеченные дела (снять галочку).

- Кнопка «Подтвердить».

- Опция «Пропустить диалог в этот раз» (только для авто-триггера, FR-C-4). Это разовый пропуск: он не меняет настройку askToCompleteOnNewDay из §2.7. Постоянный отказ от авто-диалога — только через настройку («Больше не спрашивать» на SettingsPage, см. §7).
FR-E-2. Логика фиксации после подтверждения:

- Отмеченные → status = 'done'.

- Не отмеченные (включая ранее помеченные done, с которых сняли галочку) → status = 'skipped'.

- Экземпляр получает status = 'completed', completedAt = Date.now().

- Экземпляр записывается в историю (остаётся в БД для статистики).
FR-E-3. Отмена завершения. В течение сессии после завершения доступна кнопка «Отменить завершение» (до перезагрузки страницы). После перезагрузки — экземпляр считается закрытым.
FR-E-4. Отсутствие переноса. В MVP невыполненные дела не переносятся на следующий день. Пользователь переносит их вручную из списка дел.

### 2.6 Статистика
FR-S-1. Накопительные счётчики по каждому делу:

- totalPlaced — сколько раз размещалось

- totalDone — выполнено

- totalSkipped — пропущено

- completionRate = totalDone / (totalDone + totalSkipped)
Соответствие коду и UI: в TaskStats (контракты §4.1, services/stats.ts) те же величины названы placed / done / skipped / rate; в интерфейсе подписи — «размещено / выполнено / пропущено / рейт».
FR-S-2. Экран статистики. Таблица со всеми делами:

- Название, цвет, приоритет

- Счётчики

- Прогресс-бар completionRate

- Сортировка по любой колонке
FR-S-3. Периоды (заготовка). Фильтр по периоду: 7 дней / 30 дней / всё время. В MVP — минимум «всё время».
FR-S-4. Отдельная страница дела. История размещений: дата, время, статус.

### 2.7 Настройки
FR-SET-1. Тема: Light / Dark / Auto (по системной).
FR-SET-2. Язык: ru (дефолт) / en (заготовка).
FR-SET-3. Формат времени: 24ч / 12ч.
FR-SET-4. Экспорт данных: JSON-дамп всех сущностей.
FR-SET-5. Импорт данных: из JSON, с подтверждением перезаписи.

```
import type { TaskSnapshot } from './task';

  id: 'current';
```

### 3.2 Схема БД (IndexedDB через Dexie)

| Таблица | Ключ | Индексы |
| --- | --- | --- |
| tasks | id | archived, priority, createdAt |
| dayTemplates | id | order |
| dayInstances | id | date, templateId, status |
| cycleState | singleton (id = 'current') | — |

Таблицы settings в IndexedDB нет: пользовательские настройки живут только в localStorage через useStorage (см. §5.1 контрактов сторов и §6.5 скаффолда). В экспорт/импорт (см. §5.4 контрактов) они попадают чтением из localStorage, а не из Dexie.

## 9. Критерии приёмки
По делам:

- □  Можно создать дело с названием, приоритетом, цветом, длительностью кратной 15 мин.

- □  Дело можно редактировать, архивировать, дублировать.

- □  Валидация не пропускает пустое имя и длительность вне диапазона.
По дням:

- □  Можно создать шаблон с диапазоном, правилом и порядком в цикле.

- □  Попытка создать пересекающееся правило даёт ошибку с перечнем конфликтов.

- □  Для даты без подходящего шаблона показывается пустой день.
По циклу:

- □  Календарные шаблоны подставляются по дате.

- □  Циклические шаблоны идут по order и зацикливаются.

- □  Кнопка «Следующий день» доступна только для незавершённого дня.

- □  Автопереход в 00:00 показывает диалог завершения.
По доске:

- □  Drag-and-drop из списка в слот и между слотами работает.

- □  Сетка 15 мин, крупные линии каждые 30 мин.

- □  Пересечения подсвечиваются.

- □  Дело, не влезающее в день, уходит в «нераспределённые».
По завершению:

- □  Диалог показывает все размещения с чекбоксами.

- □  Отмена галочки помечает дело skipped.

- □  После подтверждения экземпляр получает completed.

- □  Отмена завершения доступна в сессии.
По статистике:

- □  Счётчики done/skipped/rate корректны.

- □  На странице дела видна история размещений.
НФТ:

- □  Приложение работает офлайн.

- □  Устанавливается как PWA.

- □  Есть ru/en, light/dark.

## 10. Открытые вопросы (на будущее, не блокируют MVP)

- Повторяемость дела (каждый день / по дням недели) — сейчас дела просто в списке. Логично ввести в v1.1.

- Синхронизация между устройствами — бэкенд, авторизация, конфликты слияния.

- Уведомления — Web Push при наступлении слота.

- Графики статистики — тренды, streak, распределение по приоритетам.

- Шаблоны дней из пресетов («рабочий», «выходной»).

- Гибкая гранулярность сетки — вернуть 30/60 мин как опцию.

- Автоперенос невыполненных дел — вернуть как опцию (сейчас явно нет).

# ToDoDay — Контракты сторов Pinia
Документ описывает state, getters, actions каждого стора, их типы, побочные эффекты и правила взаимодействия. Все сторы — setup-стиль (defineStore('name', () => {...})), типизированы, работают поверх Dexie (IndexedDB).

> **Важно про объём.** Этот раздел — полный целевой контракт API. Стартовый скаффолд (раздел «Стартовый скаффолд») реализует только подмножество: CRUD дел, шаблоны дней, разрешение текущего дня и завершение дня. Всё остальное помечено ниже (см. §6 скаффолда, «Заглушки сторов») и не считается «сломанным скаффолдом»: расхождение устранено явной пометкой, а не доработкой кода. Контракт — источник истины для имён и типов; при расхождении имён правится скаффолд.

## 0. Общие принципы

### 0.1 Соглашения

- Именование: use<Domain>Store, файлы — src/stores/<domain>.ts.

- Стиль: setup stores (ref, computed, function).

- Асинхронность: все actions, работающие с БД, возвращают Promise.

- Ошибки: actions не бросают исключения наружу, а возвращают Result<T>:

```
type Result<T> =
  | { ok: true; data: T }
  | { ok: false; error: AppError };
```

Исключения ловятся внутри, логируются через logger, UI показывает тост.

- Реактивность БД: используются liveQuery из Dexie для синхронизации между вкладками.

- Оптимистичные обновления: для UI-критичных операций (drag-and-drop, чекбоксы) state обновляется сразу, при ошибке — откат.

- Персистентность: настройки — в localStorage через @vueuse/core (useStorage). Остальное — в IndexedDB.

## 1. useTasksStore
Ответственность: CRUD дел, архивация, поиск и фильтрация, снимки для размещений.

### 1.1 State

```
interface TasksState {
  // Данные
  tasks: Ref<Task[]>;                        // все неархивные + архивные
  loading: Ref<boolean>;                     // идёт загрузка
  initialized: Ref<boolean>;                 // данные загружены (при активной liveQuery — ещё и подписка)

  // UI-состояние (не персистится)
  searchQuery: Ref<string>;                  // '' по умолчанию
  filterPriority: Ref<Priority | null>;      // null = все
  filterColor: Ref<string | null>;           // null = все
  showArchived: Ref<boolean>;                // false по умолчанию
  sortBy: Ref<TaskSortField>;                // 'createdAt'
  sortOrder: Ref<'asc' | 'desc'>;            // 'desc'
}

type TaskSortField = 'title' | 'priority' | 'duration' | 'createdAt';
```

```
interface TaskInput {
```

| Action | Side effect |
| --- | --- |

| updateTask | db.tasks.update(...) + updatedAt |
| archiveTask | Если дело стоит в активном DayInstance с status='pending' — useCycleStore ставит skipped (через emitter/событие) |

- Использует: только db.tasks. Обратная связь с циклом — через emitter: archiveTask публикует onTaskArchived(taskId), а useCycleStore подписывается на него и снимает активные (pending) размещения. Прямой зависимости useTasksStore → useCycleStore нет (иначе получился бы цикл импортов).

### 3.4 Детальная логика

#### initialize()

- Загрузить CycleState из БД (singleton).

- Если activeInstanceId существует — загрузить экземпляр.

- Иначе — вызвать resolveCurrentDay().

- Проверить автопереход (FR-C-4) через checkDayChange().

- Подписаться на liveQuery.

#### checkDayChange() — FR-C-4

- Вызывается из App.vue при старте, по visibilitychange и по таймеру до ближайшей полуночи.

- Если currentInstance активен и currentInstance.date < currentDate (локальная дата) и settingsStore.askToCompleteOnNewDay === true → completing = true (открыть диалог завершения, FR-E-1).

- Если настройка выключена или экземпляр уже завершён — ничего не делаем.

- Отмена диалога оставляет старый день активным до следующего открытия.

#### resolveCurrentDay() — FR-C-1

```
date = today (ISO)
1. template = daysStore.monthdayMap.get(dayOfMonth(date))
2. если нет → daysStore.weekdayMap.get(isoWeekday0(date))    // 0 = Пн
3. если нет → следующий циклический шаблон после cycleState.lastCyclicTemplateId
4. если нет → создать пустой DayInstance { templateId: null, timeStart: '08:00', timeEnd: '22:00' }
5. Материализовать DayInstance { date, templateId, timeStart, timeEnd, placements: [], status: 'active' }
6. Сохранить в БД, обновить cycleState.activeInstanceId
```

Шаги 1–3 инкапсулированы в чистую функцию repeat.resolveDayForDate(date, templates, lastCyclicTemplateId) — см. §4.4 ТЗ и юнит-тесты в §9. Стор только материализует её результат (плюс ветку «пустой день»).

#### shiftToNextDay() — FR-C-3

- Проверка: canShiftNext.

- Открыть диалог завершения (completing = true), вернуть управление UI.

- После подтверждения (completeDay) → cycleState.manualShiftDate = today.

- Вычислить следующий день:

- Если есть календарный шаблон на завтра — использовать его.

- Иначе — следующий циклический.

- Материализовать.

#### completeDay(marks)

- Для каждого Placement:

- marks[id] === 'done' → status = 'done'

- marks[id] === 'skipped' → status = 'skipped'

- отсутствует → status = 'skipped' (по умолчанию)

- 'pending' в marks не приходит (см. сигнатуру); если пришёл по ошибке — трактуется как 'skipped'

- currentInstance.status = 'completed', completedAt = now.

- Транзакция: bulk-update placements + update dayInstance + update cycleState.lastCyclicTemplateId (если template был циклическим) + очистить manualShiftDate.

- Сохранить lastCompletedInstanceId = inst.id и placementsSnapshot = структурную копию inst.placements (до мутации статусов) для cancelCompletion.

- statsStore.aggregate() — пересчёт (или liveQuery сам подтянет).

- currentInstance = null.

- completing = false (диалог завершения закрывается).

#### cancelCompletion() — FR-E-3

- Проверка: lastCompletedInstanceId в памяти сессии.

- Вернуть экземпляр в status = 'active', completedAt = null.

- Восстановить placements из placementsSnapshot (снапшот в памяти на момент completeDay).

- cycleState.activeInstanceId = restored.id.

- Восстановить cycleState.lastCyclicTemplateId из lastCyclicTemplateIdSnapshot (completeDay мог продвинуть указатель циклического шаблона).

- Сбросить lastCompletedInstanceId = null, placementsSnapshot = null и lastCyclicTemplateIdSnapshot = null (повторная отмена невозможна, новая completeDay перезапишет все три).

- Доступно только в текущей сессии (после перезагрузки lastCompletedInstanceId сбрасывается).

#### checkDayChange() — FR-C-4 (описание логики — выше, в начале §3.4)

#### startCompletion() — FR-E-1

- Ручное открытие диалога завершения кнопкой «Завершить день»: `completing = true`, если есть currentInstance.

- Альтернатива для UI — писать `cycle.completing = true` напрямую, но action предпочтительнее (одно место для guard-условий).

- Закрытие диалога без подтверждения (кнопка «Вернуться к дню») выставляет `completing = false` на стороне UI (`v-model` на диалоге); `completeDay` и `cancelCompletion` делают это сами.

#### skipPendingPlacementsForTask(taskId)

- Служебный action для побочного эффекта FR-T-3: получает taskId от emitter onTaskArchived (см. контракты §1.5/§1.6) и переводит pending-размещения этого дела в текущем активном экземпляре в skipped + persist.

- Не вызывается из UI; экспортируется, чтобы его можно было покрыть тестом.

#### dispose()

- Отписка от emitter onTaskArchived (unmount/HMR). В setup-сторе подписка ставится в initialize().

#### placeTask(taskId, startMin)

- Найти задачу в tasksStore.taskById.

- Проверка: startMin % 15 === 0, startMin >= 0.

- Проверка: startMin + durationMin <= (timeEnd - timeStart).

- Если не помещается → разместить в unallocatedPlacements (по FR-B-4).

- Создать Placement со снимком:

```
{
  id, taskId, startMin, durationMin: task.durationMin,
  status: 'pending', placedAt: now,
  taskSnapshot: { title, color, priority }
}
```

- Оптимистично добавить в currentInstance.placements, затем persist.

- conflicts пересчитается через getter.

#### movePlacement(placementId, newStartMin)
Аналогично placeTask, но без снимка (сохраняем оригинальные taskSnapshot и durationMin).

#### setPlacementStatus(id, status)
Оптимистично + persist. Если status='done' и слот в будущем — предупреждение в UI (не блокирующее).

### 4.4 Детали recompute
Выборка — только завершённые экземпляры; фильтр по периоду делается внутри aggregateStats (чистая функция), а не в запросе Dexie, чтобы логика дат не дублировалась:

```
  .where('status').equals('completed')
  .toArray();
```

- pending не учитывается в rate (для завершённых экземпляров pending всегда 0 — см. комментарий в aggregateStats).

- Дела с archived = true включаются в статистику (история не теряется).

- Дела, помеченные deleted (hard), тоже остаются в статистике — по taskSnapshot в Placement. title/color/priority берутся из снимка последнего размещения.

Сериализует всё в JSON, возвращает Blob для q-file/download. После успешного экспорта обновляется lastBackupAt (ISO-строка в localStorage).
importAll:

- Парсит, валидирует version.

- Диалог подтверждения: «Перезаписать все данные?»

- Транзакция: очистка + bulk-add (Dexie).

- Блок settings записывается в localStorage, а не в Dexie.

- Переинициализация сторов (перезагрузка страницы или reload всех).

## 7. Взаимодействие сторов — карта зависимостей

```
                   ┌───────────────────┐
                   │ useSettingsStore  │  независим; настройки — localStorage,
                   │ (тема, язык,      │  читается остальными сторами и UI
                   │  экспорт/импорт)  │
                   └─────────┬─────────┘
                             │ читают настройки
                             ▼
    ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
    │ useTasks    │──▶│ useCycle    │◀──│ useDays     │
    │ Store       │   │ Store       │   │ Store       │
    └──────┬──────┘   └──────┬──────┘   └──────┬──────┘
           │                 │                 │
           │ пишут в Dexie   │                 │
           └────────┬────────┴────────┬────────┘
                    ▼                 ▼
         ┌───────────────────────────────────────┐
         │ IndexedDB (Dexie): tasks,             │
         │ dayTemplates, dayInstances, cycleState│
         └───────────────────┬───────────────────┘
                             │ читает напрямую
                             ▼
                      ┌─────────────┐
                      │ useStats    │  ← не зависит ни от одного стора
                      │ Store       │
                      └─────────────┘

    ┌─────────────┐
    │ useUiStore  │  ← независим (тосты, диалоги, online/offline)
    └─────────────┘
```

Стрелка useTasksStore → useCycleStore на схеме — не импорт стора, а emitter onTaskArchived (archiveTask снимает pending-размещения; см. контракты §1.5/§1.6). Остальные стрелки — обычные зависимости между сторами.

Правила зависимостей:

- useTasksStore не знает о useStatsStore (и вообще о статистике).

- useCycleStore зависит от tasksStore и daysStore, а также читает настройку askToCompleteOnNewDay из settingsStore (в checkDayChange) и подписывается на emitter архивации из tasksStore.

- useStatsStore читает БД напрямую, не зависит от cycleStore/tasksStore/daysStore (чтобы не плодить циклы). На диаграмме выше к useStats ведёт стрелка от IndexedDB, а не от сторов.

- useUiStore — независим.

- useSettingsStore — независим, но его actions вызывают reload других сторов при импорте.
Порядок инициализации в App.vue (onMounted):

```
1. settingsStore (sync, из localStorage)
2. tasksStore.loadAll()
3. daysStore.loadAll()
4. cycleStore.initialize()   (внутри сам вызывает loadAll обоих сторов)
5. statsStore.recompute()   (lazy — на странице статистики; initialize в контракте §4.3 = подписка + первый recompute)
6. uiStore (listeners: online/offline, visibilitychange), cycleStore.checkDayChange()
```

```
import Dexie, { type EntityTable, type Table } from 'dexie'
import type { Task } from 'src/models/task'
import type { DayTemplate } from 'src/models/day'
import type { DayInstance, CycleStateDto } from 'src/models/dayInstance'

class ToDoDayDB extends Dexie {
  tasks!: EntityTable<Task, 'id'>
  dayTemplates!: EntityTable<DayTemplate, 'id'>
  dayInstances!: EntityTable<DayInstance, 'id'>
  cycleState!: Table<CycleStateDto, 'id'>

  constructor() {
    super('ToDoDayDB')
```

```
  const initialized = ref(false)

  const filterPriority = ref<Priority | null>(null)
  const filterColor = ref<string | null>(null)
  const showArchived = ref(false)
  const sortBy = ref<'title' | 'priority' | 'duration' | 'createdAt'>('createdAt')

  const archivedTasks = computed(() => tasks.value.filter(t => t.archived))

    let list = showArchived.value ? tasks.value : activeTasks.value
    const q = searchQuery.value.trim().toLowerCase()
    if (q) list = list.filter(t => t.title.toLowerCase().includes(q))
    if (filterPriority.value) list = list.filter(t => t.priority === filterPriority.value)
    if (filterColor.value) list = list.filter(t => t.color === filterColor.value)

    const dir = sortOrder.value === 'asc' ? 1 : -1
    return [...list].sort((a, b) => {
      switch (sortBy.value) {
        case 'title': return a.title.localeCompare(b.title) * dir
        case 'priority': {
          const rank: Record<Priority, number> = { low: 0, medium: 1, high: 2, critical: 3 }
          return (rank[a.priority] - rank[b.priority]) * dir
        }
        case 'duration': return (a.durationMin - b.durationMin) * dir
        default: return (a.createdAt - b.createdAt) * dir
      }
    })
  })

      for (const handler of archivedHandlers) {
```

```
        if (inst.templateId) {
          const tpl = useDaysStore().templateById(inst.templateId)
          if (tpl?.repeatRule.type === 'none') {
            await db.cycleState.update('current', {
              lastCyclicTemplateId: inst.templateId,
              activeInstanceId: null,
              manualShiftDate: null,
            })
          } else {
            await db.cycleState.update('current', { activeInstanceId: null })
          }
        } else {
          await db.cycleState.update('current', { activeInstanceId: null })
        }
      })
    } catch (e) {
      // откат оптимистичных изменений, чтобы память совпадала с БД
      inst.status = 'active'
      delete inst.completedAt
      inst.placements = placementsSnapshot.value?.map(p => ({ ...p })) ?? inst.placements
      lastCompletedInstanceId.value = null
      placementsSnapshot.value = null
      lastCyclicTemplateIdSnapshot.value = null
      return err('DB_ERROR', 'Не удалось завершить день', e)
    }

    if (cycleState.value) cycleState.value.activeInstanceId = null
    currentInstance.value = null
    completing.value = false          // диалог завершения закрывается
    return ok(undefined)
  }

  // FR-E-3: отмена завершения в рамках сессии
  async function cancelCompletion(): Promise<Result<void>> {
    const id = lastCompletedInstanceId.value
    const snapshot = placementsSnapshot.value
    if (!id || !snapshot) return err('NOT_FOUND', 'Нет завершённого дня для отмены')

    try {
      const inst = await db.dayInstances.get(id)
      if (!inst) return err('NOT_FOUND', 'Экземпляр дня не найден')

      inst.status = 'active'
      delete inst.completedAt
      inst.placements = snapshot.map(p => ({ ...p }))

      await db.transaction('rw', db.dayInstances, db.cycleState, async () => {
        await db.dayInstances.put(inst)
        await db.cycleState.update('current', {
          activeInstanceId: inst.id,
          // completeDay мог продвинуть указатель цикла — возвращаем прежнее значение
          lastCyclicTemplateId: lastCyclicTemplateIdSnapshot.value,
        })
      })

      currentInstance.value = inst
      if (cycleState.value) {
        cycleState.value.activeInstanceId = inst.id
        cycleState.value.lastCyclicTemplateId = lastCyclicTemplateIdSnapshot.value
      }
      lastCompletedInstanceId.value = null
      placementsSnapshot.value = null
      lastCyclicTemplateIdSnapshot.value = null
      completing.value = false
      return ok(undefined)
    } catch (e) {
      return err('DB_ERROR', 'Не удалось отменить завершение дня', e)
    }
  }

  // FR-E-1: ручное открытие диалога завершения (кнопка «Завершить день»)
  function startCompletion(): void {
    if (!currentInstance.value) return
    completing.value = true
  }

  // FR-C-4: автопереход. Вызывается из App.vue (старт, visibilitychange, таймер до полуночи)
  function checkDayChange(): void {
    const inst = currentInstance.value
    if (!inst || inst.status !== 'active') return
    if (inst.date >= currentDate.value) return
    if (!useSettingsStore().askToCompleteOnNewDay) return
    completing.value = true
  }

  // Побочный эффект архивации дела (FR-T-3): pending-размещения → skipped
  async function skipPendingPlacementsForTask(taskId: string): Promise<void> {
    const inst = currentInstance.value
    if (!inst || inst.status !== 'active') return

    const affected = inst.placements.filter(p => p.taskId === taskId && p.status === 'pending')
    if (!affected.length) return

    for (const p of affected) p.status = 'skipped'
    await db.dayInstances.put(inst)
  }

  async function shiftToNextDay(): Promise<Result<void>> {
    if (!canShiftNext.value) return err('CONFLICT', 'День уже завершён')
    completing.value = true
    return ok(undefined)
  }

  // placeTask / movePlacement / removePlacement / setPlacementStatus — заглушки
  async function placeTask(_taskId: string, _startMin: number): Promise<Result<Placement>> {

  async function removePlacement(_id: string): Promise<Result<void>> {
    return err('UNKNOWN', 'Не реализовано в скаффолде')
  }
  async function setPlacementStatus(
    _id: string,
    _status: PlacementStatus,
  ): Promise<Result<void>> {
    return err('UNKNOWN', 'Не реализовано в скаффолде')
  }

  function startDrag(taskId: string, source: 'list' | 'board') {
    draggingTaskId.value = taskId
    dragSource.value = source

  function setHoveredSlot(slotIndex: number | null) { hoveredSlot.value = slotIndex }
```

```
export type { StatsPeriod }

export const useStatsStore = defineStore('stats', () => {
  const taskStats = ref<Map<string, TaskStats>>(new Map())
  const overallStats = ref<OverallStats | null>(null)
  const period = ref<StatsPeriod>('7d')
  const loading = ref(false)
  const initialized = ref(false)

  const visibleTaskStats = computed(() =>
    Array.from(taskStats.value.values()).sort((a, b) =>
      a.title.localeCompare(b.title),
    ),
  )

  async function recompute(p?: StatsPeriod): Promise<Result<void>> {
    loading.value = true
    try {
      const target = p ?? period.value
      period.value = target
      // Только завершённые экземпляры — поэтому в агрегатах pending всегда 0 (см. services/stats.ts)
      const instances = await db.dayInstances
        .where('status').equals('completed')
        .toArray()
      const { perTask, overall } = aggregateStats(instances, target)
      taskStats.value = perTask
      overallStats.value = overall
      initialized.value = true
      return ok(undefined)
    } catch (e) {
      return err('DB_ERROR', 'Не удалось пересчитать статистику', e)
    } finally {
      loading.value = false
    }
  }

  async function loadTaskHistory(taskId: string): Promise<Result<PlacementHistoryEntry[]>> {
    try {
      const instances = await db.dayInstances
        .where('status').equals('completed')
        .toArray()
      const out: PlacementHistoryEntry[] = []
      for (const inst of instances) {
        for (const p of inst.placements) {
          if (p.taskId === taskId) {
            out.push({
              instanceId: inst.id,
              date: inst.date,
              startMin: p.startMin,
              durationMin: p.durationMin,
              status: p.status,
              completedAt: inst.completedAt,
            })
          }
        }
      }
      out.sort((a, b) => b.date.localeCompare(a.date))
      return ok(out)
    } catch (e) {
      return err('DB_ERROR', 'Не удалось загрузить историю', e)
    }
  }

  function setPeriod(p: StatsPeriod) {
    period.value = p
    void recompute(p)
  }

  return {
    taskStats, overallStats, period, loading, initialized,
    visibleTaskStats,
    recompute, loadTaskHistory, setPeriod,
  }
```

```
import type { RepeatRule, DayTemplate } from 'src/models/day'

export interface OverlapIssue {
  code: 'OVERLAP_WEEKDAYS' | 'OVERLAP_MONTHDAYS'
  templateId: string
  values: number[]
}

/** Разбор 'YYYY-MM-DD' по локальным компонентам: new Date('2025-09-23') дал бы UTC. */
function parseISODate(date: string): { year: number; month: number; day: number } {
  const [year, month, day] = date.split('-').map(Number)
  return { year, month, day }
}

/**
 * FR-C-1: выбор шаблона дня для даты 'YYYY-MM-DD'.
 * Приоритет: число месяца → день недели (0 = Пн) → следующий циклический → null (пустой день).
 * Если lastCyclicTemplateId не найден среди циклических — берём первый по order.
 */
export function resolveDayForDate(
  date: string,
  templates: DayTemplate[],
  lastCyclicTemplateId: string | null = null,
): DayTemplate | null {
  const { year, month, day } = parseISODate(date)
  const local = new Date(year, month - 1, day)
  const dayOfMonth = local.getDate()
  const weekday0 = (local.getDay() + 6) % 7

  const byMonthday = templates.find(
    t => t.repeatRule.type === 'monthdays' && t.repeatRule.monthdays?.includes(dayOfMonth),
  )
  if (byMonthday) return byMonthday

  const byWeekday = templates.find(
    t => t.repeatRule.type === 'weekdays' && t.repeatRule.weekdays?.includes(weekday0),
  )
  if (byWeekday) return byWeekday

  const cyclic = templates
    .filter(t => t.repeatRule.type === 'none')
    .sort((a, b) => a.order - b.order)
  if (!cyclic.length) return null

  const idx = lastCyclicTemplateId ? cyclic.findIndex(t => t.id === lastCyclicTemplateId) : -1
  return cyclic[(idx + 1) % cyclic.length]
}

export function validateNoOverlap(
  rule: RepeatRule,
  templates: DayTemplate[],
  excludeId?: string,
): OverlapIssue[] {
  const issues: OverlapIssue[] = []

  if (rule.type === 'weekdays' && rule.weekdays?.length) {
    for (const t of templates) {
      if (t.id === excludeId) continue
      if (t.repeatRule.type !== 'weekdays') continue
      const overlap = (t.repeatRule.weekdays ?? []).filter(w =>
        rule.weekdays!.includes(w),
      )
      if (overlap.length) {
        issues.push({ code: 'OVERLAP_WEEKDAYS', templateId: t.id, values: overlap })
      }
    }
  }

  if (rule.type === 'monthdays' && rule.monthdays?.length) {
    for (const t of templates) {
      if (t.id === excludeId) continue
      if (t.repeatRule.type !== 'monthdays') continue
      const overlap = (t.repeatRule.monthdays ?? []).filter(m =>
        rule.monthdays!.includes(m),
      )
      if (overlap.length) {
        issues.push({ code: 'OVERLAP_MONTHDAYS', templateId: t.id, values: overlap })
      }
    }
  }

  return issues
}
```

### 7.3 src/services/stats.ts

```
import type { DayInstance } from 'src/models/dayInstance'
import type { PlacementStatus, Priority } from 'src/models/enums'

export type StatsPeriod = '7d' | '30d' | 'all'

export interface TaskStats {
  taskId: string
  title: string
  color: string
  priority: Priority
  placed: number
  done: number
  skipped: number
  pending: number
  rate: number | null
}

export interface OverallStats {
  placed: number
  done: number
  skipped: number
  rate: number | null
  periodStart: string | null
  periodEnd: string
}

export interface PlacementHistoryEntry {
  instanceId: string
  date: string
  startMin: number
  durationMin: number
  status: PlacementStatus
  completedAt?: number
}

/** Локальная дата в виде 'YYYY-MM-DD' (toISOString() вернул бы UTC-дату). */
function toLocalISO(d: Date): string {
  const y = d.getFullYear()
  const m = String(d.getMonth() + 1).padStart(2, '0')
  const day = String(d.getDate()).padStart(2, '0')
  return `${y}-${m}-${day}`
}

/** Начало периода как 'YYYY-MM-DD' (локальная дата) или null для 'all'.
 *  Окно включительное: '7d' = сегодня и 6 предыдущих дней (итого 7 дат). */
function periodStartISO(p: StatsPeriod, end: Date): string | null {
  if (p === 'all') return null
  const d = new Date(end)
  d.setDate(d.getDate() - (p === '7d' ? 6 : 29))
  return toLocalISO(d)
}

/**
 * Агрегация чистой функцией: считает ровно те экземпляры, которые переданы.
 *
 * Про pending: поле pending в TaskStats остаётся, но при выборке только завершённых
 * экземпляров (status = 'completed', как это делает useStatsStore.recompute) оно
 * всегда 0 — completeDay переводит все размещения в done/skipped (FR-E-2).
 * Ненулевым pending будет только если передать сюда активные экземпляры
 * (например, для будущей «статистики текущего дня»).
 */
export function aggregateStats(
  instances: DayInstance[],
  period: StatsPeriod,
): { perTask: Map<string, TaskStats>; overall: OverallStats } {
  const end = new Date()
  const startISO = periodStartISO(period, end)
  const perTask = new Map<string, TaskStats>()
  // Дата последнего встреченного размещения по делу — для снимка title/color/priority
  const lastSeenDate = new Map<string, string>()

  let placed = 0, done = 0, skipped = 0

  for (const inst of instances) {
    // Сравниваем строки 'YYYY-MM-DD' в локальной дате: new Date('2025-09-23')
    // парсится как UTC-полночь и на границе периода даёт сдвиг на сутки.
    if (startISO && inst.date < startISO) continue
    for (const p of inst.placements) {
      placed++
      const cur = perTask.get(p.taskId) ?? {
        taskId: p.taskId,
        title: p.taskSnapshot.title,
        color: p.taskSnapshot.color,
        priority: p.taskSnapshot.priority,
        placed: 0, done: 0, skipped: 0, pending: 0, rate: null,
      }
      cur.placed++
      if (p.status === 'done') { cur.done++; done++ }
      else if (p.status === 'skipped') { cur.skipped++; skipped++ }
      else cur.pending++

      // Снимок подписи берём из последнего по дате размещения (экземпляры идут не по порядку)
      const seen = lastSeenDate.get(p.taskId)
      if (!seen || inst.date >= seen) {
        cur.title = p.taskSnapshot.title
        cur.color = p.taskSnapshot.color
        cur.priority = p.taskSnapshot.priority
        lastSeenDate.set(p.taskId, inst.date)
      }

      perTask.set(p.taskId, cur)
    }
  }

  for (const s of perTask.values()) {
    const denom = s.done + s.skipped
    s.rate = denom === 0 ? null : s.done / denom
  }

  const overallDenom = done + skipped
  return {
    perTask,
    overall: {
      placed, done, skipped,
      rate: overallDenom === 0 ? null : done / overallDenom,
      periodStart: startISO,
      periodEnd: toLocalISO(end),
    },
  }
}
```

```
import type { Placement } from 'src/models/dayInstance'
import type { Conflict } from 'src/models/cycle'

export function detectConflicts(placements: Placement[]): Conflict[] {
  const sorted = [...placements].sort((a, b) => a.startMin - b.startMin)
  const out: Conflict[] = []
  for (let i = 0; i < sorted.length; i++) {
    for (let j = i + 1; j < sorted.length; j++) {
      const a = sorted[i]
      const b = sorted[j]
      const aEnd = a.startMin + a.durationMin
      const bEnd = b.startMin + b.durationMin
      if (b.startMin < aEnd && a.startMin < bEnd) {
        out.push({
          placementIds: [a.id, b.id],
          overlapStart: Math.max(a.startMin, b.startMin),
          overlapEnd: Math.min(aEnd, bEnd),
        })
      }
    }
  }
  return out
}
```

## 10. src/App.vue

```
<template>
  <router-view />
</template>

<script setup lang="ts">
import { onMounted } from 'vue'
import { useSettingsStore } from 'src/stores/settings'
import { useUiStore } from 'src/stores/ui'
import { useCycleStore } from 'src/stores/cycle'

const settings = useSettingsStore()
const ui = useUiStore()
const cycle = useCycleStore()

onMounted(async () => {
  // Тема
  settings.setTheme(settings.theme)

  // Онлайн/офлайн
  window.addEventListener('online', () => (ui.isOnline = true))
  window.addEventListener('offline', () => (ui.isOnline = false))

  // Инициализация цикла
  await cycle.initialize()

  // FR-C-4: автопереход в 00:00. Проверяем при возврате во вкладку и по таймеру,
  // который каждый раз переставляется на ближайшую полночь.
  let midnightTimer: ReturnType<typeof setTimeout> | undefined

  function scheduleMidnightCheck() {
    if (midnightTimer) clearTimeout(midnightTimer)
    const now = new Date()
    const nextMidnight = new Date(now.getFullYear(), now.getMonth(), now.getDate() + 1, 0, 0, 5)
    midnightTimer = setTimeout(checkDay, nextMidnight.getTime() - now.getTime())
  }

  function checkDay() {
    cycle.checkDayChange()
    scheduleMidnightCheck()
  }

  document.addEventListener('visibilitychange', () => {
    if (document.visibilityState === 'visible') checkDay()
  })
  scheduleMidnightCheck()

  // Тост, если офлайн
  if (!ui.isOnline) {
    ui.notify('Приложение работает офлайн', 'info')
  }

  // Тему применил settings.setTheme() выше (он вызывает Dark.set), поэтому
  // здесь НЕ форсируем boolean: иначе ломается режим 'auto' (dark: 'auto' в quasar.config.ts).
})
</script>
```

### Осознанно оставлено как задача (не противоречие, а объём работ)

Эти пункты требуют продуктовых решений или отдельной реализации; они зафиксированы в таблице §6 скаффолда и в §11, чтобы не выглядеть «сломанным скаффолдом»:

- FR-D-6: пустой день сейчас сохраняется в Dexie сразу — нужно либо не сохранять его до первого размещения/завершения, либо переформулировать FR-D-6.
- FR-C-3: `shiftToNextDay` только открывает диалог; `manualShiftDate` не пишется, следующий день после `completeDay` не материализуется (правило 12 §6 ТЗ не проверяется).
- `scheduler.fitInDay` (FR-B-4), подписки liveQuery, `resetCurrentDay`, `replacePlacement`, `changePlacementDuration`, `dayProgress` — не реализованы.
- `unallocatedPlacements` опирается на `startMin < 0`, что не описано в модели Placement и противоречит проверке `startMin >= 0` (§4.4 ТЗ) — нужен явный признак нераспределённого размещения.
- `setLanguage` не переключает локаль i18n (нужен экспорт инстанса i18n из boot-файла); настройки `autoShiftAtMidnight`, `showConflicts`, `firstDayOfWeek` нигде не используются.
- `createTemplate` / `updateTemplate` / `deleteTemplate` / `reorder` в days.ts не обёрнуты в try/catch, хотя §0.1 контрактов требует возвращать Result.
- FR-T-2 (заморозка `durationMin` при активных размещениях) и правило 7 §6 ТЗ («запрещены дубли дат») не обеспечены кодом: уникальности дат нет ни в схеме, ни в материализации сдвинутого дня.
- Нет раздела `settings.*` в i18n, хотя страница настроек есть.
