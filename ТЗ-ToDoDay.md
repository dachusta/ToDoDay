## 1. Общее описание

### 1.1 Цель
Веб-приложение ToDoDay для микроменеджмента личных дел. Пользователь формирует библиотеку дел и «шаблоны дней» (таблицы, разбитые на 15-минутные слоты), расставляет дела по слотам и проживает дни один за другим. Каждое дело — переиспользуемая сущность, по которой накапливается статистика выполнения/пропуска.

### 1.2 Область применения (MVP)

- Однопользовательское приложение.

- PWA, offline-first, работа без интернета.

- Хранение — локально (IndexedDB).

- Мобильный приоритет, адаптив до десктопа.

### 1.3 Глоссарий

| Термин | Определение |
| --- | --- |
| Дело (Task) | Переиспользуемая сущность: название, приоритет, цвет, длительность. Живёт в общем списке. |
| Шаблон дня (DayTemplate) | Конфигурация дня: имя, порядок в цикле, диапазон времени, правило повторения. |
| Правило повторения (RepeatRule) | Привязка шаблона к датам календаря: дни недели / числа месяца / без привязки. |
| Экземпляр дня (DayInstance) | Шаблон, «материализованный» на конкретную дату. Содержит размещения дел и статус. |
| Размещение (Placement) | Ссылка на Дело, поставленная в конкретный слот конкретного экземпляра дня. Имеет собственный статус. |
| Слот | Ячейка сетки дня размером 15 минут. |
| Цикл | Последовательность шаблонов дней без календарной привязки, идущая по полю order и зацикливающаяся. |

## 2. Функциональные требования

### 2.1 Управление делами (Tasks)
FR-T-1. Создание дела. Форма содержит поля:

- Название (обязательно, 1–100 символов)

- Приоритет: low | medium | high | critical (обязательно, дефолт medium)

- Цвет: 10 предустановленных HEX + произвольный `#RRGGBB` (обязательно, дефолт — случайный из палитры). Палитра, она же `TASK_PALETTE` в `src/models/task.ts`: `#F44336`, `#E91E63`, `#9C27B0`, `#673AB7`, `#3F51B5`, `#2196F3`, `#009688`, `#4CAF50`, `#FF9800`, `#795548`.

- Длительность: кратно 15 мин, 15–1425 мин (обязательно, дефолт 30 мин). 1425 — это `00:00–23:45`, верхняя граница суток шаблона (FR-D-1).
FR-T-2. Редактирование дела. Допустимо всегда. Особое правило только для длительности: она заморожена для уже созданных размещений — у каждого Placement хранится снимок durationMin, и правка дела его не меняет. Поэтому:
- Правка названия/приоритета/цвета и durationMin задачи разрешена в любой момент, в том числе когда дело стоит в активном (незавершённом) дне.
- Новые размещения берут новое значение durationMin; снимки существующих размещений не пересчитываются (ТЗ §6 правило 9).
- Длительность конкретного размещения меняется отдельно, действием «Изменить длительность» (FR-B-7) — оно правит Placement.durationMin, а не дело.
FR-T-3. Архивация дела. Soft-delete: дело помечается archived: true, пропадает из списка, но остаётся в истории для статистики. В активном экземпляре дня в skipped переводятся только размещения со статусом pending. Уже отмеченные done не меняются. Архивация и перевод размещений не одна транзакция: если emitter не дошёл, `initialize` при следующем открытии ещё раз переводит pending-размещения архивных дел активного дня в skipped. Вернуть дело из архива можно (unarchiveTask). На доску архивное дело поставить нельзя (`placeTask` / `replacePlacement` → CONSTRAINT_VIOLATION).
FR-T-4. Список дел. Отображается на отдельной странице. Поддерживается:

- Сортировка: по названию, приоритету, дате создания, длительности.

- Фильтр: по приоритету, по цвету, «Показать архивные» (`showArchived`). Выключен (дефолт) — в списке только неархивные. Включён — неархивные и архивные в одном списке, архив не подменяет живые дела. «Удалить» (FR-T-6) видно только у строк с `archived: true`. Уникальность названия в MVP не требуется (`isTitleTaken` в контракте не блокирует сохранение).

- Поиск по названию.

- Быстрый drag-and-drop дела прямо на доску дня (если доска открыта в соседней панели на широком экране).
FR-T-5. Дублирование дела — кнопка «Дублировать» создаёт копию с названием «<Название>» + суффикс из i18n `tasks.copySuffix` (ru: ` (копия)`, en: ` (copy)`). Суффикс не зашит в код по-русски: обрезка считается от уже переведённой строки, чтобы итог не превышал 100 символов из FR-T-1: `suffix = t('tasks.copySuffix')`, `base = title.slice(0, 100 - suffix.length).trimEnd()`. Дубликат неархивный, в том же приоритете, цвете и длительности. Создание дела снэкбаром не отменяется: hard delete неархивного запрещён (FR-T-6), отдельного undo-create нет (вайрфреймы §9.3).
FR-T-6. Удаление дела (hard delete). Безвозвратное удаление разрешено только для архивного дела (FR-T-3) и только с подтверждением в UI. Для неархивного дела действие в меню скрыто, а action возвращает CONSTRAINT_VIOLATION. История не теряется: статистика и история размещений берут подпись из Placement.taskSnapshot, поэтому удаление дела не ломает экран статистики (контракты §1.5, §4.4). Отмены у этого действия нет: снэкбар «Восстановить» относится к архивации, а не к удалению (вайрфреймы §9.3).

### 2.2 Управление днями (DayTemplates)
FR-D-1. Создание шаблона дня. Форма содержит:

- Название (обязательно, 1–50 символов)

- Время начала и конца (дефолт 08:00 – 22:00). Формат строго `HH:mm`: часы 00–23, минуты 00, 15, 30 или 45, обе границы внутри `00:00–23:45`. Конец позже начала, длина ≥ 1 ч. Строка не из этого формата (`abc`, `99:99`, `24:00`, `08:07`) — `INVALID_TIME`, а не тихое приведение. Акцентный цвет — `#RRGGBB`, иначе `INVALID_COLOR`.

- Шаг сетки: 15 мин (жёстко в MVP)

- Правило повторения:

- Без привязки (циклический день)

- По дням недели — мультивыбор Пн–Вс

- По числам месяца — мультивыбор 1–31

Правило нормализуется при сохранении (repeat.normalizeRule): поля, не относящиеся к выбранному type, отбрасываются, значения дедуплицируются и сортируются. То есть `{ type: 'weekdays', weekdays: [0], monthdays: [1] }` сохраняется как `{ type: 'weekdays', weekdays: [0] }`, а не «полурабочее» правило. Значения вне диапазона (weekdays — 0..6, monthdays — 1..31) — ошибка VALIDATION_ERROR/INVALID_RULE, а не тихое отбрасывание; пустой после нормализации набор — EMPTY_RULE (контракты §2.5).

- Цвет-акцент дня (для быстрого различения на списке)
FR-D-2. Порядок в цикле. Каждый шаблон имеет order. Порядок задаётся drag-and-drop на странице «Дни». Перестановка мгновенно влияет на циклическую последовательность.
FR-D-3. Редактирование шаблона. Изменения правила повторения не пересчитывают уже материализованные экземпляры (историю не переписываем).
FR-D-4. Удаление шаблона. Если на шаблон ссылается хотя бы один незавершённый (active) экземпляр — запретить удаление, предложить сначала завершить день. Отдельного пользовательского «сброса» дня в MVP нет (`resetCurrentDay` не входит в требования). Завершённые экземпляры удалению не мешают, но остаются в истории со своим templateId: снимка шаблона в DayInstance нет, поэтому после удаления шаблона экран дня/истории показывает для такого экземпляра название-заглушку «Шаблон удалён» (i18n `day.templateDeleted`), а не имя удалённого шаблона. Статистика от этого не страдает — она строится на Placement.taskSnapshot (FR-S-1). Снимок шаблона в модель не добавляем: в MVP имя шаблона в истории не требуется (ТЗ §6 правило 7, контракты §2.7).
FR-D-5. Запрет дублей дат (ответ на Q7). При сохранении правила проверяется, что ни один другой шаблон не покрывает те же даты:

- Для weekdays — пересечение множеств дней недели запрещено.

- Для monthdays — пересечение множеств чисел месяца запрещено.

- Для weekdays и monthdays между собой — пересечения допустимы, приоритет отдаётся monthdays.

- При попытке создать конфликт — показать диалог с перечнем конфликтующих шаблонов.
FR-D-6. Пустой день (ответ на Q7). Если на текущую дату ни один шаблон не подходит — рендерится день без шаблона: сетка по дефолту 08:00–22:00. Пока день виртуальный (размещений нет и в Dexie его нет), по центру CTA «Настроить день» и «Взять дело из списка». «Настроить день» открывает форму нового шаблона (DaysPage / DayTemplateForm). После сохранения DaysPage вызывает `resolveCurrentDay({ force: true })`, и только если день всё ещё виртуальный. Пустой день не «создаётся» отдельной кнопкой: он уже есть в памяти. Два признака не смешивать:

- `isTemplateless` — `templateId === null`. Истина и у виртуального дня, и после того как в него положили дела. В шапке вместо имени шаблона — «Без шаблона» (i18n `day.noTemplate`), не «Шаблон удалён». «Шаблон удалён» только когда `templateId !== null`, а шаблона в сторе нет (FR-D-4).
- Пустое состояние доски (CTA вместо дел) — только `isVirtualInstance`: дня нет в Dexie, `placements` пуст. После первого `placeTask` CTA гаснет, остаётся сетка с делами и подписью «Без шаблона».

Пустой день не имеет привязки к шаблону (`templateId === null`) и существует виртуально, пока в него не положат хотя бы одно дело или не завершат его. Отсюда однозначные правила реализации:

- Признак «пустой день ещё не в БД» — id экземпляра не записан в cycleState.activeInstanceId. Пока день виртуален, activeInstanceId === null.
- Материализация: первое размещение (placeTask) или завершение дня (completeDay) сохраняет экземпляр в Dexie под уже выданным id и записывает активный id в cycleState.
- Перезагрузка ничего не теряет: размещений в виртуальном дне нет, а сам день детерминированно пересоздаётся resolveCurrentDay на ту же дату (шаблона на дату по-прежнему нет).
- Если для даты виртуального дня позже появляется подходящий шаблон (создан или изменён на DaysPage), DaysPage вызывает `resolveCurrentDay({ force: true })`, и пустой день заменяется днём по шаблону. force пересчитывает только виртуальный день: сохранённый экземпляр с размещениями так не пересоздаётся.
- Пустой день не попадает в историю и не требует завершения при смене даты: диалог завершения для него не показывается (отмечать нечего), а новый день просто разрешается на новую дату (ТЗ §2.9).

Виртуальный день — не «второй способ хранить день», а состояние того же currentInstance: переход виртуального дня в сохранённый описан в ТЗ §2.9, в контрактах §3.4 (resolveCurrentDay, placeTask, completeDay) и в скаффолде (§6.3).

### 2.3 Правила повторения и цикл
FR-C-1. Разрешение текущего дня. При открытии приложения:

- Определяется сегодняшняя дата.

- Ищется шаблон с monthdays, покрывающий это число → он становится активным.

- Иначе — шаблон с weekdays, покрывающий текущий день недели.

- Иначе — берётся следующий циклический шаблон (см. FR-C-2).

- Если ничего не найдено → пустой день.

Числа 29–31, которых нет в текущем месяце, не совпадают ни с одним monthday. День проваливается в weekday, затем в цикл. Отдельного «пустого» исхода только из-за короткого месяца нет.
FR-C-2. Циклическая последовательность. Шаблоны с правилом «без привязки» упорядочены по order. После завершения текущего циклического экземпляра указатель lastCyclicTemplateId становится id этого шаблона. Следующий циклический — первый с order больше указателя; если такого нет — шаблон с минимальным order (зацикливание). Указатель двигается только когда завершённый шаблон циклический. Календарное завершение его не меняет. Если все семь дней недели заняты правилами weekdays, циклические шаблоны не выбираются никогда: сохранение не блокируется, форма показывает неблокирующее предупреждение (i18n `days.cyclicUnreachable`). `order` шаблонов всегда уплотнён до `0..n-1`: удаление перенумеровывает оставшиеся в той же транзакции, новый шаблон получает `order = число шаблонов до вставки`.
FR-C-3. Ручной сдвиг дня (ответ на Q4). Кнопка «Следующий день →» доступна, только пока текущий экземпляр в статусе active и CycleStateDto.manualShiftDate не равен сегодняшней локальной дате. Повторный ручной сдвиг в те же сутки запрещён (правило 12) и возвращает SHIFT_ALREADY_DONE_TODAY; попытка сдвинуть завершённый день — DAY_NOT_ACTIVE (контракты §0.2, §3.4). Сценарий один и тот же в ТЗ, контрактах и скаффолде:

- Нажатие ставит сессионные флаги shiftPending = true и shiftMode = 'early' | 'overdue' (таблица режимов — ТЗ §2.8) и открывает диалог завершения (FR-E-1). До подтверждения БД не меняется. Закрытие диалога без подтверждения сбрасывает shiftPending и shiftMode.

- Подтверждение идёт через completeDay. Обычная кнопка «Завершить день» флаг не ставит и следующий экземпляр не создаёт.

- Если shiftPending: день фиксируется по FR-E-2, затем manualShiftDate записывается как сегодня (YYYY-MM-DD, локальная дата). Пишет это поле только ручной сдвиг: обычное завершение и авто-сдвиг его не трогают.

- Новый экземпляр материализуется сразу, его date — всегда дата сдвига (сегодня). Шаблон выбирается от даты сдвига, а не от «сегодня + 1»:
  - shiftMode = 'early' (сдвиг в те же сутки, экземпляр был на сегодня) — шаблон на завтра: monthdays завтрашнего числа, иначе weekdays завтрашнего дня недели, иначе следующий циклический по FR-C-2, иначе пустой день;
  - shiftMode = 'overdue' (экземпляр был просрочен, его date < сегодня) — шаблон на сегодня: та же цепочка приоритетов для сегодняшней даты. Пропущенные дни не догоняются: «Следующий день» из просроченного дня открывает сегодняшний, а не завтрашний.
  timeStart/timeEnd — снимок шаблона или 08:00–22:00. Новый экземпляр становится активным (activeInstanceId); если он пустой — он виртуален и activeInstanceId = null (FR-D-6). Завершённый остаётся в истории со своей датой.

- Отмена завершения (FR-E-3) удаляет только что созданный этим завершением экземпляр (nextInstanceId, если он был сохранён), возвращает manualShiftDate к значению до сдвига и снова делает активным завершённый экземпляр.

Скаффолд этот переход реализует (скаффолд §6.3).
FR-C-4. Автопереход при смене локальной даты. Триггеры одни и те же: старт (initialize), возврат во вкладку (visibilitychange), таймер на ближайшую локальную полночь. Сравнение дат берёт сегодня из new Date() в момент проверки, а не из минутного кэша useNow. Смена currentDate дополнительно вызывает ту же проверку, когда кэш часов догоняет полночь. Что именно происходит — зависит от состояния текущего дня (ТЗ §2.9):

- Виртуальный пустой день (в Dexie его нет): диалога нет, отметок нет — день просто разрешается заново на новую дату (resolveCurrentDay). В историю ничего не пишется.
- Сохранённый день в статусе completed и его date < сегодня: диалога нет, отметки не переносятся — на новую дату разрешается новый день. Так закрывается случай «день завершили вечером, а приложение осталось открытым до полуночи».
- Сохранённый день в статусе active и его date < сегодня:
  - autoShiftAtMidnight включён — диалог не показывается: выполняется подтверждённый сдвиг из FR-C-3 с shiftMode = 'midnight'. Уже `done` остаётся `done`, `pending` становится `skipped`, уже `skipped` не меняется. В `marks` нельзя класть `'skipped'` для размещения со статусом `done`. Шаблон нового дня — на сегодня, пишется lastAutoShiftDate = сегодня, manualShiftDate не пишется. Перед сдвигом cycleState перечитывается из БД: если lastAutoShiftDate уже равен сегодня, второй авто-сдвиг в те же сутки не выполняется (защита в том числе от второй вкладки). Настройка «спрашивать» в этом режиме диалог не возвращает.
  - autoShiftAtMidnight выключен, askToCompleteOnNewDay включён — показывается диалог завершения (FR-E-1), completionSource = 'auto'.
  - Обе настройки выключены — диалога нет, старый день остаётся активным, пока пользователь не завершит его сам («Завершить день» или «Следующий день →»).

Авто-сдвиг пишет lastAutoShiftDate, а не manualShiftDate. Поэтому он не блокирует один ручной сдвиг в те же сутки: после полуночного сдвига пользователь может нажать «Следующий день →» и уехать в завтрашний календарь (правило 12, ТЗ §2.8). Повторный авто-сдвиг в те же сутки не выполняется.

Отмена авто-диалога («Вернуться к дню» и «Пропустить диалог в этот раз») ставит сессионный skippedAutoPromptDate = сегодня. Пока флаг равен текущей дате, visibility и таймер диалог не открывают снова. Флаг не пишется в БД и не меняет askToCompleteOnNewDay (ТЗ §2.7). После перезагрузки страницы флаг пуст, диалог показывается снова. Ручное открытие и сдвиг этот флаг не ставят.
FR-C-5. Состояние цикла. Хранится в CycleStateDto — синглтоне cycleState (см. §3.1, файл src/models/dayInstance.ts):

```
interface CycleStateDto {
  id: 'current';                        // ключ синглтона
  activeInstanceId: string | null;      // текущий экземпляр дня; null — дня в БД нет (в т.ч. виртуальный пустой день)
  lastCyclicTemplateId: string | null;  // последний завершённый циклический
  manualShiftDate: string | null;       // дата ручного сдвига (ISO). Пишет только ручной сдвиг; блокирует повторный ручной сдвиг
  lastAutoShiftDate: string | null;     // дата авто-сдвига (ISO). Пишет только autoShiftAtMidnight; защищает от второго авто-сдвига в те же сутки
}
```

### 2.4 Доска дня (DayBoard)
FR-B-1. Сетка. Вертикальный таймлайн с шагом 15 минут. Крупные линии — каждые 30 мин, часовые — жирнее и с подписью HH:00. Скролл до текущего времени при открытии.
FR-B-2. Размещение дел.

- Drag-and-drop из панели «Дела» в слот.

- Перетаскивание уже размещённого дела между слотами.

- Snap к 15-минутной сетке.

- Дело занимает durationMin / 15 слотов подряд. Одно и то же дело можно поставить в день несколько раз: каждое размещение — отдельный Placement со своим статусом.

- Клавиатурная альтернатива drag-and-drop (НФТ §7): у PlacementCard есть меню действий, пункт «Переместить в слот…» открывает список слотов текущего дня; выбор слота делает то же, что drop. Сама карточка — focusable (tabindex), Enter/Space открывает меню, стрелками — переход по слотам. aria-атрибуты: карточка — `role="button"`, `aria-grabbed`, `aria-label` с названием и временем; слот — `role="listitem"` с `aria-label` «08:15».
FR-B-3. Пересечения. Разрешены (по дефолту), но подсвечиваются:

- Конфликтующие дела отображаются полосами с частичным наложением (50% opacity) и иконкой warning.

- В шапке дня счётчик конфликтов. Баннер информационный, кнопки «Детали» нет: подсветка карточек и есть деталь.

- В конфликты попадают только размещения со статусом pending и done, у которых startMin !== null. Пропущенные (skipped) размещения конфликтов не создают и в счётчик не входят: они уже не часть плана дня (detectConflicts, контракты §4.4).

- Настройка showConflicts (ТЗ §2.7) только прячет подсветку и счётчик. Выключение не запрещает наложение и не удаляет пересечения.
FR-B-4. Выход за пределы. Дело, которое не помещается в интервал экземпляра (timeStart–timeEnd снимка, не текущего шаблона), не отклоняется: оно попадает в нераспределённую зону. Признак — Placement.startMin === null. Отрицательный startMin не используется. Проверка «помещается / не помещается» — ветка укладки, а не ошибка валидации: валидный, но не помещающийся слот превращается в null. Невалидный startMin (не целое число, не кратно 15, отрицательный) — это именно VALIDATION_ERROR, данные не меняются (контракты §3.4). Границы считает scheduler.fitInDay(startMin, durationMin, instance) (ТЗ §4.4).
FR-B-5. Нераспределённая зона. Список размещений текущего дня с startMin === null. Пользователь может позже перетащить их в сетку — тогда startMin становится смещением от timeStart, кратным 15 и не меньшим 0.
FR-B-6. Карточка размещения. Показывает:

- Название дела

- Цветную полосу слева (цвет дела)

- Значок приоритета

- Время начала и конца (подпись через `timeFormat`, FR-SET-3)

- Состояние статуса иконкой, не чекбоксом: pending — без отметки, done — ✓, skipped — ✗. Три статуса чекбоксом не различаются (снятая галочка не отделяет pending от skipped). Меняет статус только меню FR-B-7. Пока текущее локальное время попало внутрь интервала размещения, карточка дополнительно показывает ▶. Это только рисунок: `Placement.status` от него не меняется.
FR-B-7. Быстрые действия по размещению (контекстное меню / свайп):

- Отметить выполненным / снять отметку

- Отметить пропущенным / снять отметку

- Изменить длительность (только для этого размещения: правит Placement.durationMin, снимок дела не трогает; доступно, пока экземпляр active)

- Убрать из дня (удалить это размещение; дело в библиотеке и так остаётся)

- Заменить на другое дело

- Переместить в слот… (клавиатурная альтернатива drag-and-drop, FR-B-2)

Полный набор действий совпадает с контекстным меню из вайрфреймов §1.4. Действия, которых нет в скаффолде, перечислены в таблице гэпов (скаффолд §6).

### 2.5 Завершение дня
FR-E-1. Диалог завершения. Триггерится:

- Вручную (кнопка «Завершить день»)

- При сдвиге на следующий день (FR-C-3)

- Автоматически при наступлении новых суток (FR-C-4)
Содержимое диалога:

- Список всех размещений текущего дня с чекбоксами, включая нераспределённые (`startMin === null` — без времени, подпись «без времени»).

- По умолчанию: `done` — отмечены; `pending` и `skipped` — сняты.

- Пользователь может снять галочку с ранее отмеченного `done`.

- Быстрые кнопки «Отметить всё» и «Снять всё».

- Кнопка «Подтвердить». Чекбокс здесь бинарный: отмечено → `done`, снято → `skipped`. На карточке доски чекбокса нет (FR-B-6).

- Опция «Пропустить диалог в этот раз» только у авто-триггера (FR-C-4). Это разовый сессионный пропуск: skippedAutoPromptDate, без записи в настройки. Постоянный отказ — тумблер «Спрашивать о завершении при новом дне» на SettingsPage (вайрфреймы §8, ТЗ §2.7, поле askToCompleteOnNewDay). «Вернуться к дню» у авто-диалога делает тот же разовый пропуск. У ручного завершения и у сдвига «Вернуться к дню» только закрывает диалог.
FR-E-2. Логика фиксации после подтверждения:

- Отмеченные → status = 'done'.

- Не отмеченные (включая ранее помеченные done, с которых сняли галочку) → status = 'skipped'.

- Экземпляр получает status = 'completed', completedAt = Date.now() и остаётся в БД для статистики.

- activeInstanceId не обнуляется. Если завершаемый день имеет сегодняшнюю дату, завершённый экземпляр остаётся текущим до смены календарной даты или до ручного сдвига. Повторное открытие приложения в ту же дату не вызывает resolveCurrentDay и не создаёт второй экземпляр. Второй экземпляр на ту же дату появляется только как результат FR-C-3.

- Если завершаемый день просрочен (его date < сегодня) — это завершение «вчерашнего» дня из диалога FR-C-4 или сдвиг без `shiftPending` (сдвиг идёт своей веткой). После фиксации такого дня сразу разрешается день на сегодня (`resolveCurrentDay`), без диалога и без переноса отметок: пользователь не должен остаться на экране вчерашнего дня. Созданный этим завершением экземпляр запоминается в nextInstanceId — его удаляет отмена завершения (FR-E-3). Если фиксация уже записана, а `resolveCurrentDay` вернул ошибку, `completeDay` не делает вид, что всё хорошо: диалог закрывается (повторное «Подтвердить» упрётся в `DAY_NOT_ACTIVE`), статистика всё равно пересчитывается, наружу уходит `DB_ERROR` с `details.reason = 'RESOLVE_AFTER_COMPLETE'`. UI предлагает «Открыть сегодняшний день» — повторный `resolveCurrentDay()`.

- Если завершённый шаблон циклический, lastCyclicTemplateId продвигается и в IndexedDB, и в памяти cycleState. Календарный шаблон указатель не двигает. manualShiftDate и lastAutoShiftDate при обычном завершении не изменяются.

- После успешной фиксации вызывается statsStore.recompute() — экран статистики, если он открыт, показывает новые числа без ручного обновления (контракты §3.4/§3.5, FR-S-1).
FR-E-3. Отмена завершения. В течение сессии после завершения доступна кнопка «Отменить завершение» (до перезагрузки страницы). После перезагрузки — экземпляр считается закрытым. Отмена возвращает день в active, восстанавливает снимок размещений, lastCyclicTemplateId и manualShiftDate, удаляет экземпляр, созданный этим завершением (nextInstanceId, если он был сохранён), и снова делает завершённый день текущим. Специально не восстанавливается lastAutoShiftDate: авто-сдвиг в эти сутки уже произошёл, повторять его после отмены нельзя — день останется активным до ручного действия или следующей смены даты (контракты §3.4 cancelCompletion).
FR-E-4. Отсутствие переноса. В MVP невыполненные дела не переносятся на следующий день. Пользователь переносит их вручную из списка дел.

### 2.6 Статистика
FR-S-1. Накопительные счётчики по каждому делу:

- totalPlaced — сколько раз размещалось

- totalDone — выполнено

- totalSkipped — пропущено

- completionRate = totalDone / (totalDone + totalSkipped)

Имена FR и поля TaskStats (контракты §4.1, скаффолд services/stats.ts):

- totalPlaced — placed, подпись «размещено»

- totalDone — done, подпись «выполнено»

- totalSkipped — skipped, подпись «пропущено»

- completionRate — rate, подпись «рейт»
FR-S-2. Экран статистики. Таблица дел, у которых есть хотя бы одно размещение в завершённых экземплярах выбранного периода. Дело без такой истории в таблицу не попадает: строки «0 размещено / 0 выполнено / 0 пропущено» не существует ни для никогда не размещённого дела, ни для дела, размещавшегося только вне периода (нулевой рейт «—» поэтому тоже относится только к делам с размещениями). Строка с рейтом 0% — это дело, у которого в периоде placed > 0 и done = 0 (все размещения пропущены). Несколько завершённых экземпляров на одну календарную дату (ручной сдвиг, индекса уникальности `date` нет) считаются все: за этот день в счётчиках может быть больше одного размещения одного дела. Подпись title/color/priority берётся из снимка с наибольшей датой экземпляра, а при равной дате — с большим `placedAt`. Итоговая сводка считается по всем делам периода, а не по видимым строкам; в списке показываются первые N с сортировкой и прокруткой (вайрфреймы §7.1/§7.2). Топ-5 и антитоп-5 в MVP нет. Колонки:

- Название, цвет, приоритет

- Счётчики (placed / done / skipped)

- Прогресс-бар completionRate: `rate = done / (done + skipped)`, при 0/0 — прочерк «—»

- Сортировка по любой колонке
FR-S-3. Периоды. Фильтр: 7 дней / 30 дней / всё время. В MVP обязателен вариант «всё время», он же дефолт экрана. Окно 7 дней — сегодня и 6 предыдущих локальных дат, 30 дней — сегодня и 29 предыдущих.
FR-S-4. Отдельная страница дела. История размещений: дата, время, статус.

### 2.7 Настройки
FR-SET-1. Тема: Light / Dark / Auto (по системной).
FR-SET-2. Язык: ru (дефолт) / en (заготовка).
FR-SET-3. Формат времени: 24ч / 12ч. Применяется ко всем часовым подписям: слоты сетки, интервал на карточке, список диалога завершения, шапка дня. Сетка в данных по-прежнему хранит минуты; `HH:mm` в сторе — внутренний вид, на экран строка выходит через форматтер настройки. `12h` не меняет шаг 15 минут и не меняет хранение.
FR-SET-4. Экспорт данных: JSON-дамп всех сущностей. Точный формат, состав блоков и версия файла — контракты §5.4 (version «1.0»). После успешного экспорта обновляется lastBackupAt.
FR-SET-5. Импорт данных: из JSON, с подтверждением перезаписи. Перед записью файл валидируется структурно: JSON разбирается, version поддерживается, все блоки data присутствуют и совпадают с моделями по форме (контракты §5.4). Семантика не проверяется: пересечение правил, длина дня и кратность длительности импорт не отклоняет. Если в файле два шаблона делят один день недели, день разрешает `repeat.resolveDayForDate` (первый по `order`). `weekdayMap` / `monthdayMap` — кэш того же правила (первый по `order` побеждает, не последний в массиве). Невалидный файл → VALIDATION_ERROR, данные в БД и localStorage не меняются. Импорт таблиц Dexie выполняется одной транзакцией; блок settings пишется в localStorage и в эту транзакцию не входит. После импорта сторы переинициализируются (reload или полный rehydrate).
FR-SET-6. Спрашивать о завершении при новом дне (askToCompleteOnNewDay, по умолчанию включено). Постоянный выключатель авто-диалога FR-C-4. Разовый пропуск в диалоге эту настройку не меняет.
FR-SET-7. Авто-сдвиг в 00:00 (autoShiftAtMidnight, по умолчанию выключено). Если включено, смена даты выполняет подтверждённый сдвиг из FR-C-3 в режиме 'midnight' (шаблон нового дня — на сегодня) без диалога и пишет lastAutoShiftDate, а не manualShiftDate. Уже выполненные размещения остаются `done` (FR-C-4). Пока выключено, сдвиг только кнопкой «Следующий день».
FR-SET-8. Показывать конфликты (showConflicts, по умолчанию включено). См. FR-B-3: прячет подсветку и счётчик, пересечения по-прежнему разрешены.
FR-SET-9. Первый день недели для отображения (firstDayOfWeek): 0 — понедельник (дефолт), 1 — воскресенье. Влияет только на порядок чипов Пн–Вс в форме шаблона: при 1 ряд начинается с вс. На `RepeatRule.weekdays` не влияет: там 0 всегда понедельник. На заголовок «понедельник, 23 сентября» не влияет.
FR-SET-10. Очистить все данные (clearAll). Кнопка в разделе «Данные» на SettingsPage, помечена как опасная, выполняется только после подтверждения («Удалить все дела, шаблоны и историю? Действие необратимо»). Очищает:
- таблицы Dexie: tasks, dayTemplates, dayInstances;
- singleton cycleState — пересоздаётся через ensureCycleState со значениями по умолчанию (активный день, указатель цикла и обе даты сдвига обнуляются);
- настройки в localStorage по всем ключам `tododay:*`;
- сессионное состояние сторов (currentInstance, кэш статистики, снапшоты отмены завершения).

Экспорт перед очисткой автоматически не делается, но диалог предлагает выгрузить данные, если экспорта ещё не было (lastBackupAt === null). После очистки выполняется та же переинициализация, что и после импорта (reload или rehydrate), и приложение показывает пустые состояния. В коде — settingsStore.clearAll() (контракты §5.3/§5.4).

### 2.8 Правила дат (локальная дата) — единый свод
Все даты в приложении — локальные календарные даты строкой 'YYYY-MM-DD'. Этот раздел — единственное место, где описаны правила; FR-C-3, FR-C-4, FR-S-3 и контракты §3.4 ссылаются сюда.

Определения:

| Понятие | Правило |
| --- | --- |
| Сегодня | `todayISO()` = `format(new Date(), 'yyyy-MM-dd')` (date-fns, локальная зона). Никогда не `toISOString()` и не `new Date('YYYY-MM-DD')` |
| День недели (0 = пн) | `weekday0 = (local.getDay() + 6) % 7`, где `local = parseISODate(iso)`. `Date.getDay()` даёт 0 = воскресенье, поэтому без `+ 6` понедельник становится 1 и правило weekdays съезжает на сутки. `firstDayOfWeek` эту формулу не сдвигает |
| Границы периода статистики | Сравнение строк 'YYYY-MM-DD'; `periodStartISO`: '7d' — сегодня и 6 предыдущих дат, '30d' — сегодня и 29 предыдущих, 'all' — без границы |
| Дата экземпляра | DayInstance.date — локальная дата, на которую день проживается |
| Дата сдвига (targetDate) | Всегда сегодня: и ручной сдвиг, и авто-сдвиг создают экземпляр на сегодняшнюю дату |
| Дата шаблона (templateDate) | Дата календаря, по которой выбирается шаблон для нового экземпляра; зависит от режима сдвига (таблица ниже) |
| manualShiftDate | Дата последнего ручного сдвига. Пишется только ручным сдвигом (shiftMode 'early'/'overdue'); блокирует повторный ручной сдвиг, пока равна сегодня |
| lastAutoShiftDate | Дата последнего авто-сдвига. Пишется только autoShiftAtMidnight (shiftMode 'midnight'); блокирует повторный авто-сдвиг в те же сутки |

Запрещено во всём проекте:

- `new Date('YYYY-MM-DD')` — парсится как UTC-полночь и на границе суток/периода даёт сдвиг на день. Для разбора ISO-даты использовать локальный конструктор `new Date(y, m - 1, d)` (helper `dates.parseISODate`); правило проверяется линтером (скаффолд §3.5, no-restricted-syntax).
- `toISOString()` для получения календарной даты — только для timestamps (`createdAt`, `completedAt`, `exportedAt`).
- Арифметика дат «вручную» через `Date.now() + 86400000` — только через `dates.addDaysISO(iso, n)`.

Режимы сдвига (передаются в completeDay через состояние shiftMode, контракты §3.1/§3.4):

| Режим | Когда | Дата завершаемого экземпляра | targetDate | templateDate | Что пишется | Диалог |
| --- | --- | --- | --- | --- | --- | --- |
| early | Ручной сдвиг «Следующий день →» в те же сутки | = сегодня | сегодня | сегодня + 1 (завтрашний календарь) | manualShiftDate = сегодня | Да (FR-E-1, shift) |
| overdue | Ручной сдвиг, когда активный день просрочен | < сегодня | сегодня | сегодня | manualShiftDate = сегодня | Да (FR-E-1, shift) |
| midnight | autoShiftAtMidnight в момент смены даты | < сегодня | сегодня | сегодня | lastAutoShiftDate = сегодня; manualShiftDate не пишется | Нет (FR-C-4) |

Формула одна для всех режимов: `targetDate = сегодня`, `templateDate = (shiftMode === 'early') ? addDaysISO(дата экземпляра, 1) : сегодня`. Отсюда off-by-one невозможен: шаблон берётся от даты завершаемого экземпляра, а не от `new Date()` в момент сдвига. Реализация — чистая функция `repeat.resolveShiftTargets(instanceDate, today, mode)` (ТЗ §4.4, скаффолд §7.1). Инвариант: режим 'early' допустим только при `instanceDate === today`; если состояние противоречиво, функция возвращает режим 'overdue' (шаблон на сегодня) и пишет console.warn.

Смена даты без сдвига:

- Завершённый вчера день при смене даты не переиспользуется: на сегодня разрешается новый день (FR-C-4, FR-E-2).
- Просроченные дни не «догоняются»: сколько бы дней ни было пропущено, следующий проживаемый день — сегодняшний.

### 2.9 Жизненный цикл текущего дня
Состояния currentInstance и переходы. Отдельного поля «состояние» в модели нет: состояние выводится из presence в Dexie, InstanceStatus и активного id.

| Состояние | В Dexie | InstanceStatus | Признак | Как попадаем |
| --- | --- | --- | --- | --- |
| virtual-empty (пустой день) | Нет | — (в памяти 'active') | `activeInstanceId !== currentInstance.id` (обычно null) | resolveCurrentDay, когда ни один шаблон не подошёл (FR-D-6) |
| active | Да | 'active' | `activeInstanceId === currentInstance.id` | resolveCurrentDay по шаблону; либо placeTask/completeDay материализовали пустой день |
| completed | Да | 'completed' | `activeInstanceId === currentInstance.id` | completeDay без сдвига, когда дата дня = сегодня |
| next (создан завершением) | Да или нет | 'active' | новый id в activeInstanceId (или null, если новый день пустой) | completeDay со shiftPending (FR-C-3); либо автопереход с просроченного дня (FR-E-2) |

Переходы:

```
virtual-empty --placeTask--------> active        (экземпляр пишется в Dexie, activeInstanceId = id)
virtual-empty --completeDay------> completed     (пустой день сохраняется в историю: FR-D-6)
virtual-empty --смена даты-------> virtual-empty/active на новую дату (в историю не пишется, диалога нет)
active        --completeDay------> completed     (дата дня = сегодня: экземпляр остаётся текущим)
active        --completeDay+shift> next          (shiftMode early/overdue/midnight; старый — completed)
active(просрочен)--completeDay---> completed + next на сегодня (без диалога и без отметок, FR-E-2)
completed     --cancelCompletion-> active        (в течение сессии, FR-E-3; next-экземпляр удаляется)
completed     --смена даты-------> active/virtual-empty на сегодня (без диалога, отметки не переносятся)
active(просроч)--смена даты------> диалог завершения или авто-сдвиг (FR-C-4) или тишина (обе настройки выключены)
```

Инварианты:

- Один календарный день может иметь несколько экземпляров: ручной сдвиг создаёт второй экземпляр на ту же дату (индекса уникальности dayInstances.date нет намеренно). Автоматическое разрешение дня (resolveCurrentDay) второй экземпляр на уже текущую дату не создаёт.
- Виртуальный день всегда пуст: placements = [], поэтому его потеря при перезагрузке безопасна.
- Завершать можно и пустой день — это единственный случай, когда в истории появляется экземпляр без размещений.

### 2.10 Нормативные сценарии
Сценарии ниже — часть требований: тесты в контрактах §9 проверяют именно их.

1. Вчерашний день не завершён, приложение открыто сегодня, autoShiftAtMidnight выключен, askToCompleteOnNewDay включён. Показывается диалог завершения с вчерашним днём (FR-C-4). «Пропустить диалог в этот раз» ставит skippedAutoPromptDate: до перезагрузки диалог не возвращается, вчерашний день остаётся активным. Подтверждение переводит вчерашний день в completed и разрешает день на сегодня (FR-E-2). «Отменить завершение» в сессии возвращает вчерашний день и удаляет созданный сегодняшний.
2. То же, но autoShiftAtMidnight включён, и во вчерашнем дне часть размещений уже `done`. Диалога нет: `done` остаётся `done`, pending становится skipped, manualShiftDate не пишется, lastAutoShiftDate = сегодня, новый экземпляр — дата сегодня, шаблон на сегодняшний календарь. Повторный вызов checkDayChange в те же сутки сдвиг не повторяет. Кнопка «Следующий день →» в эти сутки доступна: она создаст экземпляр с датой сегодня и шаблоном на завтра (shiftMode 'early').
3. Ручной сдвиг в тот же день, когда экземпляр уже на сегодня. Первый сдвиг: manualShiftDate = сегодня, новый экземпляр — дата сегодня, шаблон на завтра. Второй сдвиг в те же сутки: кнопка недоступна (canShiftNext = false), action возвращает SHIFT_ALREADY_DONE_TODAY, БД не меняется.
4. Сдвиг просроченного дня вручную (вчерашний день, пользователь нажал «Следующий день →»). shiftMode = 'overdue': новый экземпляр — дата сегодня, шаблон на сегодня (не на завтра), manualShiftDate = сегодня.
5. Пустой день: шаблонов нет. День показывается как пустой, в Dexie ничего нет, activeInstanceId = null. Добавление первого дела сохраняет экземпляр и activeInstanceId. Перезагрузка до добавления дела даёт тот же пустой день; перезагрузка после — день с делом. Завершение пустого дня сохраняет экземпляр с placements = [] в историю.
6. Пустой день и смена даты. В полночь виртуальный пустой день не показывается в диалоге и не попадает в историю: он просто разрешается на новую дату. Если после полуночи для новой даты есть шаблон, день сразу материализуется по шаблону.
7. Дело удалено из архива, а его размещения остались в завершённых днях. Статистика показывает его по taskSnapshot размещений (FR-T-6, контракты §4.4), экран истории размещений — по тем же снимкам.

### 3.3 Политика миграций Dexie
Схема версионирована (`db.version(n).stores({...})`). Правила для MVP и дальше:

- Текущая схема — version(1). Правки документа, не меняющие набор таблиц/индексов (например, добавление поля `lastAutoShiftDate` в cycleState в ревизии 1.2), новую версию не требуют: отсутствующие поля достраивает `ensureCycleState()` дефолтами, а не Dexie-миграция.
- Как только меняется набор таблиц или индексов — добавляется `db.version(n + 1).stores({...}).upgrade(tx => ...)`. Индексы в новой версии перечисляются полностью (Dexie не наследует их автоматически), удаление индекса оформляется строкой без него.
- Данные пользователя миграция не удаляет: upgrade-функция только дополняет/перекладывает поля. Деструктивная миграция (очистка таблицы) недопустима без подтверждения пользователя.
- Изменение схемы обязательно отмечается в этом ТЗ и в журнале правок; тест `db.schema` проверяет, что объявленная версия совпадает с ожидаемой.
- Импорт JSON из файла другой версии формата не мигрирует БД: версия формата проверяется до записи (контракты §5.4), при несовпадении импорт отклоняется.

### 3.4 Локальные даты в модели
Поля-даты моделей (`DayInstance.date`, `CycleStateDto.manualShiftDate`, `lastAutoShiftDate`) хранят локальную календарную дату 'YYYY-MM-DD'. Полный свод правил — ТЗ §2.8.

### 4.4 Сервисы (чистые функции)

Даты (ТЗ §2.8, файл services/dates.ts):

- dates.todayISO(): string — сегодняшняя локальная дата 'YYYY-MM-DD'.

- dates.toLocalISO(date: Date): string — локальная дата из Date (без UTC-сдвига).

- dates.addDaysISO(iso: string, n: number): string — арифметика по календарю.

- dates.parseISODate(iso: string): Date — локальная полночь (`new Date(y, m-1, d)`).

- dates.minutesOfDay('HH:mm'): number — минуты от начала суток. Для уже проверенной строки.

- dates.parseClock('HH:mm'): number | null — FR-D-1. null, если это не `HH:mm` с минутами 00/15/30/45 в диапазоне `00:00–23:45`.

Цикл и правила дней (services/repeat.ts):

- repeat.resolveDayForDate(date, templates, lastCyclicTemplateId): DayTemplate | null — FR-C-1.

- repeat.resolveShiftTargets(instanceDate, today, mode): { mode: ShiftMode; targetDate: string; templateDate: string } — ТЗ §2.8. Единственное место, где вычисляется дата шаблона при сдвиге: `targetDate = today`, `templateDate = mode === 'early' ? addDaysISO(instanceDate, 1) : today`. Инвариант 'early' требует `instanceDate === today`, иначе возвращается 'overdue' + console.warn.

- repeat.normalizeRule(rule): RepeatRule — FR-D-1: отбрасывает поля, не относящиеся к type, дедуплицирует и сортирует значения.

- repeat.validateRule(rule): ValidationIssue[] — EMPTY_RULE (пустой набор) и INVALID_RULE (значения вне диапазона 0..6 / 1..31 или не целые).

- repeat.validateNoOverlap(rule, templates, excludeId?): ValidationIssue[] — FR-D-5. Правило и правила других шаблонов нормализуются; результат — ValidationIssue с conflictingTemplateIds и values (единый тип, см. §3.1).

Раскладка доски (services/scheduler.ts):

- scheduler.isValidStartMin(v: unknown): v is number — true только для целого, кратного 15, ≥ 0. Невалидный startMin — ошибка VALIDATION_ERROR, а не snap и не null (контракты §3.4).

- scheduler.fitInDay(startMin: number, durationMin: number, instance: DayInstance): boolean — FR-B-4. Вызывается только с не-null и уже проверенным startMin; границы берутся из снимка экземпляра (timeStart/timeEnd), не из шаблона. Дело помещается, если `startMin + durationMin <= minutesOfDay(timeEnd) - minutesOfDay(timeStart)`.

- scheduler.detectConflicts(placements): Conflict[] — FR-B-3. Учитывает только размещения со startMin !== null и статусом pending или done; skipped конфликтов не создаёт.

Статистика (services/stats.ts):

- stats.aggregateStats(instances, period): { perTask: Map<string, TaskStats>; overall: OverallStats } — FR-S-1.

## 6. Бизнес-правила и краевые случаи

| # | Кейс | Поведение |
| --- | --- | --- |
| 1 | Пустой день без дел | Виртуальный день: показ дефолтной сетки + CTA, в Dexie ничего нет, activeInstanceId = null (FR-D-6) |
| 2 | Конфликт правил дней | Запрет сохранения (FR-D-5) |
| 3 | Дело длиннее дня | Валидный, но не помещающийся слот → «нераспределённые» (startMin = null); невалидный startMin → VALIDATION_ERROR (FR-B-4) |
| 4 | Пересечения дел | Разрешены, подсветка warning. В конфликты не попадают skipped (FR-B-3) |
| 5 | День не завершён к смене даты | Авто-диалог на старте, при возврате во вкладку и в полночь (FR-C-4). Отмена гасит диалог до перезагрузки |
| 6 | Отмена завершения | Доступна в рамках сессии; возвращает день, снимки, manualShiftDate и удаляет созданный завершением экземпляр (FR-E-3) |
| 7 | Удаление шаблона с активным экземпляром | Запрет, предложение сначала завершить. Завершённые экземпляры остаются с templateId без снимка имени: показываем «Шаблон удалён» (FR-D-4) |
| 7а | Шаблон создан/изменён, когда текущий день пустой | DaysPage вызывает resolveCurrentDay({ force: true }): виртуальный пустой день заменяется днём по шаблону (FR-D-6) |
| 8 | Архивация дела с pending-размещением в активном дне | Это размещение → skipped; done не меняется; дело в архив. Если перевод размещения не дошёл, его повторяет следующий initialize |
| 8а | Удаление дела из архива | Разрешено только для archived, с подтверждением; история и статистика остаются по taskSnapshot (FR-T-6) |
| 9 | Изменение длительности дела с активными размещениями | durationMin задачи меняется, снимки существующих Placement — нет (FR-T-2) |
| 10 | Изменение правила повторения | История не пересчитывается |
| 11 | Одновременное редактирование (несколько вкладок) | Целевое поведение: Dexie liveQuery, последний пишет — выигрывает. В скаффолде подписки liveQuery ещё нет (скаффолд §6); от двойного авто-сдвига защищает перечитывание lastAutoShiftDate из БД |
| 12 | Повторный ручной сдвиг в те же сутки | Запрещён, пока manualShiftDate равен сегодня (SHIFT_ALREADY_DONE_TODAY). Первый ручной сдвиг за сутки разрешён, в том числе если незавершённый день начался вчера. Авто-сдвиг пишет lastAutoShiftDate и ручной сдвиг не блокирует; второй авто-сдвиг в те же сутки не выполняется |
| 13 | Смена даты при завершённом текущем дне | Новый день разрешается без диалога и без переноса отметок (FR-C-4, FR-E-2) |
| 14 | Смена даты при виртуальном пустом дне | День разрешается на новую дату, в историю не пишется, диалог не показывается (FR-D-6, FR-C-4) |

| 16 | Дата в ISO-строке | Всегда локальная 'YYYY-MM-DD' через services/dates.ts; new Date('YYYY-MM-DD') и toISOString() для календарных дат запрещены (ТЗ §2.8) |

## 7. Нефункциональные требования

- Производительность: FCP < 1.5 c на 3G; доска дня рендерит 100+ размещений без просадок. Виртуализируется колонка подписей времени. Слой размещений позиционируется на всю высоту дня и не размонтируется вместе с якорным слотом: карточка на несколько слотов не должна пропадать, когда её первый слот вышел из окна. Ключ карточки — placement.id. Тяжёлые вычисления (слоты, конфликты, границы) — в computed/getters, а не в разметке.

- Офлайн: 100% функционала доступно без сети (PWA + service worker).

- Хранение: IndexedDB, экспорт/импорт JSON (политика миграций — ТЗ §3.3).

- Доступность: контраст WCAG AA; focus-trap в модалках; aria-атрибуты и клавиатурная альтернатива drag-and-drop: PlacementCard — `role="button"`, `aria-grabbed`, `aria-label` с названием и временем; слоты — доступные имена («08:15»); Action-меню размещения открывается с клавиатуры (Enter/Space), пункт «Переместить в слот…» выполняет перемещение без мыши (FR-B-2, FR-B-7).

- i18n: ru (дефолт), en (заготовка), все строки через vue-i18n, включая раздел настроек и служебные тексты (скаффолд §9.3/§9.4). Переключение языка немедленно меняет локаль i18n (контракты §5.3).

- Адаптив: breakpoints Quasar; mobile-first.

- Тесты: Vitest для services/* и сторов (покрытие ≥ 70% на критичных модулях). Обязательный минимум — сценарии ТЗ §2.10 и правила дат ТЗ §2.8 (список в контрактах §9).

- Логирование: console.warn при конфликтах циклов и при противоречивом режиме сдвига.

## 9. Критерии приёмки
По делам:

- □  Можно создать дело с названием, приоритетом, цветом, длительностью кратной 15 мин.

- □  Дело можно редактировать, архивировать, дублировать.

- □  Валидация не пропускает пустое имя и длительность вне диапазона.

- □  Дубликат с длинным названием получает суффикс текущей локали (`tasks.copySuffix`) длиной не более 100 символов вместе с базой (FR-T-5).

- □  Длительность 1425 принимается, 1440 и некратная 15 — нет (FR-T-1).

- □  Правка durationMin задачи не меняет durationMin уже созданных размещений (FR-T-2, правило 9).

- □  Безвозвратное удаление доступно только архивному делу и требует подтверждения; у неархивного — CONSTRAINT_VIOLATION (FR-T-6).
По дням:

- □  Можно создать шаблон с диапазоном, правилом и порядком в цикле.

- □  Попытка создать пересекающееся правило даёт ошибку с перечнем конфликтов.

- □  Правило с лишними для своего type полями сохраняется нормализованным, значения вне диапазона отклоняются (FR-D-1).

- □  Для даты без подходящего шаблона показывается пустой день.

- □  Пустой день отсутствует в Dexie, пока в него не положили дело или не завершили его (FR-D-6).

- □  Первое дело в пустом дне сохраняет экземпляр и activeInstanceId; перезагрузка восстанавливает день (FR-D-6).

- □  Удаление шаблона с активным экземпляром запрещено; завершённые экземпляры удалённого шаблона показывают «Шаблон удалён» (FR-D-4).
По циклу:

- □  Календарные шаблоны подставляются по дате.

- □  Циклические шаблоны идут по order и зацикливаются.

- □  Кнопка «Следующий день» доступна только для незавершённого дня.

- □  Ручной сдвиг в те же сутки создаёт экземпляр с датой «сегодня» и шаблоном на завтра (shiftMode 'early'), FR-C-3.

- □  Сдвиг просроченного дня и авто-сдвиг в полночь создают экземпляр с датой «сегодня» и шаблоном на сегодня ('overdue'/'midnight'), FR-C-3/FR-C-4.

- □  Авто-сдвиг пишет lastAutoShiftDate и не блокирует ручной сдвиг в те же сутки; второй авто-сдвиг в те же сутки не выполняется, FR-C-4.

- □  Авто-сдвиг не переводит уже `done` в `skipped` (сценарий 2).

- □  Смена даты показывает диалог завершения, если день не закрыт и авто-сдвиг выключен.

- □  Завершённый вчера день при смене даты заменяется днём на сегодня без диалога и без переноса отметок (правило 13).

- □  Виртуальный пустой день при смене даты не попадает в историю и не открывает диалог (правило 14).

- □  Повторное открытие в ту же дату не создаёт второй экземпляр уже завершённого дня.

- □  Второй ручной сдвиг за сутки недоступен и отклоняется кодом SHIFT_ALREADY_DONE_TODAY; сдвиг завершённого дня — DAY_NOT_ACTIVE.

- □  Все календарные даты берутся через services/dates.ts; в коде нет new Date('YYYY-MM-DD') и toISOString() для дат (ТЗ §2.8).
По доске:

- □  Drag-and-drop из списка в слот и между слотами работает.

- □  Перемещение доступно с клавиатуры через меню размещения (НФТ §7).

- □  Сетка 15 мин, крупные линии каждые 30 мин.

- □  Пересечения подсвечиваются; skipped в конфликты не попадает (FR-B-3).

- □  Дело, не влезающее в день, уходит в «нераспределённые» (startMin = null).

- □  Невалидный startMin возвращает VALIDATION_ERROR и не меняет размещение (FR-B-4).

- □  Контекстное меню размещения содержит «Изменить длительность» (FR-B-7).
По завершению:

- □  Диалог показывает все размещения с чекбоксами.

- □  Отмена галочки помечает дело skipped.

- □  После подтверждения экземпляр получает completed.

- □  После завершения дня статистика пересчитывается без ручного обновления (FR-S-1, контракты §3.4).

- □  Отмена завершения доступна в сессии и удаляет экземпляр, созданный этим завершением.
По статистике:

- □  Счётчики done/skipped/rate корректны.

- □  Дело без размещений в завершённых экземплярах периода в таблицу не попадает; строка «0 размещено / 0 выполнено» не существует (FR-S-2).

- □  Рейт 0% показывается только для placed > 0 и done = 0.

- □  На странице дела видна история размещений.
Настройки и данные:

- □  Время шаблона вне `HH:mm` с минутами 00/15/30/45 и цвет акцента не в `#RRGGBB` отклоняются (FR-D-1).

- □  С 1024 px нижней таб-панели нет, до 1024 px она есть (ТЗ §5.1, вайрфреймы §11).

- □  Переключение языка немедленно меняет локаль интерфейса (FR-SET-2, контракты §5.3).

- □  «Очистить все данные» требует подтверждения и очищает Dexie, cycleState и localStorage (FR-SET-10).
НФТ:

- □  Приложение работает офлайн.

- □  Устанавливается как PWA.

- □  Есть ru/en, light/dark.

- □  Все строки интерфейса, включая раздел настроек, приходят из i18n (скаффолд §9.3/§9.4).

- Синхронизация между устройствами — бэкенд, авторизация, конфликты слияния.

- Уведомления — Web Push при наступлении слота.

# ToDoDay — Контракты сторов Pinia
Документ описывает state, getters, actions каждого стора, их типы, побочные эффекты и правила взаимодействия. Все сторы — setup-стиль (defineStore('name', () => {...})), типизированы, работают поверх Dexie (IndexedDB).

> **Важно про объём.** Этот раздел — полный целевой контракт API. Стартовый скаффолд (раздел «Стартовый скаффолд») реализует только подмножество: CRUD дел, шаблоны дней, разрешение текущего дня и завершение дня. Всё остальное помечено ниже (см. §6 скаффолда, «Заглушки сторов») и не считается «сломанным скаффолдом»: расхождение устранено явной пометкой, а не доработкой кода. Контракт — источник истины для имён и типов; при расхождении имён правится скаффолд.

## 0. Общие принципы

### 0.1 Соглашения

- Именование: use<Domain>Store, файлы — src/stores/<domain>.ts.

- Стиль: setup stores (ref, computed, function).

- Асинхронность: все actions, работающие с БД, возвращают Promise.

- Ошибки: actions не бросают исключения наружу, а возвращают Result<T>:

```
type Result<T> =
  | { ok: true; data: T }
  | { ok: false; error: AppError };
```

Исключения ловятся внутри, логируются через logger, UI показывает тост.

- Реактивность БД: целевой контракт — liveQuery из Dexie для синхронизации между вкладками. В скаффолде подписки subscribe/unsubscribe ещё нет (скаффолд §6). Правило 11 ТЗ §6 описывает это целевое поведение.

- Оптимистичные обновления: для UI-критичных операций (drag-and-drop, чекбоксы) state обновляется сразу, при ошибке — откат.

- Персистентность: настройки — в localStorage через @vueuse/core (useStorage). Остальное — в IndexedDB.

### 0.2 Общие типы

```
// src/models/common.ts
export interface AppError {
  code: ErrorCode;
  message: string;         // человекочитаемое
  details?: unknown;
}

export type ErrorCode =
  | 'DB_ERROR'
  | 'VALIDATION_ERROR'
  | 'CONFLICT'
  | 'NOT_FOUND'
  | 'CONSTRAINT_VIOLATION'
  | 'SHIFT_ALREADY_DONE_TODAY'   // ручной сдвиг в эти сутки уже выполнялся (FR-C-3, правило 12)
  | 'DAY_NOT_ACTIVE'             // операция требует активного дня, а он завершён или отсутствует
  | 'UNKNOWN';

export type Result<T> =
  | { ok: true; data: T }
  | { ok: false; error: AppError };

// src/models/enums.ts
export type Priority = 'low' | 'medium' | 'high' | 'critical';
export type PlacementStatus = 'pending' | 'done' | 'skipped';
export type InstanceStatus = 'active' | 'completed';
export type RepeatRuleType = 'none' | 'weekdays' | 'monthdays';
export type ThemeMode = 'light' | 'dark' | 'auto';
export type TimeFormat = '24h' | '12h';

// Режим сдвига дня (ТЗ §2.8, контракты §3.1)
export type ShiftMode = 'early' | 'midnight' | 'overdue';
```

Коды `SHIFT_ALREADY_DONE_TODAY` и `DAY_NOT_ACTIVE` введены, чтобы UI различал причины отказа кнопки «Следующий день» и показывал разные тексты (вайрфреймы §9.3). Общий CONFLICT для этих двух случаев больше не используется.

## 1. useTasksStore
Ответственность: CRUD дел, архивация, поиск и фильтрация, снимки для размещений.

### 1.1 State

```
interface TasksState {
  // Данные
  tasks: Ref<Task[]>;                        // все неархивные + архивные
  loading: Ref<boolean>;                     // идёт загрузка
  initialized: Ref<boolean>;                 // данные загружены (при активной liveQuery — ещё и подписка)

  // UI-состояние (не персистится)

  filterPriority: Ref<Priority | null>;      // null = все
  filterColor: Ref<string | null>;           // null = все

  sortBy: Ref<TaskSortField>;                // 'createdAt'
  sortOrder: Ref<'asc' | 'desc'>;            // 'desc'
}

### 2.4 DayTemplateInput

```
interface DayTemplateInput {
  name: string;               // 1..50
  accentColor: string;        // HEX
  timeStart: string;          // 'HH:mm'
  timeEnd: string;            // parseClock: HH:mm, минуты 00/15/30/45, > timeStart, длина 60..1425

```

Вход нормализуется перед сохранением: `repeatRule = repeat.normalizeRule(input.repeatRule)`. Поля, не относящиеся к выбранному `type`, отбрасываются, значения дедуплицируются и сортируются — поэтому состояние «type = weekdays, но monthdays тоже заполнен» не может попасть ни в БД, ни в detect/resolve. Нормализация не заменяет валидацию: значения вне диапазона отклоняются (§2.5), а не «подчищаются».

### 2.5 Правила валидации (детально)

Порядок проверок в `validate(input, excludeId?)`: сначала правило (`repeat.validateRule`), затем пересечения (`repeat.validateNoOverlap`), затем имя и время. Все проблемы возвращаются одним массивом ValidationIssue.

| Правило | Проверка | Issue |
| --- | --- | --- |
| Значения правила | weekdays ∈ 0..6, monthdays ∈ 1..31, только целые | INVALID_RULE (values — плохие значения), `conflictingTemplateIds: []` |
| Правило не пустое | для weekdays — массив не пуст; для monthdays — массив не пуст | EMPTY_RULE |
| Пересечение weekdays | Ни один weekday из нового правила не занят другим шаблоном; правила обеих сторон нормализуются | OVERLAP_WEEKDAYS, conflictingTemplateIds — виновники, values — пересечение |
| Пересечение monthdays | Ни одно monthday не занято | OVERLAP_MONTHDAYS |
| Имя | 1..50 после trim | INVALID_NAME |
| Цвет | `/^#[0-9A-F]{6}$/i` | INVALID_COLOR |
| Время | `dates.parseClock('HH:mm')` не null (часы 00–23, минуты 00/15/30/45), timeEnd > timeStart, длина ≥ 60 и ≤ 1425 мин | INVALID_TIME |

weekdays и monthdays между собой не конфликтуют — приоритет у monthdays (FR-C-1). Маппинг в Result у createTemplate/updateTemplate: если среди issues есть OVERLAP_* — `CONFLICT` с `details.conflictingTemplateIds`; иначе первая не-overlap проблема → `VALIDATION_ERROR` с `details.issue`; сохранение не выполняется ни в одном из случаев.

### 2.6 reorder — детали
Принимает индексы из UI (vuedraggable). Реализация:

- Оптимистично меняет локальный массив.

- Пересчитывает order (0..n-1). Перед записью запоминает прежние `order`.

- Bulk-update в БД в одной транзакции (db.transaction('rw', db.dayTemplates, ...)).

- При ошибке — вернуть запомненные `order` тем же объектам. Мутация до транзакции без отката оставляет стор и БД разными.

### 3.4 Детальная логика

#### initialize()

- Загрузить CycleStateDto из БД (singleton). Отсутствующие поля (например, lastAutoShiftDate в базе, созданной до ревизии 1.2) достраиваются дефолтами — см. ensureCycleState в скаффолде §5.

- Если activeInstanceId существует — загрузить экземпляр. Если он не найден (битая ссылка) — считать, что текущего дня нет.

- Если экземпляр есть и его date равна сегодняшней локальной дате — оставить его текущим, даже если status уже completed. resolveCurrentDay не вызывать.

- Если экземпляра нет (в том числе activeInstanceId === null — так выглядит перезагрузка на виртуальном пустом дне) — вызвать resolveCurrentDay() на сегодня.

- Если экземпляр completed и его date меньше сегодня — вызвать resolveCurrentDay() на сегодня (вчерашний завершённый день не переиспользуется, ТЗ §2.9).

- Если экземпляр active и его date меньше сегодня — не материализовать новый день, перейти к checkDayChange().

- Подписка liveQuery — целевой контракт; в скаффолде её ещё нет (скаффолд §6).

#### checkDayChange() — FR-C-4

- Вызывается из initialize, из App.vue по visibilitychange и по таймеру на 00:00:05 локального времени, а также когда computed currentDate меняет значение.

- «Сегодня» внутри функции — format(new Date(), 'yyyy-MM-dd'), не кэш useNow.

- Если currentInstance пуст или его date >= сегодня — выйти.

- Если текущий день виртуальный (нет в Dexie, isVirtualInstance) — диалога нет: вызвать resolveCurrentDay() на новую дату. В историю ничего не пишется (FR-D-6, ТЗ §2.9).

- Если текущий день completed (и его date < сегодня) — диалога нет: вызвать resolveCurrentDay() на сегодня. Отметки не переносятся (правило 13).

- Если текущий день active и его date < сегодня:
  - Если skippedAutoPromptDate === сегодня — выйти.
  - Если settings.autoShiftAtMidnight — выполнить авто-сдвиг: перечитать cycleState из БД; если lastAutoShiftDate === сегодня, выйти (второй авто-сдвиг в те же сутки запрещён). Иначе shiftPending = true, shiftMode = 'midnight', completionSource = 'shift' и вызвать completeDay с marks: у размещения со статусом `done` — `'done'`, у остальных — `'skipped'`. В skipped уходит только неотмеченное. Диалог не открывать.
  - Иначе, если settings.askToCompleteOnNewDay — completionSource = 'auto', completing = true.
  - Иначе ничего не делать: старый день остаётся активным.

- Защита от повторного входа: `dayChangeInFlight` охватывает все асинхронные ветки — виртуальный день, завершённый день и авто-сдвиг. Пока флаг истинен, повторный `checkDayChange` (полночь и `visibilitychange` в одну секунду) выходит сразу и не создаёт второй экземпляр на ту же дату.

#### resolveCurrentDay(opts) — FR-C-1

```
date = сегодняшняя локальная дата (todayISO)
cur = currentInstance
Выйти с ok(cur), если cur.date === date и не (opts.force && cur виртуальный).
1. template = repeat.resolveDayForDate(date, templates, lastCyclicTemplateId)
2. Собрать DayInstance { id: uuid, date, templateId: template?.id ?? null, status: 'active',
   placements: [], timeStart: template?.timeStart ?? '08:00', timeEnd: template?.timeEnd ?? '22:00',
   createdAt: now }
3. Если template есть — материализовать сразу: транзакция add(instance) + cycleState.activeInstanceId = id.
   Если шаблона нет — это виртуальный пустой день (FR-D-6): в Dexie НЕ писать,
   cycleState.activeInstanceId = null.
4. currentInstance = instance
```

Пояснения:

- `force: true` пересчитывает только виртуальный день (например, после создания шаблона на сегодня, ТЗ §2.9 правило 7а). Сохранённый экземпляр с размещениями force не пересоздаёт — защита от потери размещений.
- Шаги выбора шаблона — чистая функция repeat.resolveDayForDate (ТЗ §4.4, тесты в §9). Числа 29–31 в коротком месяце не совпадают с monthday и проваливаются дальше по приоритету FR-C-1.

#### shiftToNextDay() — FR-C-3

- Проверка: currentInstance.status === 'active'. Иначе `DAY_NOT_ACTIVE`.
- Проверка: canShiftNext (manualShiftDate !== сегодня). Иначе `SHIFT_ALREADY_DONE_TODAY`.
- shiftPending = true, shiftMode = (currentInstance.date === todayISO() ? 'early' : 'overdue'), completionSource = 'shift', completing = true. Вернуть управление UI. manualShiftDate и lastAutoShiftDate на этом шаге не писать.
- Материализация следующего экземпляра выполняется внутри completeDay, пока shiftPending истинен. Отдельного продолжения после возврата из shiftToNextDay нет.

#### completeDay(marks)

- Для каждого Placement: marks[id] === 'done' → done, иначе (в том числе отсутствует и ошибочный 'pending') → skipped.

- status = 'completed', completedAt = now. activeInstanceId пока остаётся на этом экземпляре.

- Снапшоты сессии до мутации: lastCompletedInstanceId, placementsSnapshot, lastCyclicTemplateIdSnapshot, manualShiftDateSnapshot. lastAutoShiftDate намеренно не снапшотится: отмена завершения не должна разрешать повторный авто-сдвиг в те же сутки (FR-E-3).

- Транзакция: записать экземпляр через put() — для виртуального пустого дня это вставка, и тогда в том же патче cycleState пишется activeInstanceId = instance.id (FR-D-6). Если завершённый шаблон циклический — обновить lastCyclicTemplateId и в БД, и в памяти cycleState. manualShiftDate и lastAutoShiftDate не очищать.

- Если shiftPending (кнопка сдвига или autoShiftAtMidnight): режим берётся из shiftMode (см. §3.3), а даты — из `repeat.resolveShiftTargets(instance.date, today, mode)`:
  - targetDate всегда сегодня — дата нового экземпляра;
  - templateDate = сегодня + 1 при 'early' и сегодня при 'midnight'/'overdue';
  - шаблон — resolveDayForDate(templateDate, templates, уже продвинутый lastCyclicTemplateId);
  - cycleState: при 'early'/'overdue' пишется manualShiftDate = сегодня, при 'midnight' — lastAutoShiftDate = сегодня (manualShiftDate не трогается, FR-C-4);
  - новый экземпляр с templateId === null (пустой день) в Dexie не пишется, activeInstanceId = null; иначе он добавляется в БД и activeInstanceId = его id;
  - id нового экземпляра сохраняется в nextInstanceId (для отмены).

- Если shiftPending ложен и завершённый день просрочен (instance.date < today): после фиксации вызывается resolveCurrentDay() — на сегодня разрешается новый день без диалога и без отметок (FR-E-2, правило 13). Если новый день сохранён, его id тоже пишется в nextInstanceId; если он виртуальный, activeInstanceId = null. Если resolveCurrentDay вернул ошибку, фиксация уже в БД не откатывается: completing = false, statsStore.recompute() всё равно вызывается, наружу — `DB_ERROR` с `details.reason = 'RESOLVE_AFTER_COMPLETE'`. Повтор — отдельный вызов resolveCurrentDay(), не повтор completeDay (день уже completed, будет DAY_NOT_ACTIVE).

- Если shiftPending ложен и дата дня = сегодня: currentInstance остаётся завершённым экземпляром. Новый экземпляр не создаётся.

- shiftPending = false, shiftMode = null, completionSource = null, completing = false только в успешной ветке.

- При ошибке БД откатить статусы и снапшоты, вернуть текущий день как был. completing не сбрасывать: диалог остаётся, пользователь может повторить. Экземпляр, созданный этим завершением, если транзакция откатилась, не оставлять.

- Пересчёт статистики — statsStore.recompute() сразу после успешной фиксации (или liveQuery, когда подписка появится). Имени aggregate() у стора нет. Ошибка пересчёта не отменяет завершение дня — она логируется, день остаётся завершённым.

#### cancelCompletion() — FR-E-3

- Проверка: lastCompletedInstanceId и placementsSnapshot в памяти сессии.

- Вернуть тот экземпляр в status = 'active', убрать completedAt, восстановить placements.

- cycleState.activeInstanceId = восстановленный id, currentInstance = он.

- lastCyclicTemplateId вернуть из lastCyclicTemplateIdSnapshot (и в БД, и в памяти).

- manualShiftDate вернуть из manualShiftDateSnapshot. lastAutoShiftDate не восстанавливается: авто-сдвиг в эти сутки уже выполнен, повторять его нельзя (FR-E-3).

- Если nextInstanceId задан — удалить этот экземпляр из БД (он создан тем же завершением и размещений не накопил). Если экземпляр был виртуальным, delete — no-op.

- Сбросить lastCompletedInstanceId, placementsSnapshot, lastCyclicTemplateIdSnapshot, manualShiftDateSnapshot, nextInstanceId. Повторная отмена невозможна.

- completing = false. Доступно только в текущей сессии.

#### dismissCompletion()

- completing = false, shiftPending = false, shiftMode = null.

- Если completionSource === 'auto' — skippedAutoPromptDate = сегодняшняя локальная дата (format(new Date())). Настройку askToCompleteOnNewDay не менять.

- completionSource = null.

#### startCompletion() — FR-E-1

- Если currentInstance в статусе active: completionSource = 'manual', completing = true.

- Закрытие без подтверждения идёт через dismissCompletion, а не прямой записью в completing. completeDay и cancelCompletion сами ставят completing = false в успешной ветке. Откат completeDay после ошибки БД completing не трогает.

#### skipPendingPlacementsForTask(taskId)

- Служебный action для побочного эффекта FR-T-3: получает taskId от emitter onTaskArchived (см. контракты §1.5/§1.6) и переводит pending-размещения этого дела в текущем активном экземпляре в skipped + persist.

- Не вызывается из UI; экспортируется, чтобы его можно было покрыть тестом.

#### dispose()

- Отписка от emitter onTaskArchived (unmount/HMR). В setup-сторе подписка ставится в initialize().

#### placeTask(taskId, startMin)

- Если текущего дня нет или его status !== 'active' → `DAY_NOT_ACTIVE`.

- Найти задачу в tasksStore.taskById; нет — `NOT_FOUND`. Если `task.archived` — `CONSTRAINT_VIOLATION` (FR-T-3).

- Валидация слота: `startMin === null` — допустимо (сразу в нераспределённые). Число — только если `scheduler.isValidStartMin(startMin)` (целое, кратно 15, ≥ 0). Иначе `VALIDATION_ERROR` с `details.field = 'startMin'`; данные не меняются, snap к сетке не делается (FR-B-4).

- Границы дня — timeStart/timeEnd текущего экземпляра (снимок, не текущий шаблон). `scheduler.fitInDay(startMin, durationMin, instance)` вызывается только для не-null и уже валидного startMin.

- Если дело не помещается до timeEnd — startMin = null (нераспределённое, FR-B-4). Это не ошибка валидации и не отрицательное число.

- Создать Placement со снимком:

```
{
  id, taskId, startMin, durationMin: task.durationMin,
  status: 'pending', placedAt: now,
  taskSnapshot: { title, color, priority }
}
```

- Оптимистично добавить в currentInstance.placements. Если день был виртуальным (пустой день, FR-D-6) — первое размещение материализует его: транзакция put(instance) + cycleState.activeInstanceId = instance.id. Иначе достаточно put(instance).

- При ошибке БД откатить placements (и activeInstanceId, если он был выставлен) и вернуть DB_ERROR.

- conflicts пересчитается через getter.

#### movePlacement(placementId, newStartMin)

- Размещение ищется в текущем экземпляре; нет — `NOT_FOUND`; день не active — `DAY_NOT_ACTIVE`.

- Валидация newStartMin — как в placeTask: null допустим (перенос в нераспределённые), число проверяется isValidStartMin, иначе `VALIDATION_ERROR`.

- Валидный, но не помещающийся слот → newStartMin = null (FR-B-4), а не отказ.

- Сохраняются оригинальные taskSnapshot и durationMin (снимок не обновляется).

- Оптимистично + persist; при ошибке — откат позиции.

#### replacePlacement(placementId, newTaskId)

- День не active — `DAY_NOT_ACTIVE`. Размещения нет — `NOT_FOUND`. Нового дела нет — `NOT_FOUND`. Новое дело архивное — `CONSTRAINT_VIOLATION`.

- `taskSnapshot` и `durationMin` берутся с нового дела (старый снимок не сохраняется). `status` и `placedAt` не меняются.

- Если новый `durationMin` с текущим `startMin` не проходит `fitInDay`, `startMin` становится `null` (FR-B-4). `startMin === null` остаётся `null`.

- Оптимистично + persist; при ошибке БД — откат снимка, длительности и слота.

#### changePlacementDuration(placementId, newDurationMin)

- День не active — `DAY_NOT_ACTIVE`. Размещения нет — `NOT_FOUND`.

- `newDurationMin` — целое, кратно 15, 15..1425. Иначе `VALIDATION_ERROR` с `details.field = 'durationMin'`. `Task.durationMin` не меняется (FR-T-2, FR-B-7).

- Если новый размер с текущим не-null `startMin` не помещается, `startMin` становится `null`. Уже нераспределённое таким и остаётся.

- Оптимистично + persist; при ошибке — откат.

#### setPlacementStatus(id, status)

Оптимистично + persist. Если status='done' и слот в будущем — предупреждение в UI (не блокирующее). Допустимые значения — pending | done | skipped; снятие отметки возвращает pending, а не удаляет размещение. Смена статуса влияет на счётчик конфликтов: skipped в detectConflicts не участвует (FR-B-3).

## 4. useStatsStore
Ответственность: агрегация по Placement, предоставление данных для экранов статистики.

### 4.1 State

```
interface StatsState {
  // Кэш агрегатов
  taskStats: Ref<Map<string /*taskId*/, TaskStats>>;
  overallStats: Ref<OverallStats | null>;
  history: Ref<Map<string /*taskId*/, PlacementHistoryEntry[]>>;

  // UI-фильтр
  period: Ref<StatsPeriod>;    // '7d' | '30d' | 'all'
  sortBy: Ref<StatsSortField>; // 'title' | 'rate' | 'done' | 'skipped' | 'placed'
  sortOrder: Ref<'asc' | 'desc'>;

  loading: Ref<boolean>;
  initialized: Ref<boolean>;
}

type StatsSortField = 'title' | 'rate' | 'done' | 'skipped' | 'placed';

interface TaskStats {
  taskId: string;
  title: string;        // подпись из taskSnapshot последнего по дате размещения
  color: string;
  priority: Priority;
  placed: number;
  done: number;
  skipped: number;
  pending: number;      // в MVP всегда 0: recompute выбирает только completed-экземпляры, а completeDay переводит всё в done/skipped.
                        // Поле оставлено для будущей агрегации по активным дням и в UI не показывается (FR-S-1, §4.4)
  rate: number | null;  // done / (done + skipped), null если 0/0. Дела с 0/0 в таблицу не попадают (FR-S-2)
}

interface OverallStats {
  placed: number;
  done: number;
  skipped: number;
  rate: number | null;
  periodStart: string | null;  // ISO или null для 'all'
  periodEnd: string;
}

interface PlacementHistoryEntry {
  instanceId: string;
  date: string;         // ISO
  startMin: number | null;
  durationMin: number;
  status: PlacementStatus;
  completedAt?: number;
}
```

### 4.4 Детали recompute
Выборка — только завершённые экземпляры; фильтр по периоду делается внутри aggregateStats (чистая функция), а не в запросе Dexie, чтобы логика дат не дублировалась:

```
const instances = await db.dayInstances
  .where('status').equals('completed')
  .toArray();
```

Агрегация — чистая функция aggregateStats(instances, period) в services/stats.ts (юнит-тестируема). Границы периода сравниваются по локальной дате 'YYYY-MM-DD'; отдельный хелпер isInPeriod не вводится.
Правила:

- pending не учитывается в rate. Для выборки только completed-экземпляров pending всегда 0 (completeDay переводит все размещения в done/skipped) — в MVP поле не используется и в UI не показывается; ненулевым оно станет, если в агрегацию попадут активные экземпляры.

- Дела с archived = true включаются в статистику (история не теряется).

- Дела, удалённые жёстко (FR-T-6), тоже остаются в статистике — по taskSnapshot в Placement. title/color/priority берутся из снимка с наибольшей датой экземпляра; при равной дате побеждает больший `placedAt` (FR-S-2). Два завершённых экземпляра на одну дату оба входят в счётчики.

- Дело без размещений в завершённых экземплярах периода в perTask не попадает: строки «0 / 0» в таблице нет (FR-S-2). rate = null (0/0) остаётся только у вырожденного случая placed > 0 при done + skipped = 0.

### 4.5 Побочные эффекты

| Action | Side effect |
| --- | --- |
| setPeriod | Автоматически вызывает recompute |
| subscribe | liveQuery на dayInstances → при изменениях пересчитывает |
| recompute | Вызывается страницей статистики и cycleStore.completeDay после успешной фиксации дня (FR-S-1). Ошибка пересчёта не влияет на завершение дня |

- Читает: db.dayInstances напрямую (без других сторов — см. контракты §7).

- Используется: StatsPage, TaskStatsPage. Вызывается из useCycleStore.completeDay (recompute), обратной зависимости (statsStore → cycleStore) нет.

### 5.4 Экспорт / импорт / очистка
Формат файла:

```
{
  "version": "1.0",
  "exportedAt": "2025-09-23T12:00:00Z",
  "data": {
    "tasks": [...],
    "dayTemplates": [...],
    "dayInstances": [...],
    "cycleState": {...},
    "settings": {...}
  }
}
```

exportAll: собирает все таблицы Dexie (tasks, dayTemplates, dayInstances, cycleState) плюс блок settings — он читается из localStorage по ключам из §5.1 и собирается в объект вручную. Сериализует всё в JSON, возвращает Blob для q-file/download. После успешного экспорта обновляется lastBackupAt (ISO-строка в localStorage).
importAll:

- Читает файл, парсит JSON. Ошибка парсинга → VALIDATION_ERROR, данные не меняются.
- Валидирует структуру до записи: `version` — поддерживаемая строка («1.0»); `data` содержит все пять блоков; tasks/dayTemplates/dayInstances — массивы; cycleState — объект с полем id === 'current'; settings — объект. Ошибка структуры или версии → VALIDATION_ERROR с `details.reason` ('VERSION_UNSUPPORTED' | 'MALFORMED'), данные не меняются. Пересечения правил, длительность и формат времени импорт не проверяет (ТЗ FR-SET-5): день потом выбирает `resolveDayForDate`, первый шаблон по `order`.
- Диалог подтверждения: «Перезаписать все данные?»
- Транзакция: очистка + bulk-add (Dexie). cycleState пишется через ensureCycleState (отсутствующие поля достраиваются дефолтами, ТЗ §3.3).
- Блок settings записывается в localStorage, а не в Dexie.
- Переинициализация сторов (перезагрузка страницы или reload всех).

clearAll (FR-SET-10): подтверждение → очистка таблиц tasks/dayTemplates/dayInstances, пересоздание cycleState через ensureCycleState, удаление ключей `tododay:*` из localStorage, сброс сессионного состояния сторов, затем та же переинициализация, что и после импорта. Пока идёт очистка, UI блокирует повторный вызов (флаг busy).

### 5.5 Побочные эффекты

| Action | Side effect |
| --- | --- |
| setTheme | Dark.set() из Quasar |
| setLanguage | i18n.global.locale.value = l (немедленное переключение локали) |
| importAll | Триггерит window.location.reload() (или явный rehydrate всех сторов) |
| clearAll | Чистит Dexie + localStorage, сбрасывает in-memory состояние сторов, затем reload/rehydrate |

## 7. Взаимодействие сторов — карта зависимостей

```
                   ┌───────────────────┐
                   │ useSettingsStore  │  независим; настройки — localStorage,
                   │ (тема, язык,      │  читается остальными сторами и UI
                   │  экспорт/импорт)  │
                   └─────────┬─────────┘
                             │ читают настройки
                             ▼
    ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
    │ useTasks    │──▶│ useCycle    │◀──│ useDays     │
    │ Store       │   │ Store       │   │ Store       │
    └──────┬──────┘   └──────┬──────┘   └──────┬──────┘
           │                 │                 │
           │ пишут в Dexie   │                 │
           └────────┬────────┴────────┬────────┘
                    ▼                 ▼
         ┌───────────────────────────────────────┐
         │ IndexedDB (Dexie): tasks,             │
         │ dayTemplates, dayInstances, cycleState│
         └───────────────────┬───────────────────┘
                             │ читает напрямую
                             ▼
                      ┌─────────────┐
                      │ useStats    │  ← не зависит ни от одного стора
                      │ Store       │
                      └─────────────┘

    ┌─────────────┐
    │ useUiStore  │  ← независим (тосты, диалоги, online/offline)
    └─────────────┘
```

Стрелка useTasksStore → useCycleStore на схеме — не импорт стора, а emitter onTaskArchived (archiveTask снимает pending-размещения; см. контракты §1.5/§1.6). Остальные стрелки — обычные зависимости между сторами.

Правила зависимостей:

- useTasksStore не знает о useStatsStore (и вообще о статистике).

- useCycleStore зависит от tasksStore и daysStore, читает askToCompleteOnNewDay и autoShiftAtMidnight из settingsStore (в checkDayChange) и подписывается на emitter архивации из tasksStore. После успешного completeDay он вызывает statsStore.recompute() — это единственная зависимость cycle → stats, обратной нет.

- useStatsStore читает БД напрямую, не зависит от cycleStore/tasksStore/daysStore (чтобы не плодить циклы). На диаграмме выше к useStats ведёт стрелка от IndexedDB, а не от сторов.

- useUiStore — независим.

- useSettingsStore — независим, но его actions вызывают reload других сторов при импорте.
Порядок инициализации в App.vue (onMounted):

```
1. settingsStore.setTheme(settings.theme)   // sync, из localStorage
2. settingsStore.setLanguage(settings.language) // sync: применяет локаль i18n
3. cycleStore.initialize()                  // сам вызывает tasks.loadAll() и days.loadAll(), в конце checkDayChange()
4. statsStore.recompute()                   // lazy, на странице статистики; отдельно вызывается из completeDay
5. uiStore: слушатели online/offline и visibilitychange; таймер полуночи вызывает cycleStore.checkDayChange()
```

Повторный loadAll снаружи initialize не нужен: App.vue вызывает только cycle.initialize().

## 9. Тестирование
Юнит-тесты (Vitest) для каждой чистой функции:

- validateTaskInput — границы полей.

- validateNoOverlap — все 4 сценария (weekdays×weekdays, monthdays×monthdays, weekdays×monthdays, none) + INVALID_RULE / EMPTY_RULE.

- normalizeRule — отбрасывает поля, не относящиеся к type; дедупликация и сортировка.

- resolveDayForDate — 5 сценариев (monthday → weekday → cyclic → empty, приоритет monthday).

- resolveShiftTargets — 'early' в те же сутки (templateDate = завтра), 'overdue' и 'midnight' (templateDate = сегодня), противоречивый 'early' (instanceDate !== today) вырождается в 'overdue' + console.warn.

- detectConflicts — пусто / одно пересечение / несколько; skipped-размещение конфликта не создаёт.

- isValidStartMin — 0, 15, 1425 → true; −15, 7, 15.5, NaN, '15' → false.

- fitInDay(startMin, durationMin, instance) — ровно в притык по границам экземпляра / на 15 мин больше.

- aggregateStats — границы периодов, отсутствие данных, деление на ноль, отсутствие дела без размещений в периоде в perTask.

- dates.* — todayISO/toLocalISO/addDaysISO/parseISODate/parseClock на границе суток (локальная зона ≠ UTC). `weekday0 = (getDay() + 6) % 7`: понедельник → 0, воскресенье → 6.

- validateTaskInput — 1425 принимается, 1440 и 7 отклоняются.
Интеграционные тесты сторов:

- cycleStore.completeDay → статистика обновилась (recompute вызван).

- cycleStore.completeDay по просроченному дню → создан день на сегодня, вчерашний completed, nextInstanceId заполнен.

- cycleStore.shiftToNextDay + completeDay (early) → manualShiftDate = сегодня, новый экземпляр с date = сегодня и шаблоном на завтра; повторный сдвиг в те же сутки → SHIFT_ALREADY_DONE_TODAY.

- completeDay (overdue) → новый экземпляр с date = сегодня и шаблоном на сегодня (а не на завтра).

- checkDayChange при autoShiftAtMidnight на просроченном дне → lastAutoShiftDate = сегодня, manualShiftDate не изменён, повторный вызов сдвиг не повторяет; canShiftNext остаётся true. Размещение, которое до сдвига было `done`, остаётся `done`; `pending` становится `skipped`.

- Два параллельных checkDayChange на виртуальном дне не создают два экземпляра: второй выходит по dayChangeInFlight.

- checkDayChange при завершённом вчерашнем дне → новый день без диалога.

- checkDayChange на виртуальном пустом дне → день пересоздан на новую дату, в dayInstances ничего не добавлено.

- Пустой день: resolveCurrentDay без шаблона не пишет в Dexie и не трогает activeInstanceId; placeTask материализует экземпляр и пишет activeInstanceId; повторный initialize возвращает тот же пустой день.

- completeDay на виртуальном пустом дне → экземпляр появился в БД со status completed и placements = [].

- cycleStore.completeDay + cancelCompletion → день снова active, nextInstanceId удалён, manualShiftDate восстановлен.

- Повторный initialize в ту же дату не создаёт второй экземпляр.

- tasksStore.archiveTask → активный placement переведён в skipped.

- daysStore.createTemplate при конфликте → Result.err + conflictingTemplateIds; при мусорном правиле → VALIDATION_ERROR. Время `abc` и акцентный цвет `red` → VALIDATION_ERROR. Удаление шаблона уплотняет order до 0..n-1. reorder при ошибке БД возвращает прежние order.

- placeTask архивного дела → CONSTRAINT_VIOLATION. Одно дело можно разместить в дне дважды.

- settingsStore.clearAll → таблицы пусты, ключи tododay:* удалены, ensureCycleState вернул дефолты.
Мок БД: fake-indexeddb + тестовый Dexie-instance.

import type { Task } from 'src/models/task'

class ToDoDayDB extends Dexie {

  dayInstances!: EntityTable<DayInstance, 'id'>
  cycleState!: Table<CycleStateDto, 'id'>

export const db = new ToDoDayDB()

// Синглтон состояния цикла. Дополняет отсутствующие поля дефолтами: ревизия 1.2
// добавила lastAutoShiftDate, а база могла быть создана раньше. Отдельная
// Dexie-миграция для этого не нужна (меняется не схема, а набор полей записи) —
// политика в ТЗ §3.3.
export async function ensureCycleState(): Promise<CycleStateDto> {
  const defaults: CycleStateDto = {
    id: 'current',
    activeInstanceId: null,
    lastCyclicTemplateId: null,
    manualShiftDate: null,
    lastAutoShiftDate: null,
  }

  const existing = await db.cycleState.get('current')
  if (!existing) {
    await db.cycleState.put(defaults)
    return defaults
  }

  const merged = { ...defaults, ...existing, id: 'current' as const }
  if (existing.lastAutoShiftDate === undefined) await db.cycleState.put(merged)
  return merged
}

### 6.1 src/stores/tasks.ts

```
import { defineStore } from 'pinia'
import { computed, ref } from 'vue'
import { db } from 'src/services/db'
import type { Task, TaskInput } from 'src/models/task'
import type { Priority } from 'src/models/enums'
import { ok, err, type Result } from 'src/models/common'
import { validateTaskInput } from 'src/services/validators/task'
import { i18n } from 'src/boot/i18n'

// Мини-emitter для побочного эффекта архивации (контракт §1.5: «через emitter/событие»).
// Так useCycleStore подписывается на архивацию, не создавая циклический импорт.
type TaskArchivedHandler = (taskId: string) => void | Promise<void>
const archivedHandlers = new Set<TaskArchivedHandler>()

/** Подписка на архивацию дела. Возвращает функцию отписки. */
export function onTaskArchived(handler: TaskArchivedHandler): () => void {
  archivedHandlers.add(handler)
  return () => archivedHandlers.delete(handler)
}

export const useTasksStore = defineStore('tasks', () => {
  const tasks = ref<Task[]>([])
  const loading = ref(false)
  const initialized = ref(false)

  const searchQuery = ref('')
  const filterPriority = ref<Priority | null>(null)
  const filterColor = ref<string | null>(null)
  const showArchived = ref(false)
  const sortBy = ref<'title' | 'priority' | 'duration' | 'createdAt'>('createdAt')
  const sortOrder = ref<'asc' | 'desc'>('desc')

  const activeTasks = computed(() => tasks.value.filter(t => !t.archived))
  const archivedTasks = computed(() => tasks.value.filter(t => t.archived))

  const visibleTasks = computed(() => {
    let list = showArchived.value ? tasks.value : activeTasks.value
    const q = searchQuery.value.trim().toLowerCase()
    if (q) list = list.filter(t => t.title.toLowerCase().includes(q))
    if (filterPriority.value) list = list.filter(t => t.priority === filterPriority.value)
    if (filterColor.value) list = list.filter(t => t.color === filterColor.value)

    const dir = sortOrder.value === 'asc' ? 1 : -1
    return [...list].sort((a, b) => {
      switch (sortBy.value) {
        case 'title': return a.title.localeCompare(b.title) * dir
        case 'priority': {
          const rank: Record<Priority, number> = { low: 0, medium: 1, high: 2, critical: 3 }
          return (rank[a.priority] - rank[b.priority]) * dir
        }
        case 'duration': return (a.durationMin - b.durationMin) * dir
        default: return (a.createdAt - b.createdAt) * dir
      }
    })
  })

  const taskById = (id: string) => tasks.value.find(t => t.id === id)

  async function loadAll(): Promise<Result<void>> {
    loading.value = true
    try {
      tasks.value = await db.tasks.toArray()
      initialized.value = true
      return ok(undefined)
    } catch (e) {
      return err('DB_ERROR', 'Не удалось загрузить дела', e)
    } finally {
      loading.value = false
    }
  }

  async function createTask(input: TaskInput): Promise<Result<Task>> {
    const v = validateTaskInput(input)
    if (!v.ok) return v

    const now = Date.now()
    const task: Task = {
      id: crypto.randomUUID(),
      ...input,
      title: input.title.trim(),
      archived: false,
      createdAt: now,
      updatedAt: now,
    }
    try {
      await db.tasks.add(task)
      tasks.value.push(task)
      return ok(task)
    } catch (e) {
      return err('DB_ERROR', 'Не удалось создать дело', e)
    }
  }

  async function updateTask(id: string, patch: Partial<TaskInput>): Promise<Result<Task>> {
    const current = taskById(id)
    if (!current) return err('NOT_FOUND', 'Дело не найдено')

    const merged = { ...current, ...patch, updatedAt: Date.now() }
    const v = validateTaskInput(merged)
    if (!v.ok) return v

    try {
      await db.tasks.put(merged)
      const idx = tasks.value.findIndex(t => t.id === id)
      if (idx >= 0) tasks.value[idx] = merged
      return ok(merged)
    } catch (e) {
      return err('DB_ERROR', 'Не удалось обновить дело', e)
    }
  }

  async function archiveTask(id: string): Promise<Result<void>> {
    const t = taskById(id)
    if (!t) return err<void>('NOT_FOUND', 'Дело не найдено')
    if (t.archived) return ok(undefined)

    try {
      const updatedAt = Date.now()
      await db.tasks.update(id, { archived: true, updatedAt })
      const idx = tasks.value.findIndex(x => x.id === id)
      if (idx >= 0) tasks.value[idx] = { ...t, archived: true, updatedAt }

      // Побочный эффект из контракта §1.5: активные (pending) размещения этого дела
      // переводятся в skipped. Подписчики — через emitter, чтобы не создавать
      // циклическую зависимость useTasksStore → useCycleStore (см. onTaskArchived).
      for (const handler of archivedHandlers) {
        try {
          await handler(id)
        } catch (e) {
          console.warn('[tasks] не удалось обработать архивные размещения', e)
        }
      }
      return ok(undefined)
    } catch (e) {
      return err<void>('DB_ERROR', 'Не удалось архивировать дело', e)
    }
  }

  async function unarchiveTask(id: string): Promise<Result<void>> {
    const t = taskById(id)
    if (!t) return err<void>('NOT_FOUND', 'Дело не найдено')

    try {
      const updatedAt = Date.now()
      await db.tasks.update(id, { archived: false, updatedAt })
      const idx = tasks.value.findIndex(x => x.id === id)
      if (idx >= 0) tasks.value[idx] = { ...t, archived: false, updatedAt }
      return ok(undefined)
    } catch (e) {
      return err<void>('DB_ERROR', 'Не удалось вернуть дело из архива', e)
    }
  }

  async function deleteTask(id: string): Promise<Result<void>> {
    const t = taskById(id)
    if (!t) return err<void>('NOT_FOUND', 'Дело не найдено')
    // Hard delete разрешён только для архивных (контракт §1.3/§1.5)
    if (!t.archived) {
      return err<void>('CONSTRAINT_VIOLATION', 'Удалять можно только дела из архива')
    }
    try {
      await db.tasks.delete(id)
      tasks.value = tasks.value.filter(x => x.id !== id)
      return ok(undefined)
    } catch (e) {
      return err<void>('DB_ERROR', 'Не удалось удалить дело', e)
    }
  }

  async function duplicateTask(id: string): Promise<Result<Task>> {
    const src = taskById(id)
    if (!src) return err('NOT_FOUND', 'Дело не найдено')
    // Название копии ограничено 100 символами (валидатор), поэтому обрезаем базу
    const suffix = String(i18n.global.t('tasks.copySuffix'))
    const base = src.title.slice(0, 100 - suffix.length).trimEnd()
    return createTask({
      title: `${base}${suffix}`,

import { defineStore } from 'pinia'

const OVERLAP_CODES = ['OVERLAP_WEEKDAYS', 'OVERLAP_MONTHDAYS'] as const

export const useDaysStore = defineStore('days', () => {
  const templates = ref<DayTemplate[]>([])
  const loading = ref(false)
  const initialized = ref(false)

  const orderedTemplates = computed(() =>
    [...templates.value].sort((a, b) => a.order - b.order),
  )
  const cyclicTemplates = computed(() =>
    orderedTemplates.value.filter(t => t.repeatRule.type === 'none'),
  )
  const templateById = (id: string) => templates.value.find(t => t.id === id)

  const weekdayMap = computed(() => {
    const map = new Map<number, string>()
    // Тот же приоритет, что resolveDayForDate: первый по order, не последний в массиве.
    for (const t of orderedTemplates.value) {
      if (t.repeatRule.type === 'weekdays') {
        for (const wd of t.repeatRule.weekdays ?? []) {
          if (!map.has(wd)) map.set(wd, t.id)
        }
      }
    }
    return map
  })

  const monthdayMap = computed(() => {
    const map = new Map<number, string>()
    for (const t of orderedTemplates.value) {
      if (t.repeatRule.type === 'monthdays') {
        for (const md of t.repeatRule.monthdays ?? []) {
          if (!map.has(md)) map.set(md, t.id)
        }
      }
    }
    return map
  })

  // FR-C-2: циклические шаблоны недостижимы, если weekdays закрыли все 7 дней.
  const cyclicUnreachable = computed(() => {
    if (!cyclicTemplates.value.length) return false
    const covered = new Set<number>()
    for (const t of orderedTemplates.value) {
      if (t.repeatRule.type !== 'weekdays') continue
      for (const wd of t.repeatRule.weekdays ?? []) covered.add(wd)
    }
    return covered.size === 7
  })

  async function loadAll(): Promise<Result<void>> {
    loading.value = true
    try {
      templates.value = await db.dayTemplates.toArray()
      initialized.value = true
      return ok(undefined)
    } catch (e) {
      return err('DB_ERROR', 'Не удалось загрузить шаблоны', e)
    } finally {
      loading.value = false
    }
  }

  // Валидация как в контрактах §2.5: сначала правило, затем пересечения, затем имя и время.
  function validate(input: DayTemplateInput, excludeId?: string): ValidationIssue[] {
    const issues = validateNoOverlap(input.repeatRule, templates.value, excludeId)

    const name = input.name.trim()
    if (name.length < 1 || name.length > 50) {
      issues.push({
        code: 'INVALID_NAME',
        message: 'Название: 1–50 символов',
        conflictingTemplateIds: [],
      })
    }
    if (!/^#[0-9A-F]{6}$/i.test(input.accentColor ?? '')) {
      issues.push({
        code: 'INVALID_COLOR',
        message: 'Цвет: HEX #RRGGBB',
        conflictingTemplateIds: [],
      })
    }
    const start = parseClock(input.timeStart)
    const end = parseClock(input.timeEnd)
    const span = start !== null && end !== null ? end - start : NaN
    if (start === null || end === null || span < 60 || span > 1425) {
      issues.push({
        code: 'INVALID_TIME',
        message: 'Время: HH:mm, минуты кратны 15, конец позже начала минимум на час',
        conflictingTemplateIds: [],
      })
    }
    return issues
  }

  /** Конфликт правил → CONFLICT, остальное → VALIDATION_ERROR. null — проблем нет. */
  function inputError(issues: ValidationIssue[]): Result<never> | null {
    const conflicts = issues.filter(i => (OVERLAP_CODES as readonly string[]).includes(i.code))
    if (conflicts.length) {
      return err('CONFLICT', 'Конфликт правил повторения', {
        conflictingTemplateIds: [...new Set(conflicts.flatMap(i => i.conflictingTemplateIds))],
      })
    }
    const first = issues[0]
    if (first) return err('VALIDATION_ERROR', first.message, { issue: first })
    return null
  }

  async function createTemplate(input: DayTemplateInput): Promise<Result<DayTemplate>> {
    const invalid = inputError(validate(input))
    if (invalid) return invalid

    const tpl: DayTemplate = {
      id: crypto.randomUUID(),
      name: input.name.trim(),
      order: templates.value.length,
      timeStart: input.timeStart,
      timeEnd: input.timeEnd,
      gridStepMin: 15,
      accentColor: input.accentColor,
      repeatRule: normalizeRule(input.repeatRule), // FR-D-1: лишние для type поля не сохраняем
      createdAt: Date.now(),
    }
    try {
      await db.dayTemplates.add(tpl)
      templates.value.push(tpl)
      return ok(tpl)
    } catch (e) {
      return err('DB_ERROR', 'Не удалось создать шаблон', e)
    }
  }

  async function updateTemplate(
    id: string,
    patch: Partial<DayTemplateInput>,
  ): Promise<Result<DayTemplate>> {
    const cur = templateById(id)
    if (!cur) return err('NOT_FOUND', 'Шаблон не найден')

    const merged: DayTemplate = { ...cur, ...patch, name: patch.name?.trim() ?? cur.name }
    merged.repeatRule = normalizeRule(merged.repeatRule)

    const invalid = inputError(validate(merged, id))
    if (invalid) return invalid

    try {
      await db.dayTemplates.put(merged)
      const idx = templates.value.findIndex(t => t.id === id)
      if (idx >= 0) templates.value[idx] = merged
      return ok(merged)
    } catch (e) {
      return err('DB_ERROR', 'Не удалось обновить шаблон', e)
    }
  }

  async function deleteTemplate(id: string): Promise<Result<void>> {
    try {
      const active = await db.dayInstances
        .where('templateId').equals(id)
        .and(i => i.status === 'active')
        .first()
      if (active) {
        return err('CONSTRAINT_VIOLATION', 'Шаблон используется активным днём', {
          instanceId: active.id,
        })
      }
      const rest = templates.value
        .filter(t => t.id !== id)
        .sort((a, b) => a.order - b.order)
      const previousOrders = new Map(rest.map(t => [t.id, t.order]))
      rest.forEach((t, i) => (t.order = i))
      try {
        await db.transaction('rw', db.dayTemplates, async () => {
          await db.dayTemplates.delete(id)
          await db.dayTemplates.bulkPut(rest)
        })
      } catch (e) {
        for (const t of rest) {
          const prev = previousOrders.get(t.id)
          if (prev !== undefined) t.order = prev
        }
        throw e
      }
      templates.value = rest
      return ok(undefined)
    } catch (e) {
      return err('DB_ERROR', 'Не удалось удалить шаблон', e)
    }
  }

  async function reorder(fromIndex: number, toIndex: number): Promise<Result<void>> {
    const list = [...orderedTemplates.value]
    const previousOrders = new Map(list.map(t => [t.id, t.order]))
    const [moved] = list.splice(fromIndex, 1)
    if (!moved) return err('VALIDATION_ERROR', 'Некорректный индекс порядка')
    list.splice(toIndex, 0, moved)
    list.forEach((t, i) => (t.order = i))
    try {
      await db.transaction('rw', db.dayTemplates, async () => {
        await db.dayTemplates.bulkPut(list)
      })
      templates.value = list
      return ok(undefined)
    } catch (e) {
      for (const t of list) {
        const prev = previousOrders.get(t.id)
        if (prev !== undefined) t.order = prev
      }
      return err('DB_ERROR', 'Не удалось изменить порядок шаблонов', e)
    }
  }

  return {
    templates, loading, initialized,
    orderedTemplates, cyclicTemplates, cyclicUnreachable, templateById, weekdayMap, monthdayMap,
    loadAll, createTemplate, updateTemplate, deleteTemplate, reorder, validate,
  }
})

   * виртуальный пустой день (только в памяти, activeInstanceId = null).
   * force пересчитывает виртуальный день, когда на сегодня появился шаблон.
   */
  async function resolveCurrentDay(opts?: { force?: boolean }): Promise<Result<DayInstance>> {
    const today = todayISO()
    const cur = currentInstance.value
    if (cur?.date === today && !(opts?.force && isVirtualInstance.value)) return ok(cur)

    const days = useDaysStore()
    // FR-C-1. Выбор шаблона — repeat.resolveDayForDate (тесты в контрактах §9).
    const tpl = resolveDayForDate(
      today,
      days.orderedTemplates,
      cycleState.value?.lastCyclicTemplateId ?? null,
    )

    const inst: DayInstance = {
      id: crypto.randomUUID(),
      templateId: tpl?.id ?? null,
      date: today,
      status: 'active',
      placements: [],
      timeStart: tpl?.timeStart ?? '08:00',
      timeEnd: tpl?.timeEnd ?? '22:00',
      createdAt: Date.now(),
    }

    try {
      if (tpl) {
        // День по шаблону материализуется сразу
        await db.transaction('rw', db.dayInstances, db.cycleState, async () => {
          await db.dayInstances.add(inst)
          await db.cycleState.update('current', { activeInstanceId: inst.id })
        })
      } else {
        // FR-D-6: пустой день виртуален — в Dexie не пишем
        await db.cycleState.update('current', { activeInstanceId: null })
      }
    } catch (e) {
      return err('DB_ERROR', 'Не удалось разрешить текущий день', e)
    }

    currentInstance.value = inst
    if (cycleState.value) cycleState.value.activeInstanceId = tpl ? inst.id : null
    return ok(inst)
  }

  /** Экземпляр нового дня после сдвига. Дата шаблона — из repeat.resolveShiftTargets (ТЗ §2.8). */
  function buildShiftedInstance(

    today: string,
    nextLastCyclicId: string | null,
  ): DayInstance {
    const finishedDate = currentInstance.value?.date ?? today
    // Шаблон берётся от даты завершаемого экземпляра, а не от new Date():
    // 'early' → завтрашний календарь, 'midnight'/'overdue' → сегодняшний.
    const { targetDate, templateDate } = resolveShiftTargets(finishedDate, today, mode)
    const tpl = resolveDayForDate(templateDate, useDaysStore().orderedTemplates, nextLastCyclicId)
    return {
      id: crypto.randomUUID(),
      templateId: tpl?.id ?? null,
      date: targetDate,
      status: 'active',
      placements: [],
      timeStart: tpl?.timeStart ?? '08:00',
      timeEnd: tpl?.timeEnd ?? '22:00',
      createdAt: Date.now(),
    }
  }

  async function completeDay(
    marks: Record<string, 'done' | 'skipped'>,
  ): Promise<Result<void>> {
    const inst = currentInstance.value
    if (!inst || inst.status !== 'active') return err('DAY_NOT_ACTIVE', 'Нет активного дня')

    const wasShift = shiftPending.value
    const wasVirtual = isVirtualInstance.value
    const today = todayISO()
    const prevLast = cycleState.value?.lastCyclicTemplateId ?? null
    const prevManual = cycleState.value?.manualShiftDate ?? null

    lastCompletedInstanceId.value = inst.id
    placementsSnapshot.value = inst.placements.map(p => ({ ...p, taskSnapshot: { ...p.taskSnapshot } }))
    lastCyclicTemplateIdSnapshot.value = prevLast
    manualShiftDateSnapshot.value = prevManual
    nextInstanceId.value = null

    for (const p of inst.placements) {
      p.status = marks[p.id] === 'done' ? 'done' : 'skipped'
    }
    inst.status = 'completed'
    inst.completedAt = Date.now()

    // Циклический указатель двигает только завершение циклического шаблона (FR-C-2)
    const finishedTemplate = inst.templateId
      ? useDaysStore().templateById(inst.templateId)
      : undefined
    const nextLast =
      finishedTemplate?.repeatRule.type === 'none' ? inst.templateId : prevLast

    // Режим сдвига: выставлен shiftToNextDay ('early'/'overdue') или checkDayChange ('midnight').
    // Если флаг сдвига есть, а режима нет — выводим из даты завершаемого дня и предупреждаем.
    let mode: ShiftMode | null = null
    if (wasShift) {
      mode = shiftMode.value
      if (!mode) {
        mode = inst.date === today ? 'early' : 'overdue'
        console.warn('[cycle] shiftPending без shiftMode — режим выведен из даты:', mode)
      }
    }
    // Даты берутся от даты завершаемого экземпляра (ТЗ §2.8), а не от new Date()
    const shifted = mode ? buildShiftedInstance(mode, today, nextLast) : null
    const shiftedIsEmpty = shifted !== null && shifted.templateId === null

    try {
      await db.transaction('rw', db.dayInstances, db.cycleState, async () => {
        // put() работает и для виртуального пустого дня: он вставляется (FR-D-6)
        await db.dayInstances.put(inst)
        const patch: Partial<CycleStateDto> = {}
        if (nextLast !== prevLast && nextLast) patch.lastCyclicTemplateId = nextLast
        if (wasVirtual) patch.activeInstanceId = inst.id
        if (shifted) {
          if (shiftedIsEmpty) {
            patch.activeInstanceId = null // пустой день виртуален
          } else {
            await db.dayInstances.add(shifted)
            patch.activeInstanceId = shifted.id
          }
          if (mode === 'midnight') patch.lastAutoShiftDate = today
          else patch.manualShiftDate = today
        }
        if (Object.keys(patch).length) await db.cycleState.update('current', patch)
      })
    } catch (e) {
      inst.status = 'active'
      delete inst.completedAt
      inst.placements =
        placementsSnapshot.value?.map(p => ({ ...p, taskSnapshot: { ...p.taskSnapshot } })) ??
        inst.placements
      lastCompletedInstanceId.value = null
      placementsSnapshot.value = null
      lastCyclicTemplateIdSnapshot.value = null
      manualShiftDateSnapshot.value = null
      nextInstanceId.value = null
      // Диалог не закрываем: пользователь может повторить подтверждение.
      return err('DB_ERROR', 'Не удалось завершить день', e)
    }

    if (cycleState.value) {
      if (nextLast !== prevLast) cycleState.value.lastCyclicTemplateId = nextLast
      if (wasVirtual) cycleState.value.activeInstanceId = inst.id
      if (shifted) {
        if (mode === 'midnight') cycleState.value.lastAutoShiftDate = today
        else cycleState.value.manualShiftDate = today
        cycleState.value.activeInstanceId = shiftedIsEmpty ? null : shifted.id
      }
    }

    let resolveFailed = false
    if (shifted) {
      currentInstance.value = shifted
      nextInstanceId.value = shiftedIsEmpty ? null : shifted.id
    } else if (inst.date < today) {
      // Завершили просроченный день: сразу переходим на сегодня, без диалога и отметок (FR-E-2)
      const resolved = await resolveCurrentDay()
      if (resolved.ok && !isVirtualInstance.value) nextInstanceId.value = resolved.data.id
      if (!resolved.ok) resolveFailed = true
    }

    shiftPending.value = false
    shiftMode.value = null
    completionSource.value = null
    completing.value = false

    // FR-S-1: статистика пересчитывается сразу; её ошибка не отменяет завершение дня
    void useStatsStore()
      .recompute()
      .then(r => {
        if (!r.ok) console.warn('[cycle] статистика не пересчитана', r.error)
      })

    if (resolveFailed) {
      return err(
        'DB_ERROR',
        'День завершён, но сегодняшний день не открылся',
        { reason: 'RESOLVE_AFTER_COMPLETE' },
      )
    }

    return ok(undefined)
  }

  // FR-E-3: отмена завершения в рамках сессии
  async function cancelCompletion(): Promise<Result<void>> {
    const id = lastCompletedInstanceId.value
    const snapshot = placementsSnapshot.value
    if (!id || !snapshot) return err('NOT_FOUND', 'Нет завершённого дня для отмены')

    try {
      const inst = await db.dayInstances.get(id)
      if (!inst) return err('NOT_FOUND', 'Экземпляр дня не найден')

      inst.status = 'active'
      delete inst.completedAt
      inst.placements = snapshot.map(p => ({ ...p, taskSnapshot: { ...p.taskSnapshot } }))

      const createdId = nextInstanceId.value
      await db.transaction('rw', db.dayInstances, db.cycleState, async () => {
        await db.dayInstances.put(inst)
        // Экземпляр, созданный этим завершением (сдвиг или переход на сегодня), удаляем
        if (createdId) await db.dayInstances.delete(createdId)
        // lastAutoShiftDate не восстанавливаем: авто-сдвиг в эти сутки уже был (FR-E-3)
        await db.cycleState.update('current', {
          activeInstanceId: inst.id,
          lastCyclicTemplateId: lastCyclicTemplateIdSnapshot.value,
          manualShiftDate: manualShiftDateSnapshot.value,
        })
      })

      currentInstance.value = inst
      if (cycleState.value) {
        cycleState.value.activeInstanceId = inst.id
        cycleState.value.lastCyclicTemplateId = lastCyclicTemplateIdSnapshot.value
        cycleState.value.manualShiftDate = manualShiftDateSnapshot.value
      }
      lastCompletedInstanceId.value = null
      placementsSnapshot.value = null
      lastCyclicTemplateIdSnapshot.value = null
      manualShiftDateSnapshot.value = null
      nextInstanceId.value = null
      shiftPending.value = false
      shiftMode.value = null
      completionSource.value = null
      completing.value = false
      return ok(undefined)
    } catch (e) {
      return err('DB_ERROR', 'Не удалось отменить завершение дня', e)
    }
  }

  function startCompletion(): void {
    if (currentInstance.value?.status !== 'active') return
    completionSource.value = 'manual'
    completing.value = true
  }

  function dismissCompletion(): void {
    if (completionSource.value === 'auto') skippedAutoPromptDate.value = todayISO()
    completing.value = false
    shiftPending.value = false
    shiftMode.value = null
    completionSource.value = null
  }

  // FR-C-4 + ТЗ §2.9. «Сегодня» — todayISO(), не кэш useNow.
  function checkDayChange(): void {
    const inst = currentInstance.value
    if (!inst) return
    const today = todayISO()
    if (inst.date >= today) return
    if (dayChangeInFlight.value) return

    // Виртуальный пустой день: истории не касается, диалога нет — просто переезжаем на новую дату
    if (isVirtualInstance.value) {
      dayChangeInFlight.value = true
      void resolveCurrentDay().finally(() => {
        dayChangeInFlight.value = false
      })
      return
    }

    // День уже завершён (например, закрыли его вчера вечером): показываем сегодняшний
    if (inst.status === 'completed') {
      dayChangeInFlight.value = true
      void resolveCurrentDay().finally(() => {
        dayChangeInFlight.value = false
      })
      return
    }

    if (skippedAutoPromptDate.value === today) return

    const settings = useSettingsStore()
    if (settings.autoShiftAtMidnight) {
      dayChangeInFlight.value = true
      void autoShift().finally(() => {
        dayChangeInFlight.value = false
      })
      return
    }
    if (!settings.askToCompleteOnNewDay) return
    if (completing.value) return
    completionSource.value = 'auto'
    completing.value = true
  }

  /** Авто-сдвиг в полночь (FR-C-4): как подтверждённый сдвиг, но пишет lastAutoShiftDate. */
  async function autoShift(): Promise<void> {
    const today = todayISO()
    const inst = currentInstance.value
    if (!inst || inst.status !== 'active' || inst.date >= today) return

    // Защита от второго авто-сдвига в те же сутки, в том числе из второй вкладки
    const fresh = await db.cycleState.get('current')
    if (fresh?.lastAutoShiftDate === today) return

    shiftPending.value = true
    shiftMode.value = 'midnight'
    completionSource.value = 'shift'

    const marks: Record<string, 'done' | 'skipped'> = {}
    for (const p of inst.placements) marks[p.id] = p.status === 'done' ? 'done' : 'skipped'

    const res = await completeDay(marks)
    if (!res.ok) {
      // Диалога нет — снимаем флаги, чтобы следующий триггер мог повторить попытку
      shiftPending.value = false
      shiftMode.value = null
      completionSource.value = null
    }
  }

  // Побочный эффект архивации дела (FR-T-3): pending-размещения → skipped
  async function skipPendingPlacementsForTask(taskId: string): Promise<void> {
    const inst = currentInstance.value
    if (!inst || inst.status !== 'active') return

    const affected = inst.placements.filter(p => p.taskId === taskId && p.status === 'pending')
    if (!affected.length) return

    for (const p of affected) p.status = 'skipped'
    await db.dayInstances.put(inst)
  }

  async function shiftToNextDay(): Promise<Result<void>> {
    const inst = currentInstance.value
    if (!inst || inst.status !== 'active') return err('DAY_NOT_ACTIVE', 'День уже завершён')
    if (cycleState.value?.manualShiftDate === todayISO()) {
      return err('SHIFT_ALREADY_DONE_TODAY', 'Сдвиг в эти сутки уже выполнен')
    }
    shiftPending.value = true
    // FR-C-3 + ТЗ §2.8: в те же сутки — шаблон на завтра, просроченный день — шаблон на сегодня
    shiftMode.value = inst.date === todayISO() ? 'early' : 'overdue'
    completionSource.value = 'shift'
    completing.value = true
    return ok(undefined)
  }

  /** Общая запись размещений: оптимистично, с откатом и материализацией виртуального дня. */
  async function persistPlacements(
    inst: DayInstance,
    prev: Placement[],
    wasVirtual: boolean,
    failMessage: string,
  ): Promise<Result<void>> {
    try {
      await db.transaction('rw', db.dayInstances, db.cycleState, async () => {
        await db.dayInstances.put(inst)
        // FR-D-6: первое размещение в пустом дне сохраняет экземпляр и активный id
        if (wasVirtual) await db.cycleState.update('current', { activeInstanceId: inst.id })
      })
    } catch (e) {
      inst.placements = prev
      return err('DB_ERROR', failMessage, e)
    }
    if (wasVirtual && cycleState.value) cycleState.value.activeInstanceId = inst.id
    return ok(undefined)
  }

  /** FR-B-4: валидный, но не помещающийся слот → нераспределённое; невалидный → VALIDATION_ERROR. */
  function resolveStartMin(
    startMin: number | null,
    durationMin: number,
    inst: DayInstance,
  ): Result<number | null> {
    if (startMin === null) return ok(null)
    if (!isValidStartMin(startMin)) {
      return err('VALIDATION_ERROR', 'startMin: целое, кратно 15, не меньше 0', {
        field: 'startMin',
      })
    }
    return ok(fitInDay(startMin, durationMin, inst) ? startMin : null)
  }

  // FR-B-2/FR-B-4: размещение дела (в т.ч. первое дело в виртуальном пустом дне)
  async function placeTask(taskId: string, startMin: number | null): Promise<Result<Placement>> {
    const inst = currentInstance.value
    if (!inst || inst.status !== 'active') return err('DAY_NOT_ACTIVE', 'Нет активного дня')

    const task = useTasksStore().taskById(taskId)
    if (!task) return err('NOT_FOUND', 'Дело не найдено')
    if (task.archived) return err('CONSTRAINT_VIOLATION', 'Архивное дело нельзя поставить на доску')

    const resolved = resolveStartMin(startMin, task.durationMin, inst)
    if (!resolved.ok) return resolved

    const placement: Placement = {
      id: crypto.randomUUID(),
      taskId,
      startMin: resolved.data,
      durationMin: task.durationMin,
      status: 'pending',
      placedAt: Date.now(),
      taskSnapshot: { title: task.title, color: task.color, priority: task.priority },
    }

    const prev = inst.placements
    const wasVirtual = isVirtualInstance.value
    inst.placements = [...prev, placement]

    const persisted = await persistPlacements(inst, prev, wasVirtual, 'Не удалось разместить дело')
    if (!persisted.ok) {
      return err(persisted.error.code, persisted.error.message, persisted.error.details)
    }
    return ok(placement)
  }

  // FR-B-2/FR-B-4: перенос размещения (снимок дела и длительности сохраняем)
  async function movePlacement(
    placementId: string,
    newStartMin: number | null,
  ): Promise<Result<void>> {
    const inst = currentInstance.value
    if (!inst || inst.status !== 'active') return err('DAY_NOT_ACTIVE', 'Нет активного дня')

    const placement = inst.placements.find(p => p.id === placementId)
    if (!placement) return err('NOT_FOUND', 'Размещение не найдено')

    const resolved = resolveStartMin(newStartMin, placement.durationMin, inst)
    if (!resolved.ok) return resolved

    const prev = inst.placements
    const prevStart = placement.startMin
    placement.startMin = resolved.data

    const persisted = await persistPlacements(inst, prev, false, 'Не удалось перенести размещение')
    if (!persisted.ok) {
      placement.startMin = prevStart
      return persisted
    }
    return ok(undefined)
  }

  async function removePlacement(placementId: string): Promise<Result<void>> {
    const inst = currentInstance.value
    if (!inst || inst.status !== 'active') return err('DAY_NOT_ACTIVE', 'Нет активного дня')

    const prev = inst.placements
    if (!prev.some(p => p.id === placementId)) return err('NOT_FOUND', 'Размещение не найдено')
    inst.placements = prev.filter(p => p.id !== placementId)

    return persistPlacements(inst, prev, false, 'Не удалось убрать размещение')
  }

  // FR-T-3: если архивация уже записана, а pending-размещения остались, дожимаем их при открытии.
  async function reconcileArchivedPlacements(): Promise<void> {
    const inst = currentInstance.value
    if (!inst || inst.status !== 'active') return
    const archivedIds = new Set(
      useTasksStore().tasks.filter(t => t.archived).map(t => t.id),
    )
    if (!archivedIds.size) return
    const affected = inst.placements.filter(p => archivedIds.has(p.taskId) && p.status === 'pending')
    if (!affected.length) return
    for (const p of affected) p.status = 'skipped'
    if (!isVirtualInstance.value) await db.dayInstances.put(inst)
  }

  async function replacePlacement(placementId: string, newTaskId: string): Promise<Result<void>> {
    const inst = currentInstance.value
    if (!inst || inst.status !== 'active') return err('DAY_NOT_ACTIVE', 'Нет активного дня')
    const placement = inst.placements.find(p => p.id === placementId)
    if (!placement) return err('NOT_FOUND', 'Размещение не найдено')
    const task = useTasksStore().taskById(newTaskId)
    if (!task) return err('NOT_FOUND', 'Дело не найдено')
    if (task.archived) return err('CONSTRAINT_VIOLATION', 'Архивное дело нельзя поставить на доску')

    const prev = inst.placements
    const prevTaskId = placement.taskId
    const prevStart = placement.startMin
    const prevDuration = placement.durationMin
    const prevSnapshot = { ...placement.taskSnapshot }
    placement.durationMin = task.durationMin
    placement.taskSnapshot = { title: task.title, color: task.color, priority: task.priority }
    placement.taskId = newTaskId
    if (prevStart !== null && !fitInDay(prevStart, task.durationMin, inst)) placement.startMin = null

    const persisted = await persistPlacements(inst, prev, false, 'Не удалось заменить дело')
    if (!persisted.ok) {
      placement.taskId = prevTaskId
      placement.startMin = prevStart
      placement.durationMin = prevDuration
      placement.taskSnapshot = prevSnapshot
      return persisted
    }
    return ok(undefined)
  }

  async function changePlacementDuration(
    placementId: string,
    newDurationMin: number,
  ): Promise<Result<void>> {
    const inst = currentInstance.value
    if (!inst || inst.status !== 'active') return err('DAY_NOT_ACTIVE', 'Нет активного дня')
    const placement = inst.placements.find(p => p.id === placementId)
    if (!placement) return err('NOT_FOUND', 'Размещение не найдено')
    if (
      !Number.isInteger(newDurationMin) ||
      newDurationMin < 15 ||
      newDurationMin > 1425 ||
      newDurationMin % 15 !== 0
    ) {
      return err('VALIDATION_ERROR', 'Длительность: 15–1425 мин, кратно 15', { field: 'durationMin' })
    }

    const prev = inst.placements
    const prevStart = placement.startMin
    const prevDuration = placement.durationMin
    placement.durationMin = newDurationMin
    if (prevStart !== null && !fitInDay(prevStart, newDurationMin, inst)) placement.startMin = null

    const persisted = await persistPlacements(inst, prev, false, 'Не удалось изменить длительность')
    if (!persisted.ok) {
      placement.startMin = prevStart
      placement.durationMin = prevDuration
      return persisted
    }
    return ok(undefined)
  }

  async function setPlacementStatus(
    placementId: string,
    status: PlacementStatus,
  ): Promise<Result<void>> {
    const inst = currentInstance.value
    if (!inst || inst.status !== 'active') return err('DAY_NOT_ACTIVE', 'Нет активного дня')

    const placement = inst.placements.find(p => p.id === placementId)
    if (!placement) return err('NOT_FOUND', 'Размещение не найдено')

    const prev = inst.placements
    const prevStatus = placement.status
    placement.status = status

    const persisted = await persistPlacements(inst, prev, false, 'Не удалось изменить статус')
    if (!persisted.ok) {
      placement.status = prevStatus
      return persisted
    }
    return ok(undefined)
  }

  function startDrag(taskId: string, source: 'list' | 'board') {
    draggingTaskId.value = taskId
    dragSource.value = source
  }
  function setHoveredSlot(slotIndex: number | null) { hoveredSlot.value = slotIndex }
  function endDrag() {
    draggingTaskId.value = null
    dragSource.value = null
    hoveredSlot.value = null
  }

  // Отписка от emitter (вызывать при unmount/HMR, чтобы не копить обработчики в модульном Set)
  function dispose() {
    unsubscribeArchived?.()
    unsubscribeArchived = null
  }

  watch(currentDate, () => {
    if (!initialized.value) return
    checkDayChange()
  })

  return {
    currentInstance, cycleState, completing, loading, initialized,
    lastCompletedInstanceId, placementsSnapshot, nextInstanceId,
    shiftPending, shiftMode, completionSource, skippedAutoPromptDate,
    draggingTaskId, dragSource, hoveredSlot,
    currentDate, currentTemplate, isTemplateless, isCurrentDayEmpty, isVirtualInstance,
    slots, placementsBySlot,
    conflicts, hasConflicts, unallocatedPlacements, canShiftNext, canComplete,
    initialize, resolveCurrentDay, completeDay, cancelCompletion, checkDayChange,
    startCompletion, dismissCompletion,
    skipPendingPlacementsForTask, shiftToNextDay, dispose,
    placeTask, movePlacement, removePlacement, replacePlacement, changePlacementDuration, setPlacementStatus,
    startDrag, setHoveredSlot, endDrag,
  }
})

export const useStatsStore = defineStore('stats', () => {
  const taskStats = ref<Map<string, TaskStats>>(new Map())
  const overallStats = ref<OverallStats | null>(null)
  const period = ref<StatsPeriod>('all')
  const loading = ref(false)
  const initialized = ref(false)

  const visibleTaskStats = computed(() =>
    Array.from(taskStats.value.values()).sort((a, b) =>
      a.title.localeCompare(b.title),
    ),
  )

  async function recompute(p?: StatsPeriod): Promise<Result<void>> {
    loading.value = true
    try {
      const target = p ?? period.value
      period.value = target
      // Только завершённые экземпляры: поэтому pending в агрегатах всегда 0
      // (в MVP поле не используется — см. services/stats.ts и контракты §4.1)

        .where('status').equals('completed')
        .toArray()
      const { perTask, overall } = aggregateStats(instances, target)
      taskStats.value = perTask
      overallStats.value = overall
      initialized.value = true
      return ok(undefined)
    } catch (e) {
      return err('DB_ERROR', 'Не удалось пересчитать статистику', e)
    } finally {
      loading.value = false
    }
  }

  async function loadTaskHistory(taskId: string): Promise<Result<PlacementHistoryEntry[]>> {
    try {
      const instances = await db.dayInstances
        .where('status').equals('completed')
        .toArray()
      const out: PlacementHistoryEntry[] = []
      for (const inst of instances) {
        for (const p of inst.placements) {
          if (p.taskId === taskId) {
            out.push({
              instanceId: inst.id,
              date: inst.date,
              startMin: p.startMin,
              durationMin: p.durationMin,
              status: p.status,
              completedAt: inst.completedAt,
            })
          }
        }
      }
      out.sort((a, b) => b.date.localeCompare(a.date))
      return ok(out)
    } catch (e) {
      return err('DB_ERROR', 'Не удалось загрузить историю', e)
    }
  }

  function setPeriod(p: StatsPeriod) {
    period.value = p
    void recompute(p)
  }

  return {
    taskStats, overallStats, period, loading, initialized,
    visibleTaskStats,
    recompute, loadTaskHistory, setPeriod,
  }
})

import { format } from 'date-fns'

/** ТЗ §2.8: единственный источник локальной календарной даты 'YYYY-MM-DD'. */
export function todayISO(): string {
  return format(new Date(), 'yyyy-MM-dd')
}

/** Локальная дата из Date. toISOString() для календарной даты не используем (UTC-сдвиг). */
export function toLocalISO(date: Date): string {
  const y = date.getFullYear()
  const m = String(date.getMonth() + 1).padStart(2, '0')
  const d = String(date.getDate()).padStart(2, '0')
  return `${y}-${m}-${d}`
}

/** Разбор 'YYYY-MM-DD' по локальным компонентам: new Date('2025-09-23') дал бы UTC-полночь. */
export function parseISODate(iso: string): Date {
  const [y, m, d] = iso.split('-').map(Number)
  return new Date(y, m - 1, d)
}

/** Календарная арифметика: addDaysISO('2025-01-31', 1) === '2025-02-01'. */
export function addDaysISO(iso: string, n: number): string {
  const d = parseISODate(iso)
  d.setDate(d.getDate() + n)
  return toLocalISO(d)
}

/** 'HH:mm' → минуты от начала суток (для расчёта слотов и границ дня). */
export function minutesOfDay(hhmm: string): number {
  const [h, m] = hhmm.split(':').map(Number)
  return h * 60 + m
}

/** ТЗ FR-D-1: только HH:mm, часы 00–23, минуты 00/15/30/45. Иначе null. */
export function parseClock(hhmm: string): number | null {
  if (!/^([01]\d|2[0-3]):(00|15|30|45)$/.test(hhmm)) return null
  return minutesOfDay(hhmm)
}

import { addDaysISO } from 'src/services/dates'
import type { DayTemplate, RepeatRule, ValidationIssue } from 'src/models/day'
import type { ShiftMode } from 'src/models/enums'

/**
 * FR-C-1: выбор шаблона дня для даты 'YYYY-MM-DD'.
 * Приоритет: число месяца → день недели (0 = Пн, формула ТЗ §2.8: (getDay() + 6) % 7) → следующий циклический → null (пустой день).
 * Если lastCyclicTemplateId не найден среди циклических — берём первый по order.
 */
export function resolveDayForDate(
  date: string,
  templates: DayTemplate[],
  lastCyclicTemplateId: string | null = null,
): DayTemplate | null {
  const [year, month, day] = date.split('-').map(Number)
  const local = new Date(year, month - 1, day)
  const dayOfMonth = local.getDate()
  const weekday0 = (local.getDay() + 6) % 7

  const byMonthday = templates.find(
    t => t.repeatRule.type === 'monthdays' && t.repeatRule.monthdays?.includes(dayOfMonth),
  )
  if (byMonthday) return byMonthday

  const byWeekday = templates.find(
    t => t.repeatRule.type === 'weekdays' && t.repeatRule.weekdays?.includes(weekday0),
  )
  if (byWeekday) return byWeekday

  const cyclic = templates
    .filter(t => t.repeatRule.type === 'none')
    .sort((a, b) => a.order - b.order)
  if (!cyclic.length) return null

  const idx = lastCyclicTemplateId ? cyclic.findIndex(t => t.id === lastCyclicTemplateId) : -1
  return cyclic[(idx + 1) % cyclic.length]
}

/**
 * ТЗ §2.8: единственное место, где считается дата шаблона при сдвиге дня.
 * targetDate всегда сегодня; templateDate — завтра только для раннего ручного
 * сдвига ('early'), иначе сегодня. Инвариант 'early' — только в те же сутки.
 * Именно здесь закрыт off-by-one: шаблон берётся от даты завершаемого
 * экземпляра, а не от new Date() в момент сдвига.
 */
export function resolveShiftTargets(
  instanceDate: string,
  today: string,
  mode: ShiftMode,
): { mode: ShiftMode; targetDate: string; templateDate: string } {
  if (mode === 'early' && instanceDate !== today) {
    console.warn('[repeat] shiftMode="early" для просроченного дня — трактуем как "overdue"')
    return { mode: 'overdue', targetDate: today, templateDate: today }
  }
  return {
    mode,
    targetDate: today,
    templateDate: mode === 'early' ? addDaysISO(instanceDate, 1) : today,
  }
}

/** FR-D-1: убирает поля, не относящиеся к type; дедуплицирует и сортирует значения. */
export function normalizeRule(rule: RepeatRule): RepeatRule {
  const uniqSorted = (values: number[] | undefined) =>
    [...new Set(values ?? [])].sort((a, b) => a - b)

  if (rule.type === 'weekdays') return { type: 'weekdays', weekdays: uniqSorted(rule.weekdays) }
  if (rule.type === 'monthdays') return { type: 'monthdays', monthdays: uniqSorted(rule.monthdays) }
  return { type: 'none' }
}

/** Валидация самого правила: пустой набор и значения вне диапазона (контракты §2.5). */
export function validateRule(rule: RepeatRule): ValidationIssue[] {
  if (rule.type === 'none') return []

  const isWeekdays = rule.type === 'weekdays'
  const raw = (isWeekdays ? rule.weekdays : rule.monthdays) ?? []
  const min = isWeekdays ? 0 : 1
  const max = isWeekdays ? 6 : 31
  const bad = raw.filter(v => !Number.isInteger(v) || v < min || v > max)

  if (bad.length) {
    return [
      {
        code: 'INVALID_RULE',
        message: `Значения правила вне диапазона ${min}..${max}: ${bad.join(', ')}`,
        conflictingTemplateIds: [],
        values: bad,
      },
    ]
  }
  if (!raw.length) {
    return [
      {
        code: 'EMPTY_RULE',
        message: isWeekdays
          ? 'Выберите хотя бы один день недели'
          : 'Выберите хотя бы одно число месяца',
        conflictingTemplateIds: [],
      },
    ]
  }
  return []
}

/** FR-D-5: пересечения правил. Единый тип ValidationIssue (без OverlapIssue). */
export function validateNoOverlap(
  rule: RepeatRule,
  templates: DayTemplate[],
  excludeId?: string,
): ValidationIssue[] {
  const own = validateRule(rule)
  const normalized = normalizeRule(rule)
  const issues: ValidationIssue[] = [...own]

  if (own.some(i => i.code === 'EMPTY_RULE' || i.code === 'INVALID_RULE')) return issues

  if (normalized.type === 'weekdays' && normalized.weekdays?.length) {
    for (const t of templates) {
      if (t.id === excludeId) continue
      const other = normalizeRule(t.repeatRule)
      if (other.type !== 'weekdays') continue
      const overlap = (other.weekdays ?? []).filter(w => normalized.weekdays!.includes(w))
      if (overlap.length) {
        issues.push({
          code: 'OVERLAP_WEEKDAYS',
          message: `Пересечение по дням недели с шаблоном «${t.name}»`,
          conflictingTemplateIds: [t.id],
          values: overlap,
        })
      }
    }
  }

  if (normalized.type === 'monthdays' && normalized.monthdays?.length) {
    for (const t of templates) {
      if (t.id === excludeId) continue
      const other = normalizeRule(t.repeatRule)
      if (other.type !== 'monthdays') continue
      const overlap = (other.monthdays ?? []).filter(m => normalized.monthdays!.includes(m))
      if (overlap.length) {
        issues.push({
          code: 'OVERLAP_MONTHDAYS',
          message: `Пересечение по числам месяца с шаблоном «${t.name}»`,
          conflictingTemplateIds: [t.id],
          values: overlap,
        })
      }
    }
  }

  return issues
}

```
import { toLocalISO } from 'src/services/dates'
import type { DayInstance } from 'src/models/dayInstance'
import type { PlacementStatus, Priority } from 'src/models/enums'

export type StatsPeriod = '7d' | '30d' | 'all'

export interface TaskStats {
  taskId: string
  title: string
  color: string
  priority: Priority
  placed: number
  done: number
  skipped: number
  pending: number
  rate: number | null
}

export interface OverallStats {
  placed: number
  done: number
  skipped: number
  rate: number | null
  periodStart: string | null
  periodEnd: string
}

export interface PlacementHistoryEntry {
  instanceId: string
  date: string
  startMin: number | null
  durationMin: number
  status: PlacementStatus
  completedAt?: number
}

/** Начало периода как 'YYYY-MM-DD' (локальная дата) или null для 'all'.
 *  Окно включительное: '7d' = сегодня и 6 предыдущих дней (итого 7 дат). */
function periodStartISO(p: StatsPeriod, end: Date): string | null {
  if (p === 'all') return null
  const d = new Date(end)
  d.setDate(d.getDate() - (p === '7d' ? 6 : 29))
  return toLocalISO(d)
}

/**
 * Агрегация чистой функцией: считает ровно те экземпляры, которые переданы.
 *
 * Про pending: поле в TaskStats остаётся, но при выборке только завершённых
 * экземпляров (status = 'completed', как это делает useStatsStore.recompute) оно
 * всегда 0 — completeDay переводит все размещения в done/skipped (FR-E-2), и в
 * MVP это поле нигде не показывается. Ненулевым pending станет только если
 * передать сюда активные экземпляры (например, для будущей «статистики дня»).
 *
 * Дело без размещений в периоде в perTask не попадает вовсе (FR-S-2), поэтому
 * строки «0 / 0» в таблице статистики не бывает.
 */
export function aggregateStats(
  instances: DayInstance[],
  period: StatsPeriod,
): { perTask: Map<string, TaskStats>; overall: OverallStats } {
  const end = new Date()
  const startISO = periodStartISO(period, end)
  const perTask = new Map<string, TaskStats>()
  // Дата и placedAt последнего снимка: при одной дате побеждает больший placedAt (FR-S-2)
  const lastSeen = new Map<string, { date: string; placedAt: number }>()

  let placed = 0, done = 0, skipped = 0

  for (const inst of instances) {
    // Сравниваем строки 'YYYY-MM-DD' в локальной дате: new Date('2025-09-23')
    // парсится как UTC-полночь и на границе периода даёт сдвиг на сутки.
    if (startISO && inst.date < startISO) continue
    for (const p of inst.placements) {
      placed++
      const cur = perTask.get(p.taskId) ?? {
        taskId: p.taskId,
        title: p.taskSnapshot.title,
        color: p.taskSnapshot.color,
        priority: p.taskSnapshot.priority,
        placed: 0, done: 0, skipped: 0, pending: 0, rate: null,
      }
      cur.placed++
      if (p.status === 'done') { cur.done++; done++ }
      else if (p.status === 'skipped') { cur.skipped++; skipped++ }
      else cur.pending++

      // Снимок подписи: большая дата экземпляра, при равенстве — больший placedAt
      const seen = lastSeen.get(p.taskId)
      const newer =
        !seen ||
        inst.date > seen.date ||
        (inst.date === seen.date && p.placedAt >= seen.placedAt)
      if (newer) {
        cur.title = p.taskSnapshot.title
        cur.color = p.taskSnapshot.color
        cur.priority = p.taskSnapshot.priority
        lastSeen.set(p.taskId, { date: inst.date, placedAt: p.placedAt })
      }

      perTask.set(p.taskId, cur)
    }
  }

  for (const s of perTask.values()) {
    const denom = s.done + s.skipped
    s.rate = denom === 0 ? null : s.done / denom
  }

  const overallDenom = done + skipped
  return {
    perTask,
    overall: {
      placed, done, skipped,
      rate: overallDenom === 0 ? null : done / overallDenom,
      periodStart: startISO,
      periodEnd: toLocalISO(end),
    },
  }
}

### 7.4 src/services/scheduler.ts

```
import { minutesOfDay } from 'src/services/dates'
import type { DayInstance, Placement } from 'src/models/dayInstance'
import type { Conflict } from 'src/models/cycle'

/**
 * FR-B-4: валидный startMin — целое, кратное 15, не меньше 0.
 * Невалидное значение — ошибка VALIDATION_ERROR в placeTask/movePlacement,
 * а не snap к сетке и не null (контракты §3.4).
 */
export function isValidStartMin(v: unknown): v is number {
  return typeof v === 'number' && Number.isInteger(v) && v >= 0 && v % 15 === 0
}

/**
 * FR-B-4: помещается ли дело в интервал экземпляра.
 * Вызывается только для проверенного не-null startMin; границы — из снимка
 * экземпляра (timeStart/timeEnd), а не из текущего шаблона.
 */
export function fitInDay(
  startMin: number,
  durationMin: number,
  instance: DayInstance,
): boolean {
  const dayLength = minutesOfDay(instance.timeEnd) - minutesOfDay(instance.timeStart)
  return startMin + durationMin <= dayLength
}

/**
 * FR-B-3: пересечения подсвечиваются только для pending/done.
 * Размещения без слота (startMin === null) и пропущенные (skipped) в конфликты не входят.
 */
export function detectConflicts(placements: Placement[]): Conflict[] {
  const sorted = placements
    .filter(
      (p): p is Placement & { startMin: number } =>
        p.startMin !== null && p.status !== 'skipped',
    )
    .sort((a, b) => a.startMin - b.startMin)

  const out: Conflict[] = []
  for (let i = 0; i < sorted.length; i++) {
    for (let j = i + 1; j < sorted.length; j++) {
      const a = sorted[i]
      const b = sorted[j]
      const aEnd = a.startMin + a.durationMin
      const bEnd = b.startMin + b.durationMin
      if (b.startMin < aEnd && a.startMin < bEnd) {
        out.push({
          placementIds: [a.id, b.id],
          overlapStart: Math.max(a.startMin, b.startMin),
          overlapEnd: Math.min(aEnd, bEnd),
        })
      }
    }
  }
  return out
}

## 10. src/App.vue

```
<template>
  <router-view />
</template>

<script setup lang="ts">
import { onMounted } from 'vue'
import { useSettingsStore } from 'src/stores/settings'
import { useUiStore } from 'src/stores/ui'
import { useCycleStore } from 'src/stores/cycle'

const settings = useSettingsStore()
const ui = useUiStore()
const cycle = useCycleStore()

onMounted(async () => {
  // Тема и язык (оба — sync из localStorage; setLanguage переключает локаль i18n)
  settings.setTheme(settings.theme)
  settings.setLanguage(settings.language)

  // Онлайн/офлайн
  window.addEventListener('online', () => (ui.isOnline = true))
  window.addEventListener('offline', () => (ui.isOnline = false))

  // Инициализация цикла
  await cycle.initialize()

  // FR-C-4: старт уже проверен внутри cycle.initialize(). Здесь — возврат во вкладку
  // и таймер на 00:00:05. checkDayChange сам берёт todayISO() из new Date(),
  // поэтому минутный useNow к этому таймеру не привязан. Смена currentDate
  // дополнительно будит проверку из стора.
  let midnightTimer: ReturnType<typeof setTimeout> | undefined

  function scheduleMidnightCheck() {
    if (midnightTimer) clearTimeout(midnightTimer)
    const now = new Date()
    const nextMidnight = new Date(now.getFullYear(), now.getMonth(), now.getDate() + 1, 0, 0, 5)
    midnightTimer = setTimeout(checkDay, nextMidnight.getTime() - now.getTime())
  }

  function checkDay() {
    cycle.checkDayChange()
    scheduleMidnightCheck()
  }

  document.addEventListener('visibilitychange', () => {
    if (document.visibilityState === 'visible') checkDay()
  })
  scheduleMidnightCheck()

  // Тост, если офлайн
  if (!ui.isOnline) {
    ui.notify('Приложение работает офлайн', 'info')
  }

  // Тему применил settings.setTheme() выше (он вызывает Dark.set), поэтому
  // здесь НЕ форсируем boolean: иначе ломается режим 'auto' (dark: 'auto' в quasar.config.ts).
})
</script>
```
